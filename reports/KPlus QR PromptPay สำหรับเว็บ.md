# ต่อ KBank QR ให้ผ่านเริ่มที่ K-APi

**BLUF:** ถ้าจะลองทำ payment gateway ของ KBank เพื่อรับ QR/PromptPay บนเว็บ ให้เริ่มที่พอร์ทัลทางการชื่อ **K-APi (KBANK OPEN API) ที่ apiportal.kasikornbank.com** ไม่ใช่แอป K PLUS เพราะ **K PLUS คือแอป consumer ส่วนฝั่งร้านค้าคือผลิตภัณฑ์ QR Payment / QR API / K Payment Gateway / KGP Merchant Payment Platform** ([K APi portal](https://apiportal.kasikornbank.com/)) ความจริงที่ต้องรับให้ได้ก่อนเขียนโค้ดคือ **QR API ของ KBank ไม่มีปุ่มสมัครแล้วได้ key ทันที ต้องกรอกฟอร์มความสนใจแล้วรอเจ้าหน้าที่ติดต่อกลับภายในประมาณ 5 วันทำการ** ([BentoWeb help](https://help.bentoweb.com/th/article/qr-payment-ape0g5/)) และเอกสาร API ละเอียด (request schema, webhook signature, error table) **อยู่หลังพอร์ทัลแบบ login + JavaScript app ซึ่งดึงมาตรวจสอบจากข้างนอกไม่ได้** ดังนั้นแผนที่ดีที่สุดสำหรับ backend developer คืออ่าน landing + Try API หน้าพอร์ทัลเพื่อเข้าใจตระกูลผลิตภัณฑ์ เริ่ม prototype ด้วย static PromptPay QR หรือ aggregator (Omise/Stripe/2C2P) ที่สมัครออนไลน์ได้ในวันเดียว แล้วค่อยย้ายมา KBank ตรงเมื่อต้องการ settlement เข้าบัญชี KBank และผ่าน onboarding แล้ว

## สมัคร QR API ไม่มีปุ่ม instant key ต้องผ่านคน

ความคาดหวังแบบสมัคร Stripe แล้วได้ test key ทันทีใช้กับ KBank ไม่ได้ หน้า QR API ระบุวิธีการสมัครและคุณสมบัติเริ่มที่เข้าเว็บไซต์ KBank K API เป็นข้อ 1 จาก 9 ขั้น แต่เนื้อหาเต็มอยู่หลังรูปและ JS ([KBank QR API (TH)](https://www.kasikornbank.com/th/business/sme/financial-services/pages/qr-api.aspx)) ภาพที่ชัดกว่ามาจากคู่มือฝั่ง platform อย่าง BentoWeb ที่บอกว่ารูปแบบธุรกิจที่สมัครได้คือ **บุคคลธรรมดาและนิติบุคคล ลงทะเบียนผ่านลิงก์สนใจสมัคร QR Payment แล้วเจ้าหน้าที่จะติดต่อกลับพร้อมฟอร์มและเอกสารภายใน 5 วันทำการ** ([BentoWeb help](https://help.bentoweb.com/th/article/qr-payment-ape0g5/)) ประเด็นที่ developer มองข้ามคือถ้าต่อผ่าน platform หรือ aggregator **ต้องเช็ก Partner Shop ID จากหลังร้านมาใส่ในใบสมัคร และหลังอนุมัติจะได้ Merchant ID มากรอกในระบบ** ([BentoWeb help](https://help.bentoweb.com/th/article/qr-payment-ape0g5/)) ช่องทางติดตามผลคือ **KBIZ Call Center 02-888-8822 กด 1 ต่อ 3 ต่อ 0 แล้วแจ้งว่าต้องการติดตามสถานะสมัคร QR API พร้อม email หรือเลขบัญชีที่ใช้สมัคร** ([BentoWeb help](https://help.bentoweb.com/th/article/qr-payment-ape0g5/)) ส่วนฝั่ง KGP ใช้คนละเบอร์คือ **Support Center 02-008-8820 ตลอด 24 ชม. กับอีเมล partnersupport@kasikornglobalpayment.com สำหรับ merchant ทั่วไป** ([KGP](https://www.kasikornglobalpayment.com/en)) โมเดล credential ที่ยืนยันได้จากแหล่งเปิดมีอย่างน้อย **Merchant ID บวก Partner Shop ID กรณีผ่าน platform** ส่วน API secret OAuth client และ certificate ต้องอ่านหลัง login เพราะแหล่งทางการที่ดึงได้ไม่ลงรายละเอียด ([KBank QR API (TH)](https://www.kasikornbank.com/th/business/sme/financial-services/pages/qr-api.aspx)) แต่บทความ KBTG ยืนยันว่า partner app ที่รับรองแล้วใช้ **OAuth 2.0 client credentials** ไม่ใช่ static key อย่างเดียว ([KBTG Life](https://medium.com/kbtg-life/%E0%B8%95%E0%B9%88%E0%B8%AD-api-%E0%B8%81%E0%B8%B1%E0%B8%9A-kbank-%E0%B8%A1%E0%B8%B2%E0%B8%95%E0%B9%88%E0%B8%AD%E0%B8%81%E0%B8%B1%E0%B8%99%E0%B8%81%E0%B8%B1%E0%B8%9A-ep-2-%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99%E0%B8%9C%E0%B9%88%E0%B8%B2%E0%B8%99-oauth-2-0-b8c01ea9f5bc)) สิ่งที่ยังเป็น gap และต้องถามเจ้าหน้าที่คือ **รายการเอกสารสมัคร ระยะเวลาอนุมัติจริง และขั้นตอนขอ sandbox key เทียบกับ production key** เพราะไม่พบใน official docs แบบไม่ login และไม่พบ deep link ฟอร์มสมัครตรง

## สร้าง QR แบบ dynamic แล้วอย่าเชื่อ webhook อย่างเดียว

สำหรับ checkout บนเว็บให้เลือก **dynamic QR เสมอ คือ QR ต่อ transaction ที่ล็อกยอดไว้ ลูกค้าแก้ไม่ได้** ซึ่งต่างจาก static QR ที่เป็นป้าย reusable ให้ลูกค้ากรอกยอดเองและต้องตรวจสลิป manual ([KBank QR API (TH)](https://www.kasikornbank.com/th/business/sme/financial-services/pages/qr-api.aspx)) ([BOT Thai QR standard](https://www.bot.or.th/content/dam/bot/fipcs/documents/FPG/2562/EngPDF/25620084.pdf)) ในเชิงสเปก EMVCo Tag 01 ค่า **12 คือ dynamic ส่วน 11 คือ static Tag 54 คือยอดเงิน Tag 53 คือ 764 (THB) Tag 58 คือ TH** และ PromptPay merchant template อยู่ใต้ Tag 29 ([thai-qr-payment spec](https://thai-qr-payment.js.org/reference/spec/)) เส้นทาง K Payment Gateway คือ backend เรียก **POST /qr/v2/order** บน host แยกกันระหว่าง **production https://kpaymentgateway-services.kasikornbank.com กับ sandbox https://dev-kpaymentgateway-services.kasikornbank.com** ([Create Order API](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/Create%20Order%20API)) โดย payload ระดับ order ขับด้วย **amount currency (THB only) และ referenceOrder ที่ต้อง unique** ตามที่ community SDK สะท้อนโครงจริงทั้ง paymentType เท่ากับ qr amount currency description referenceOrder ([bilions-org/kbank-sdk](https://github.com/bilions-org/kbank-sdk)) ส่วน Embedded UI รุ่น KPG ใช้สคริปต์ kpayment.min.js ฝัง data-apikey data-amount data-payment-methods เท่ากับ qr data-order-id แล้วเรียก KPayment.show() ([bilions-org/kbank-sdk](https://github.com/bilions-org/kbank-sdk)) ลูกค้าสแกนด้วย **bank app ใดก็ได้** เพราะเป็นมาตรฐาน PromptPay กลาง ไม่ผูกกับ K PLUS ([BOT PromptPay](https://www.bot.or.th/en/financial-innovation/digital-finance/digital-payment/promptpay.html)) เมื่อลูกค้ากดยืนยันในแอปธนาคาร KBank จะยิง **HTTP POST พร้อม event ทุกครั้งที่ลูกค้ายืนยันการชำระ QR** มาที่ webhook ที่ร้านค้าลงทะเบียนไว้ล่วงหน้า ([WebHook Notify API for QR Payment](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/WebHook%20Notify%20API%20for%20QR%20Payment)) โดยมี webhook แยกตาม rail ทั้ง card QR Alipay และ payment link ([Inquiry QR Transaction API](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/Inquiry%20QR%C2%A0%20Transaction%C2%A0%20API)) แพทเทิร์นที่ถูกต้องคือ **webhook-first แต่ inquiry-confirm** คือเก็บ mapping referenceOrder กับ orderId เป็น pending รอ webhook แล้วเมื่อ webhook มาถึงให้ **เรียก Inquiry QR Transaction API ซ้ำเพื่ออ่านสถานะจริงก่อน fulfill** อย่าเชื่อ callback อย่างเดียว แนวนี้ตรงกับ reference ของ Omise ที่ charge เริ่มที่ pending แล้ว provider แจ้งกลับก่อน merchant จะ GET charge ซ้ำและเทียบ status ว่า successful failed หรือ expired ([Omise PromptPay](https://www.omise.co/promptpay)) และตรงกับคำแนะนำว่า dynamic QR ได้ real-time webhook ส่วน static QR ต้องตรวจ manual หรือผ่าน slip API ([seaindev Thai QR guide](https://seaindev.com/p/thailand-qr-code-payment-integration)) งานยกเลิกเป็น state machine ไม่ใช่ปุ่มเดียว KBank แยก **Cancel QR Transaction API ใช้ได้เฉพาะสถานะ Requested** ([Cancel QR Transaction API](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/Cancel%20QR%C2%A0Transaction%20API)) กับ **Void Transaction API ใช้ได้เฉพาะสถานะ Authorized ที่ยังไม่ settle** ([Void Transaction API](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/Void%20Transaction%20API)) ส่วน error ด้าน auth ที่เห็นคือ **Token was expired or cannot be found กับ Failed Authentication** ([KPG Others errors](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/Others)) เรื่องเงินคืนคือกับดักใหญ่ **PromptPay QR ผ่าน gateway ส่วนใหญ่ void หรือ refund ผ่านระบบไม่ได้** ตามตาราง refund ของ PortOne ที่ช่อง PromptPay กากบาททั้ง void partial และ multiple refunds ขณะที่บัตรทำได้ ([PortOne K-Bank](https://docs.portone.cloud/docs/k-bank)) Omise พูดตรงว่า **PromptPay charges cannot be voided or refunded through Omise** ([Omise PromptPay](https://www.omise.co/promptpay)) ส่วน Refund Transaction API ของ KBank อธิบายเป็นการคืนเงินเข้าบัญชีผู้ถือบัตรหลัง settlement จึงเป็นสายบัตร ไม่ใช่โอน PromptPay กลับ ([Refund Transaction API](https://apiportal.kasikornbank.com/product/content/All/K%20PAYMENT%20GATEWAY/API%20Reference/Refund%20Transaction%20API)) ข้อยกเว้นคือ Stripe ที่ refund ได้แต่ต้อง email ขอเลขบัญชีคืนเงินจากลูกค้าก่อน ([Stripe PromptPay](https://docs.stripe.com/payments/promptpay)) งานกระทบยอดจึงต้อง join สามขาเอา **referenceOrder เป็น primary key เทียบ Create/Inquiry response กับ ## Backend ต้องผ่าน mTLS บวก OAuth และทำ QR ให้ใช้ครั้งเดียว

ตระกูล Open API ของ KBank ใช้ **OAuth2 client credentials บวก Two-Way SSL (mTLS) พร้อมกัน** ไม่ใช่ API key เดี่ยว โดยขอ token ด้วยการเอา Consumer ID กับ Consumer Secret มาต่อด้วย colon ทำ Base64 ใส่ header Authorization แบบ Basic พร้อม Content-Type เป็น application/x-www-form-urlencoded และ body grant_type เท่ากับ client_credentials ([KBTG Life EP.2](https://medium.com/kbtg-life/%E0%B8%95%E0%B9%88%E0%B8%AD-api-%E0%B8%81%E0%B8%B1%E0%B8%9A-kbank-%E0%B8%A1%E0%B8%B2%E0%B8%95%E0%B9%88%E0%B8%AD%E0%B8%81%E0%B8%B1%E0%B8%99%E0%B8%81%E0%B8%B1%E0%B8%9A-ep-2-%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99%E0%B8%9C%E0%B9%88%E0%B8%AD%E0%B8%9C%E0%B9%88%E0%B8%B2%E0%B8%99-oauth-2-0-b8c01ea9f5bc)) ตัวอย่าง cURL ต้องแนบ client cert กับ key ไปด้วยพร้อมกัน เช่น curl ด้วย flag cert กับ key ยิงไป **https://openapi-sandbox.kasikornbank.com/oauth/token** ([KBTG Life EP.2](https://medium.com/kbtg-life/%E0%B8%95%E0%B9%88%E0%B8%AD-api-%E0%B8%81%E0%B8%B1%E0%B8%9A-kbank-%E0%B8%A1%E0%B8%B2%E0%B8%95%E0%B9%88%E0%B8%AD%E0%B8%81%E0%B8%B1%E0%B8%9A-ep-2-%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99%E0%B8%9C%E0%B9%88%E0%B8%B2%E0%B8%99-oauth-2-0-b8c01ea9f5bc)) แล้วเอา access token ไปใส่ **Authorization Bearer ทุก API call** ([KBTG Life EP.2](https://medium.com/kbtg-life/%E0%B8%95%E0%B9%88%E0%B8%AD-api-%E0%B8%81%E0%B8%B1%E0%B8%9A-kbank-%E0%B8%A1%E0%B8%B2%E0%B8%95%E0%B9%88%E0%B8%AD%E0%B8%81%E0%B8%B1%E0%B8%9A-ep-2-%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99%E0%B8%9C%E0%B9%88%E0%B8%B2%E0%B8%99-oauth-2-0-b8c01ea9f5bc)) โดย response มี **expires_in เป็นวินาที ตัวอย่างอายุราว 30 นาที และธนาคารขอให้ reuse จนหมดอายุก่อนขอใหม่** ([KBTG Life EP.2](https://medium.com/kbtg-life/%E0%B8%95%E0%B9%88%E0%B8%AD-api-%E0%B8%81%E0%B8%B1%E0%B8%9A-kbank-%E0%B8%A1%E0%B8%B2%E0%B8%95%E0%B9%88%E0%B8%AD%E0%B8%81%E0%B8%B1%E0%B8%9A-ep-2-%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99%E0%B8%9C%E0%B9%88%E0%B8%AD%E0%B8%9C%E0%B9%88%E0%B8%B2%E0%B8%99-oauth-2-0-b8c01ea9f5bc)) พื้นฐาน mTLS ด้วย X.509 client cert อธิบายไว้ใน EP.1 ([KBTG Katalyst](https://katalyst.kasikornbank.com/th/blog/Pages/api-with-kbank.html)) และพอร์ทัลย้ำว่าต้องรับ OAuth2 credentials จาก Developer Portal ก่อน ([QR Payment auth](https://apiportal.kasikornbank.com/product/public/LandingPage/QR%20Payment/Documentation/%E0%B8%81%E0%B8%B2%E0%B8%A3%E0%B8%A2%E0%B8%B7%E0%B8%99%E0%B8%A2%E0%B8%B1%E0%B8%99%E0%B8%95%E0%B8%B1%E0%B8%A7%E0%B8%95%E0%B8%99)) ส่วนตระกูล K-Payment Gateway ใช้คนละโมเดลคือ **API key บวก MID/TID กับ JS SDK** ตามตัวอย่างฝัง data-apikey ใน kpayment.min.js ([bilions-org/kbank-sdk](https://github.com/bilions-org/kbank-sdk)) อย่าสับสนสองตระกูลนี้ สำหรับ checklist ระดับ implement ให้ยึดตารางข้างล่างเป็นขั้นต่ำ เริ่มจากเก็บ **consumer secret กับ .key ใน secrets manager ห้าม commit** ต่อ mTLS ทุก call พร้อม verify server cert ทำ **token cache แบบ in-memory หรือ Redis พร้อมเผื่อ clock-skew** ฝั่ง webhook ให้ **verify signature หรือ partnerSecret ตอบ 200 เร็วแล้วค่อยประมวลผล async และใช้ partnerTxnUid หรือ reference เป็น idempotency key** ทุกครั้งที่ webhook บอกว่าจ่ายแล้วให้ **inquiry ซ้ำก่อน fulfill** ตามแนว Omise ([Omise PromptPay](https://www.omise.co/promptpay)) ออก **QR ต่อ order ครั้งเดียว มี expiry ห้าม reuse** เพราะ Stripe เตือนว่า **สแกน QR ซ้ำอาจโดนตัดเงินซ้ำและเงินเกินต้องคืนนอกระบบเอง** ([Stripe PromptPay](https://docs.stripe.com/payments/promptpay)) บังคับ **HTTPS เท่านั้นพร้อม HSTS** ใส่ IP allowlist ถ้า KBank ให้มา และทำ **audit log พร้อม alert ยอดไม่ตรง** ข่าวดีคือ **QR-only ไม่แตะเลขบัตรจึงไม่อยู่ใน scope PCI DSS เต็มรูปแบบ** แต่ยังต้องดูแล PDPA และหลักธนาคารกลาง ส่วน pitfall ที่เจอซ้ำคือสับสน KPG กับ Open API ลืมติด cert บน server จริงทั้งที่ Postman ผ่าน ส่ง body ขอ token เป็น JSON แทนที่จะเป็น **x-www-form-urlencoded** ขอ token ใหม่ทุก request จนโดน throttle เชื่อ webhook อย่างเดียว reuse QR หลาย order และลืม handle สถานะ expired failed แบบที่ Omise นิยาม failure codes ไว้ทั้ง failed_processing insufficient_balance และ payment_cancelled ([Omise PromptPay](https://www.omise.co/promptpay)) โค้ดตัวอย่างทางการไม่พบ แต่ community มีโครงให้ลอกสามชิ้นคือ PHP KPG ที่ตั้ง paymentType amount currency referenceOrder แล้วเรียก getQRPaymentOrderId กับ getCharge ([bilions-org/kbank-sdk](https://github.com/bilions-org/kbank-sdk)) PHP Open API ที่ใช้ ClientBuilder setConsumer แบบ sandbox แล้วสร้าง RequestThaiQRCode ใส่ merchant partner amount ([GitBook](https://farzai.gitbook.io/kbank-kapi-php)) ซึ่งยัง **WIP เหลือ OAuth2 test suite webhook callback และ two-way SSL** จึงใช้เป็น checklist field ได้แต่อย่าก็อป auth ไปใช้ดิบ ส่วน static QR พร้อมคำเตือนว่า bank API ตรงมี upfront สูง ([codustry/thanakan](https://github.com/codustry/thanakan))

| ขั้น implement backend | สิ่งที่ต้องทำ | กับดักที่พบบ่อย |
|---|---|---|
| เก็บ secret | consumer secret + .crt/.key ใน secrets manager ห้าม commit | commit cert หลุดขึ้น repo |
| ต่อ mTLS + OAuth | client cert ทุก call + Basic ขอ token + Bearer เรียก API + cache token | ลืม cert บน prod ส่ง body ผิด format ขอ token ทุก request |
| สร้าง QR | referenceOrder เป็น UUID ต่อ checkout ครั้งเดียว amount + THB | reuse referenceOrder ทำให้ duplicate order |
| แสดง QR | คืน QR payload/image หรือ orderId ให้ frontend render มี countdown | ไม่มี expiry ทำให้ QR ค้างจ่ายช้าแล้วงง |
| รับ webhook | ลงทะเบียน URL ล่วงหน้า ตอบ 200 เร็ว ทำ idempotent | เชื่อ webhook อย่างเดียว ไม่ inquiry ซ้ำ |
| ยืนยันยอด | เรียก Inquiry QR Transaction ก่อน fulfill | ไม่อ่าน status ก่อน Cancel/Void ทำให้เรียกผิด state |
| กวาด pending | poller กวาด pending เกิน TTL ด้วย Inquiry แล้ว Cancel | ปล่อย Requested ค้างไม่ cleanup |
| กระทบยอด | join referenceOrder สามขา webhook inquiry settlement | webhook paid แต่ settlement ไม่มาแล้วไม่ alert |

## Conclusion

ความเข้าใจที่เปลี่ยนไปหลังรวมโน้ตคือ KBank QR ไม่ใช่ API เดียวแต่เป็นสองโลกคู่กันคือ Open API สาย server-to-server ที่ใช้ OAuth2 บวก mTLS กับ K Payment Gateway สาย checkout ที่ใช้ Order API บวก hosted UI และทั้งสองโลกซ่อนรายละเอียดสำคัญไว้หลัง login ทำให้รายงานนี้ยืนยันได้แค่ประตูทางเข้า flow ระดับ concept และ checklist ที่ยืมความเข้มจาก aggregator ส่วน schema จริง webhook signing key และไฟล์ settlement ต้องเก็บจาก sandbox capture หลังอนุมัติ merchant เท่านั้น นัยสำหรับทีมคืออย่ารอ KBank เพื่อเดโม ให้ขึ้น prototype บน Omise หรือ Stripe ก่อนเพื่อล็อก UX กับ state machine แบบ pending webhook inquiry cancel void ให้เสร็จ แล้วค่อยสลับ adapter มา KBank ตรงโดยไม่เปลี่ยน core logic
