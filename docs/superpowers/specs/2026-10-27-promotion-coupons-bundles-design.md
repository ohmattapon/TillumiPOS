# คูปอง ซื้อแถม จำกัดจำนวนครั้ง และรายงานโปรโมชัน

ต่อยอดจาก [แบบโปรโมชันเดิม](2026-10-15-promotions-design.md) ที่ตัด 4 เรื่องนี้ออกไว้ งานนี้เพิ่มทั้ง 4 เรื่องบน branch `ohmattpon/promotion-coupons-bundles` โดยไม่เปลี่ยนหลักเดิม:

- ส่วนลดจากโปรโมชันกับส่วนลดที่พิมพ์เองไม่ซ้อนกัน
- ระบบเลือกโปรที่ลดมากที่สุด
- ราคาถูกตรึงด้วย quote ก่อนชำระ
- ห้ามแก้สูตร `calculateTotals`

## เป้าหมาย

- **คูปอง:** ลูกค้าบอกรหัส เช่น `SUMMER10` แคชเชียร์พิมพ์ในตะกร้า แล้วได้ส่วนลดของโปรนั้น
- **ซื้อแถม:** "ซื้อ 2 แถม 1" ในสินค้าหรือหมวดที่เลือก โดยตัวที่แถมคือตัวที่ถูกที่สุด
- **จำกัดจำนวนครั้ง:** จำกัดรวมทั้งร้าน และจำกัดต่อสมาชิก
- **รายงานแยกตามโปรโมชัน:** ในช่วงวันที่เลือก แต่ละโปรใช้กี่บิล ลดไปเท่าไร และยอดขายเท่าไร พร้อมส่งออก Excel

## ไม่ทำ

- คูปองรหัสเฉพาะใช้ได้ครั้งเดียว (สร้างทีละหลายรหัส) แต่ละโปรมีรหัสเดียวที่ใช้ร่วมกัน
- ใช้หลายโปรพร้อมกันในบิลเดียว (ยังเลือกโปรเดียวที่ลดมากสุด)
- แถมสินค้าคนละตัวกับที่ซื้อ เช่น ซื้อกาแฟแถมขนม (แถมเฉพาะภายในขอบเขตเดียวกัน)
- ซื้อแถมที่นับสินค้าแบบแพ็ค บรรทัดแพ็คไม่นับในโปรซื้อแถม
- โปรโมชันต่อสาขา และการส่งโปรไปจอลูกค้า

## ห้ามเกิด

- บิลที่ชำระด้วย QR แล้วออกบิลไม่ได้ เพราะโปรเต็มสิทธิ์ระหว่างรอเงิน
- ยอดบนจอไม่ตรงกับใบเสร็จ สูตรประเมินโปรต้องอยู่ที่ `domains/promotion.domain.ts` ที่เดียว และเว็บใช้สูตรเดียวกันผ่าน `@pos/api/promotions`
- นับครั้งที่ใช้เกินขีดจำกัด เมื่อมีสองเครื่องขายพร้อมกัน

## โมเดลข้อมูล (migration เพิ่มอย่างเดียว)

ตาราง `promotions` เพิ่มคอลัมน์ทั้งหมดเป็น nullable ยกเว้นที่มีค่าเริ่มต้น:

| คอลัมน์ | ความหมาย |
|---|---|
| `coupon_code text` | null = โปรอัตโนมัติแบบเดิม ถ้ามีค่า = ต้องพิมพ์รหัสนี้ เก็บเป็นตัวพิมพ์ใหญ่ ตัดช่องว่าง 3–20 ตัว `[A-Z0-9-]` และ unique index บน `upper(coupon_code)` |
| `buy_quantity integer`, `free_quantity integer` | ใช้กับ `kind = 'bundle'` เท่านั้น ค่า 1–99 |
| `max_uses integer` | null = ไม่จำกัด ถ้ามีค่าต้อง ≥ 1 |
| `max_uses_per_member integer` | null = ไม่จำกัด ถ้ามีค่า โปรต้องเป็น `audience = 'members'` |

- **ชนิดใหม่:** enum `promotion_kind` เพิ่มค่า `bundle`
- **check constraint:** `promotions_value_positive` เปลี่ยนเป็น `kind = 'bundle' OR value > 0` และเพิ่ม check ว่า bundle ต้องมี `buy_quantity` และ `free_quantity`
  - การเปลี่ยนนี้เป็นการผ่อนกฎ ข้อมูลเดิมผ่านทุกแถว
- **`value` ของ bundle:** เก็บ 0 ไม่ได้ใช้คำนวณ
- **ขอบเขต:** bundle ต้องมี scope (สินค้าหรือหมวด) ห้ามเป็นทั้งบิล เพราะต้องรู้ว่าแถมตัวไหน
- **บิลที่มีโปรอยู่แล้ว:** `sales.promotion` (snapshot) ใช้ type เดิม `SalePromotion` เพิ่มฟิลด์ optional `couponCode`, `buyQuantity`, `freeQuantity` บิลเก่าไม่ต้อง backfill

## สูตร (ที่เดียว: `domains/promotion.domain.ts`)

**ข้อมูลบรรทัดสำหรับประเมินโปร:** `PromotionLine` เพิ่ม `unitPriceSatang`, `quantity` และ `isPack` ทั้ง server และเว็บต้องส่งค่าครบ

**คูปอง:** `PromotionContext` เพิ่ม `couponCode: string | null` (เทียบแบบตัวพิมพ์ใหญ่ ตัดช่องว่างแล้ว)
- โปรที่มี `couponCode` จะ eligible ก็ต่อเมื่อรหัสตรงกัน และผ่านกฎเดิมทุกข้อ (วันเวลา ยอดขั้นต่ำ สมาชิก)
- โปรอัตโนมัติยังแข่งตามปกติ
- **ผลที่ตั้งใจ:** ถ้าโปรอัตโนมัติลดมากกว่าคูปอง ลูกค้าได้โปรอัตโนมัติ

**ซื้อแถม (`bundle`):**
1. เอาบรรทัดในขอบเขตที่ `isPack = false` มาแตกเป็นหน่วยละ `unitPriceSatang`
2. เรียงจากแพงไปถูก จับกลุ่มทีละ `buy + free` หน่วยตามลำดับ
3. ในแต่ละกลุ่มที่ครบ หน่วยที่ถูกที่สุด `free` หน่วยท้ายกลุ่มเป็นส่วนลด
4. ส่วนลดรวมถูกจำกัดด้วย `maxDiscountSatang` (ถ้ามี) และยอดในขอบเขต
5. ไม่ครบกลุ่มแรก = ไม่ eligible

ตัวอย่าง: ซื้อ 2 แถม 1 มีชา 55, 50, 50, 45, 40
- เรียงแล้วจับกลุ่มเป็น [55, 50, 50] และ [45, 40] ซึ่งกลุ่มที่สองไม่ครบ
- ได้ส่วนลด 50 บาท

**การแตกหน่วย:** จำนวนหน่วยต่อบิลจำกัดไม่เกิน 9999 × 100 บรรทัด แต่สูตรต้องไม่สร้าง array ทีละหน่วย ให้นับแบบเป็นช่วงต่อบรรทัด (builder เลือกวิธีได้ เทสต์ต้องครอบกรณี 9999 ชิ้น)

**การเลือกโปร:** `pickBestPromotion` ใช้กติกาเดิม ลดมากสุดชนะ ถ้าเท่ากันใช้ id ต่ำสุด แต่ตัดโปรที่ "ใช้ครบสิทธิ์แล้ว" ออกก่อน โดยผู้เรียกส่งชุดโปรที่ยังเหลือสิทธิ์เข้ามา สูตรไม่อ่านฐานข้อมูล

## จำกัดจำนวนครั้ง

**การนับ "ครั้งที่ใช้"** ของโปร P นับสองแบบรวมกัน:
- บิล `completed` ที่ `promotion_id = P`
- quote ที่สถานะ `reserved` (รอ QR) และ promotion = P

บิลที่ void แล้วคืนสิทธิ์ (ไม่นับ) ส่วนการนับต่อสมาชิกนับแบบเดียวกันแต่กรองด้วย `member_id`

**การอ่านค่า:** อ่านผ่าน port ใหม่ที่ผู้ใช้เป็นเจ้าของ คือ `IPromotionUsage` ใน `quotes/applications/ports` และ `sales/applications/ports` โดยโมดูล `promotions` เป็นผู้ implement และ bind
- `countUses(promotionId, memberId | null)` → `{ total, byMember }`
- `lockForUse(promotionId)` ล็อกแถว `promotions` (`FOR UPDATE`)

**จุดที่ตรวจ:**

| เวลา | ตรวจ | ถ้าเต็ม |
|---|---|---|
| สร้าง quote | ตัดโปรที่เต็มออกจากผู้สมัคร (ไม่ล็อก) | ได้โปรอื่นหรือไม่มีโปร |
| reserve quote ให้ QR | ล็อกโปรแล้วนับใหม่ | `PROMOTION_LIMIT_REACHED` (409) แล้วเว็บขอราคาใหม่ |
| checkout ด้วย quote ที่ยัง `open` (เงินสด/บัตร) | ล็อกโปรแล้วนับใหม่ | `PROMOTION_LIMIT_REACHED` (409) แล้วเว็บขอราคาใหม่ |
| checkout ด้วย quote ที่ `reserved` (เงิน QR มาแล้ว) | ไม่ตรวจ | สิทธิ์ถูกนับไปตั้งแต่ตอน reserve แล้ว เงินที่จ่ายแล้วได้บิลเสมอ |

**ลำดับการล็อกใหม่:** order → QR → quote → **promotion** → member → product ต้องแก้ข้อความใน AGENTS.md ด้วย

**error code ใหม่:** `PROMOTION_LIMIT_REACHED`, `COUPON_NOT_FOUND` (404), `COUPON_NOT_APPLICABLE` (400) ต้องเพิ่มคำแปลใน `src/locales/errors.ts` ทุกตัว

## API (v1 เพิ่มอย่างเดียว)

- **สร้าง/แก้โปร:** `POST/PATCH /promotions` รับฟิลด์ใหม่ทั้งหมดแบบ optional และ response คืนฟิลด์ใหม่
- **ขอ quote:** `POST /quotes` รับ `couponCode` แบบ optional
  - รหัสที่ไม่ตรงโปรใดเลย → `COUPON_NOT_FOUND`
  - ตรงโปรแต่ไม่ eligible (นอกเวลา ยอดไม่ถึง ไม่มีสมาชิก หรือเต็มสิทธิ์) → `COUPON_NOT_APPLICABLE` พร้อม `params.reason`
  - quote เก็บ `couponCode` ไว้ และถูกนับเป็นส่วนหนึ่งของสิ่งที่ตรึง
- **รายงาน:** `GET /sales/reports/promotions?from&to&limit&offset` (สิทธิ์ `reports.read`)
  - ตอบ `{ items, total }` แต่ละแถวมี `promotionId`, `name` (ชื่อจาก snapshot ล่าสุดในช่วง), `bills`, `discountSatang`, `netSalesSatang`
  - ไม่นับบิล void และใช้นิยามวันกับเขตเวลาเดียวกับ [รายงานยอดขาย](../../sales-reports.md)
  - เรียงตาม `discountSatang` มากไปน้อย ถ้าเท่ากันเรียงตาม id
- **Excel:** ไฟล์ส่งออกรายงานยอดขายเพิ่ม sheet "โปรโมชัน"
- **OpenAPI:** baseline ต้องบันทึกใหม่ (เปลี่ยนแบบเพิ่มอย่างเดียว) และแจ้งเจ้าของก่อน

## หน้าเว็บ

- **ฟอร์มโปร:**
  - ช่อง "รหัสคูปอง" (ว่าง = อัตโนมัติ)
  - ตัวเลือกชนิด "ซื้อแถม" พร้อมช่อง ซื้อ/แถม (ซ่อนช่องมูลค่าเมื่อเลือกซื้อแถม และบังคับเลือกสินค้าหรือหมวด)
  - ช่องจำกัดครั้งรวมและต่อสมาชิก
  - หน้ารายการโปรแสดงจำนวนครั้งที่ใช้แล้ว/ขีดจำกัด
- **ตะกร้า:** ปุ่ม "ใส่คูปอง" เปิดช่องพิมพ์รหัส
  - เก็บรหัสใน zustand (เป็นสิ่งที่ผู้ใช้พิมพ์) และล้างพร้อมตะกร้า
  - ตะกร้าแสดงชื่อโปรคูปองเมื่อใช้ได้ หรือแสดงเหตุผลเมื่อใช้ไม่ได้ (จาก error code)
  - ออเดอร์ค้างใช้คูปองได้ตอนชำระ โดยส่งรหัสไปกับ quote ของออเดอร์ ไม่เก็บรหัสในออเดอร์
- **ตัวอย่างโปรในตะกร้า:** ตะกร้ายังเดาโปรด้วยสูตรเดียวกันเหมือนเดิม แต่เว็บไม่รู้จำนวนครั้งที่ใช้ไปแล้ว ดังนั้นตัวอย่างในตะกร้าเป็นแค่คำแนะนำ ยอดจริงคือ quote ที่หน้าชำระเงินแสดง และ list โปรสำหรับแคชเชียร์ควรตัดโปรที่เต็มสิทธิ์ออกให้ (ส่ง `isExhausted` มาใน response)
- **หน้ารายงาน:** แท็บ "โปรโมชัน" ใช้ `DataTable` (กำหนด priority ทุกคอลัมน์) และต้องใช้ได้ที่ 390/768/1366px

## เทสต์ที่ต้องมี

- **เทสต์ของสูตร:**
  - ซื้อแถมกลุ่มครบ/ไม่ครบ ราคาผสม บรรทัดแพ็คไม่นับ เพดานส่วนลด 9999 ชิ้น
  - คูปองตรง/ไม่ตรง/ตัวพิมพ์เล็ก
  - คูปองแพ้โปรอัตโนมัติที่ลดมากกว่า
- **use case:** เต็มสิทธิ์ตอนสร้าง quote (ตัดออก), ตอน checkout เงินสด (409), ตอน reserve QR (409), quote reserved ผ่านแม้เต็ม, บิล void คืนสิทธิ์, จำกัดต่อสมาชิก
- **integration:** สองคำขอพร้อมกันกับโปรที่เหลือสิทธิ์ 1 ครั้ง ได้บิลโปรเดียว (อีกคำขอได้ 409) และรายงานโปรตรงกับผลรวมของบิล

## ปล่อยให้ builder ตัดสิน

- วิธีนับหน่วยของซื้อแถมโดยไม่แตก array
- ชื่อไฟล์ port และ adapter ตามรูปแบบใน AGENTS.md
- การวางช่องคูปองบนจอมือถือ (ต้องสูงอย่างน้อย 44px ตาม DESIGN.md)

## ข้อที่ผมตัดสินใจเอง (เจ้าของโครงการอนุมัติแล้ว 2026-10-27)

- บิล void คืนสิทธิ์ของโปร
- คูปองเป็นรหัสร่วมต่อโปร ไม่ใช่รหัสใช้ครั้งเดียว
- แถมตัวที่ถูกที่สุด และไม่นับแพ็ค
- quote ที่รอ QR นับเป็นการใช้สิทธิ์แล้ว
