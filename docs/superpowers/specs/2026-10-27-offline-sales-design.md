# ขายได้ตอนเน็ตหลุด แล้วซิงก์ทีหลัง

ตอนนี้หน้าขายต้องคุยกับเซิร์ฟเวอร์ทุกครั้ง เน็ตหลุดเมื่อไรก็ขายไม่ได้ทันที งานนี้ทำให้เครื่องขายยังรับเงินสดได้ตอนเชื่อมต่อเซิร์ฟเวอร์ไม่ได้ แล้วส่งบิลขึ้นเซิร์ฟเวอร์เองเมื่อกลับมาเชื่อมต่อได้ อยู่บน branch `ohmattpon/offline-sales`

งานนี้ขัดกับหลัก "เซิร์ฟเวอร์เป็นผู้ตัดสิน ไม่เชื่อยอดจากเครื่องลูก" โดยตรง เพราะเงินรับไปแล้วตอนออฟไลน์ เอกสารนี้จึงกำหนดว่าเซิร์ฟเวอร์ยอมรับอะไร ตรวจอะไร และส่งอะไรให้คนตรวจต่อ

## เป้าหมาย

- **ขายต่อได้:** เมื่อเชื่อมต่อเซิร์ฟเวอร์ไม่ได้ หน้าขายยังขายแบบขั้นตอนเดียวได้ (สแกน/เลือกสินค้า ตัวเลือก แพ็ค โปรอัตโนมัติ ส่วนลดที่พิมพ์) และรับเงินสด บัตร (แค่บันทึก) หรือพร้อมเพย์แบบกำหนดผู้รับ (แคชเชียร์ตรวจเงินเข้าเอง)
- **พิมพ์ใบได้:** พิมพ์ "ใบรับเงินชั่วคราว" ได้ทันที
- **ซิงก์เอง:** บิลที่ขายออฟไลน์ถูกส่งขึ้นเซิร์ฟเวอร์เองเมื่อกลับมาออนไลน์ ตามลำดับที่ขาย ส่งซ้ำได้โดยไม่เกิดบิลซ้ำ
- **มีคนตรวจ:** เจ้าของเห็นรายการบิลออฟไลน์ที่ต้องตรวจ (ราคาไม่ตรง สต็อกติดลบ ซิงก์ไม่ผ่าน)

## ไม่ทำ (ใช้ได้เฉพาะตอนออนไลน์)

- QR ของ SCB (ต้องถามธนาคาร)
- ออเดอร์ค้าง โต๊ะ รวม/แยกบิล
- void บิล
- คูปองและโปรที่จำกัดจำนวนครั้ง เพราะต้องนับที่เซิร์ฟเวอร์ (ดู [แบบคูปอง](2026-10-27-promotion-coupons-bundles-design.md))
- แลกแต้มสมาชิก
- สร้างสมาชิกใหม่
- เปิด/ปิด/นับกะ
- สลับพนักงานด้วย PIN และเข้าสู่ระบบใหม่
- รับสินค้าเข้า
- แก้ข้อมูลสินค้า
- จอลูกค้าผ่านเซิร์ฟเวอร์ (BroadcastChannel ในเบราว์เซอร์เดียวกันยังทำงาน)
- เครื่องพิมพ์ ESC/POS ผ่าน LAN ที่ต้องผ่านเซิร์ฟเวอร์
- ขายออฟไลน์ข้ามหลายวันโดยไม่จำกัด (ดูขีดจำกัดด้านล่าง)

## ห้ามเกิด

- **บิลซ้ำ:** ส่งบิลออฟไลน์ซ้ำแล้วได้บิลเพิ่ม
- **บิลหาย:** ปิดแท็บหรือเบราว์เซอร์ระหว่างออฟไลน์แล้วบิลที่ยังไม่ซิงก์หายไป
- **รายงานปิดกะถูกแก้ย้อนหลัง:** บิลออฟไลน์ที่มาถึงหลังปิดกะต้องไม่เปลี่ยนรายงานเดิม ให้แสดงแยกเหมือน void หลังปิดกะ
- **ปลอมบิลได้ง่ายกว่าการขายปกติ:** ต้องเป็นผู้ใช้ที่ล็อกอินอยู่ และทุกบิลมี audit
- **ใช้เลขใบเสร็จจริงซ้ำหรือข้ามเลข:** เลขใบเสร็จจริงยังออกจากเซิร์ฟเวอร์ที่เดียว

## ภาพรวม

| ส่วน | ที่อยู่ | หน้าที่ |
|---|---|---|
| service worker | เว็บ (`vite-plugin-pwa`, Workbox) | cache ไฟล์ของแอปให้เปิดหน้าขายได้ตอนออฟไลน์ (รวมถึงตอน reload) |
| ภาพสินค้าในเครื่อง | IndexedDB (`idb`) | สำเนาสินค้า แพ็ค ตัวเลือก โปรอัตโนมัติ การตั้งค่าร้าน ผู้ใช้ที่ล็อกอิน และกะที่เปิดอยู่ |
| outbox | IndexedDB | บิลออฟไลน์ที่ยังไม่ซิงก์ แต่ละใบมี key (UUID) |
| ตัวซิงก์ | เว็บ `features/offline/lib/sync.ts` | ส่ง outbox ทีละใบตามลำดับ ใช้ key เดิมทุกครั้งที่ลองใหม่ |
| API ใหม่ | `POST /api/v2/offline-sales` | รับบิลออฟไลน์แบบ idempotent |
| หน้าตรวจ | เว็บ `features/offline` + `GET /api/v2/offline-sales/review` | รายการที่ต้องตรวจ |

**dependency ใหม่ที่ผมเลือก:** `vite-plugin-pwa` (สร้าง service worker) และ `idb` (ห่อ IndexedDB ขนาดเล็ก) ถ้าเจ้าของไม่ต้องการ dependency ใหม่ ให้เขียนเองได้ แต่ใช้เวลามากกว่า

## ภาพสินค้าในเครื่อง (snapshot)

- **เวลาดึง:** ดาวน์โหลดเมื่อเปิดหน้าขาย เมื่อเปิดกะ และทุก 10 นาทีที่ออนไลน์
  - ใช้ `GET /api/v2/offline/snapshot` (query) ตอบสินค้าที่เปิดขายทั้งหมดพร้อมแพ็ค ราคา ต้นทุนไม่ต้องส่ง ตัวเลือกที่เปิดอยู่ โปรอัตโนมัติที่เปิดอยู่และไม่จำกัดจำนวนครั้ง การตั้งค่า VAT/เขตเวลา/หัวใบเสร็จ และ `version`
  - route นี้เป็นข้อยกเว้นของกฎ "list ต้องเป็น `{ items, total }`" เพราะเป็นเอกสารชุดเดียว ไม่ใช่ list ต้องเขียนเหตุผลไว้ใน comment
- **ขีดจำกัด:** สินค้าเกิน 5,000 รายการ → ไม่เปิดโหมดออฟไลน์ และแสดงเหตุผลในหน้าตั้งค่า
- **อายุ:** snapshot อายุเกิน 24 ชั่วโมง → ไม่ขายออฟไลน์ต่อ เพราะราคาเก่าเกินไป

## เมื่อไรถือว่าออฟไลน์

- **เงื่อนไข:** คำขอไปเซิร์ฟเวอร์ล้มด้วย network error หรือ timeout 8 วินาที 2 ครั้งติด หรือ `navigator.onLine === false`
  - error ที่เซิร์ฟเวอร์ตอบกลับ (4xx/5xx) ไม่นับเป็นออฟไลน์
- **ตอนออฟไลน์:** แสดงแถบสีเตือน "ออฟไลน์ — ขายได้เฉพาะเงินสด บัตร พร้อมเพย์แบบกำหนดผู้รับ" และนับจำนวนบิลรอซิงก์
- **กลับมาออนไลน์:** ping `GET /api/v1/health` (ต้องมีหรือเพิ่ม) ทุก 15 วินาทีระหว่างออฟไลน์ ตอบได้แล้วจึงเริ่มซิงก์

## ขายตอนออฟไลน์

**การคำนวณบนเครื่อง:** ใช้สูตรเดียวกับเซิร์ฟเวอร์ทั้งหมด
- `calculateTotals`, `resolveLineOptions`, `packUnitPriceSatang`, `evaluatePromotion` / `pickBestPromotion`
- ห้ามมีสูตรที่สองในเว็บ

**ข้อมูลที่บันทึกลง outbox:**
- `key` (UUID จาก `newIdempotencyKey`), `registerId`, `shiftId` (กะที่เปิดอยู่ตอนเริ่มออฟไลน์ หรือ null ในโหมด legacy), `cashierId`
- `soldAt` (นาฬิกาเครื่อง), `offlineNo`
- รายการ (`productId`, `optionIds`, `packId`, `quantity`, `unitPriceSatang` ที่ขายจริง), โปรที่ใช้ (`promotionId`, `discountSatang`), ส่วนลดที่พิมพ์
- การชำระ, ยอดทุกตัวที่คำนวณได้ และ `snapshotVersion`

**การบันทึกต้องเสร็จก่อนพิมพ์:**
- เขียนลง IndexedDB ใน transaction เดียว
- ถ้าเขียนไม่สำเร็จ → ไม่นับว่าขายแล้ว และแจ้งแคชเชียร์

**เลขชั่วคราว `offlineNo`:**
- รูปแบบ `OFF-<registerCode>-<เลขต่อเนื่องของเครื่อง 6 หลัก>`
- เลขต่อเนื่องเก็บใน IndexedDB
- ใบที่พิมพ์มีหัวว่า "ใบรับเงินชั่วคราว" ไม่ใช่ใบกำกับภาษีอย่างย่อ และบอกว่าขอรับใบเสร็จจริงได้หลังระบบออนไลน์
- เหตุผล: เลขใบกำกับภาษีต้องต่อเนื่องและออกจากที่เดียว

**ขีดจำกัด:**
- outbox มีได้ไม่เกิน 500 บิล
- บิลแรกที่ยังไม่ซิงก์อายุเกิน 24 ชั่วโมง → ห้ามขายออฟไลน์เพิ่ม

**กะ:**
- เครื่องที่ outbox ยังไม่ว่างห้ามเริ่มนับเงินปิดกะ (ตรวจที่เว็บ)
- เซิร์ฟเวอร์รับบิลที่มาช้าตามกฎด้านล่าง

**outbox กับการออกจากระบบ:**
- outbox ไม่ใช่ข้อมูลของผู้ใช้คนเดียว แต่เป็นของเครื่อง จึงต้องไม่ถูกล้างตอนออกจากระบบ (ต่างจากตะกร้า)
- ถ้า outbox ยังไม่ว่าง ปุ่มออกจากระบบต้องเตือนว่ามีบิลรอซิงก์กี่ใบ
- ผู้ใช้คนถัดไปที่ล็อกอินบนเครื่องนั้นเป็นคนซิงก์ต่อ (`syncedById`) และ `cashierId` ยังเป็นคนที่ขายจริง

**session หมดอายุตอนซิงก์:**
- ถ้าซิงก์แล้วได้ 401 ให้หยุดซิงก์และเก็บ outbox ไว้ครบ
- แสดงหน้าเข้าสู่ระบบ เมื่อเข้าแล้วซิงก์ต่อ
- 401 ไม่ใช่การปฏิเสธบิล

## ซิงก์ (`POST /api/v2/offline-sales`, `auth: true`, header `Idempotency-Key` = key ของบิล)

**ใช้ทางเดียวกับการขายปกติ:** เซิร์ฟเวอร์สร้างบิลผ่าน `ISaleCheckout` ตามกฎที่ว่าทุกบิลต้องผ่านที่เดียว โดยเพิ่มโหมด "บันทึกการขายที่เกิดขึ้นแล้ว" (`recorded`) ซึ่งต่างจากการขายปกติ:

| เรื่อง | ขายปกติ | `recorded` (ออฟไลน์) |
|---|---|---|
| ราคาต่อหน่วย | จากสินค้าตอนนี้ / quote | จากที่เครื่องขายจริง ตรวจเทียบกับราคาปัจจุบันแล้วทำเครื่องหมาย `priceMismatch` ถ้าไม่ตรง |
| โปร | quote เลือก | เครื่องเลือก เซิร์ฟเวอร์ตรวจด้วย `evaluatePromotion` ณ `soldAt` ถ้าไม่ eligible หรือส่วนลดไม่ตรง → `promotionMismatch` แต่ยังบันทึกตามที่ขายจริง |
| ยอดรวม | เซิร์ฟเวอร์คำนวณ | เซิร์ฟเวอร์คำนวณใหม่ด้วย `calculateTotals` จากราคา/ส่วนลดที่ส่งมา ถ้าไม่เท่ากับยอดที่เครื่องส่ง → **ไม่สร้างบิล** แล้วเก็บไว้ในรายการตรวจ |
| สต็อก | ตรวจว่าพอ | ไม่ตรวจ ตัดผ่าน `IStockLedger` เสมอ ยอมให้ติดลบ แล้วทำเครื่องหมาย `negativeStock` |
| สมาชิก | ต้องเปิดใช้งาน | ถ้าสมาชิกถูกปิดไปแล้วยังบันทึกได้ และได้แต้มตาม [แบบแต้ม](2026-10-27-member-points-design.md) |
| QR / quote | ใช้ได้ | ปฏิเสธ (`OFFLINE_PAYMENT_NOT_ALLOWED`) |
| เวลา/เลขใบเสร็จ | ตอนนี้ | `sold_at` = เวลาจากเครื่อง (ตรวจว่าไม่อยู่ในอนาคตเกิน 5 นาที และไม่เก่ากว่า 48 ชั่วโมง) ส่วนเลขใบเสร็จออกจาก counter ของ**วันที่ขาย**ในเขตเวลาร้าน ต่อจากเลขล่าสุดของวันนั้น |
| กะ | ต้องเปิด | กะ `open` → เข้ากะตามปกติ ส่วนกะ `closing`/`closed` → บันทึกเป็น "บิลออฟไลน์ที่มาหลังปิดกะ" ไม่แก้ `shift_summaries` และแสดงแยกในหน้ากะเหมือน void หลังปิดกะ |
| ผู้ขาย | ผู้ใช้ที่ล็อกอิน | `cashierId` จากเครื่อง ต้องเป็นผู้ใช้ที่ยังเปิดใช้งาน ส่วน `syncedById` = ผู้ใช้ที่ส่ง |

- **audit:** ทุกบิลบันทึก `sale.offline_recorded` ใน unit of work เดียวกัน
- **คำขอที่ล้ม:** เก็บใน `offline_sale_rejections` (append-only: key, payload, เหตุผล, เวลา) แล้วตอบ 409 `OFFLINE_SALE_REJECTED`
  - เครื่องย้ายบิลนั้นไปสถานะ "ต้องตรวจ" และซิงก์บิลถัดไปต่อ ไม่ค้างทั้งคิว
- **ตารางบิล (`sales`) เพิ่ม:** `source` (`online` | `offline`, ค่าเริ่มต้น `online`), `offline_no`, `sold_at` (บิลเก่าใช้ `created_at`), `synced_by_id`, `review_flags text[]`
- **unique ใหม่:** `(source, offline_no)` เมื่อ `offline_no` ไม่เป็น null เป็นตัวกันซ้ำชั้นที่สองต่อจาก idempotency
- **รายงาน:** รายงานยอดขายต้องใช้ `sold_at` แทน `created_at` เพื่อให้บิลออฟไลน์อยู่ในวันที่ขายจริง ต้องตรวจทุก query ของรายงานและรายงานปิดกะ

## หน้าตรวจ (เจ้าของ, สิทธิ์ใหม่ `sales.offline_review`)

- **รายการ:** บิลออฟไลน์ที่มี `review_flags` และคำขอที่ถูกปฏิเสธ แบ่งหน้า `{ items, total }`
- **การจัดการ:**
  - กด "รับทราบ" เป็น command ที่บันทึก audit โดยไม่แก้บิล
  - ถ้าบิลผิดจริงให้ void ตามขั้นตอนเดิม
- **คำขอที่ถูกปฏิเสธ:** แสดงข้อมูลที่เครื่องส่งมาให้เจ้าของทำบิลใหม่เองตอนออนไลน์ ระบบไม่สร้างบิลให้อัตโนมัติ

## เทสต์ที่ต้องมี

- **web:**
  - ตัวตัดสินว่าออฟไลน์ (network error เทียบกับ 4xx)
  - outbox (เขียน/อ่าน/ลำดับ/ขีดจำกัด)
  - ตัวซิงก์: ลองใหม่ด้วย key เดิม, 409 แล้วข้ามไปบิลถัดไป, หยุดเมื่อออฟไลน์อีก
  - เลขชั่วคราว
  - ยอดบนเครื่องเท่ากับยอดที่เซิร์ฟเวอร์คำนวณ
- **use case `recorded`:**
  - ราคาไม่ตรง → บันทึกพร้อม flag
  - ยอดไม่ตรง → ไม่สร้างบิล
  - สต็อกติดลบ
  - กะปิดแล้ว
  - เวลาในอนาคต/เก่าเกิน
  - QR → ปฏิเสธ
  - key ซ้ำ → บิลเดิม
  - ผู้ขายถูกปิด
- **integration:**
  - ซิงก์บิลวันก่อนได้เลขของวันนั้นต่อจากเลขล่าสุด
  - ส่งซ้ำพร้อมกัน 2 คำขอได้บิลเดียว
  - รายงานปิดกะเดิมไม่เปลี่ยน
- **e2e:** ตัดเน็ตด้วย Playwright (`context.setOffline(true)`) → ขายเงินสด → reload หน้า → ต่อเน็ต → บิลขึ้นเซิร์ฟเวอร์

## ลำดับที่แนะนำให้ builder แบ่งงาน

1. service worker + snapshot
2. outbox + ขายออฟไลน์บนเครื่อง
