# โปรโมชัน — แบบออกแบบรุ่นแรก

วันที่: 2026-10-15

สถานะ: รอเจ้าของโครงการตรวจไฟล์นี้ก่อนเขียนแผนลงมือ (ดีไซน์ทั้งสามส่วนผ่านการตรวจในแชทแล้ว ข้อที่ผมเพิ่มเองอยู่ท้ายเอกสาร)

branch: `ohmattpon/promotions` แตกจาก `origin/main` หลังสมาชิกถูก merge แล้ว (`01dae68`)

## เป้าหมาย

พนักงานขายแล้วได้ส่วนลดโปรโมชันที่เซิร์ฟเวอร์เป็นผู้คำนวณ ใบเสร็จและประวัติบิลแสดงส่วนลดนั้น ยอดตรงกับเงินที่เก็บจริง และเงิน QR ที่ลูกค้าจ่ายแล้วไม่เคยกลายเป็นยอดที่บิลสร้างไม่ได้เพียงเพราะโปรโมชันหรือราคาเปลี่ยนระหว่างรอ

## ขอบเขต

ทำ:

- ลดท้ายบิลเป็นบาทหรือเปอร์เซ็นต์ (เปอร์เซ็นต์ตั้งเพดานได้)
- ยอดขั้นต่ำ วันเริ่ม/สิ้นสุด วันในสัปดาห์ และช่วงเวลาของวัน ตามเขตเวลาร้าน
- สิทธิ์ทุกคนหรือเฉพาะสมาชิก
- ใช้ร่วมทุกสาขา เจ้าของจัดการ แคชเชียร์ดูได้
- ตรึงราคาด้วย quote ฝั่งเซิร์ฟเวอร์ ก่อนชำระและก่อนสร้าง QR

ไม่ทำ: จำกัดจำนวนครั้งที่ใช้, คูปอง, ซื้อแถม, แต้ม, โปรโมชันต่อสาขา, โปรโมชันรายสินค้า, รายงานแยกตามโปรโมชัน, การส่งโปรโมชันไปจอลูกค้า

## 1. ข้อมูลโปรโมชัน

ใช้ร่วมทุกสาขา เปิด/ปิดใช้ได้ ลบไม่ได้ เจ้าของสร้างและแก้ได้ เจ้าของและแคชเชียร์อ่านได้

| ช่อง | กติกา |
|---|---|
| `name` | 1–80 ตัวอักษรหลังตัดช่องว่างหัวท้าย ห้ามซ้ำโดยไม่สนตัวพิมพ์ |
| `kind` | `fixed` หรือ `percent` |
| `value` | ถ้า `fixed` เป็นสตางค์ จำนวนเต็ม 1 ถึง `MAX_AMOUNT_SATANG`; ถ้า `percent` เป็น basis points จำนวนเต็ม 1–10000 (700 = 7%) แบบเดียวกับ `vatRateBp` |
| `maxDiscountSatang` | ใช้กับ `percent` เท่านั้น จำนวนเต็ม ≥ 1 หรือ null = ไม่มีเพดาน ห้ามตั้งกับ `fixed` |
| `minSubtotalSatang` | จำนวนเต็ม ≥ 0 เทียบกับยอดสินค้ารวมตัวเลือก ก่อนส่วนลดและก่อน VAT ที่บวกเพิ่ม |
| `startsOn`, `endsOn` | วันที่ตามเขตเวลาร้าน รวมวันสิ้นสุด ว่างได้ทั้งสองช่อง ถ้ามีทั้งคู่ต้อง start ≤ end |
| `weekdays` | ชุดของ 0–6 (0 = อาทิตย์) ว่างหรือ null = ทุกวัน |
| `windowStartMinute`, `windowEndMinute` | นาทีของวัน 0–1439 ต้องตั้งทั้งคู่หรือไม่ตั้งเลย และห้ามเท่ากัน ถ้า end < start ถือว่าข้ามเที่ยงคืน |
| `audience` | `everyone` หรือ `members` |
| `isActive` | เปิด/ปิดใช้ |

`INVALID_PROMOTION` ครอบคลุมทุกค่าข้างบนที่ไม่ผ่าน

## 2. สูตร (`domains/promotion.domain.ts` ฟังก์ชันล้วน)

`evaluatePromotion(promotion, { subtotalSatang, hasMember, at, timeZone })` คืน `{ eligible: false }` หรือ `{ eligible: true, discountSatang }`

- ต้องเปิดใช้ ผ่านวันเริ่ม/สิ้นสุด วันในสัปดาห์ ช่วงเวลา ยอดขั้นต่ำ และสิทธิ์ จึงถือว่าตรงเงื่อนไข
- `at` แปลงเป็นวันที่และนาทีของวันในเขตเวลาร้านด้วย `Intl`
- ช่วงที่ข้ามเที่ยงคืน (เช่น 22:00–02:00) นับตามวันที่ช่วงนั้นเริ่ม ดังนั้น 01:00 วันพุธเทียบ `weekdays` ด้วยวันอังคาร
- `fixed`: ส่วนลด = `value`
- `percent`: `Math.round(subtotal * value / 10000)` แล้วจำกัดด้วย `maxDiscountSatang` ถ้ามี
- ส่วนลดไม่เกินยอดสินค้า และต้อง ≥ 1 ถ้าได้ 0 ถือว่าไม่ตรงเงื่อนไข
- `pickBestPromotion` เลือกส่วนลดมากสุด ถ้าเท่ากันเลือก id ต่ำสุด ผลจึงคงที่
- ยอดสุทธิและ VAT คำนวณต่อด้วย `calculateTotals` เดิม ไม่แก้สูตรนั้น

เว็บใช้ฟังก์ชันเดียวกันผ่าน `@pos/api/promotions` เพื่อแสดงตัวอย่างในตะกร้า เซิร์ฟเวอร์เป็นผู้ตัดสินจริง

## 3. quote

quote คือตะกร้าที่เซิร์ฟเวอร์คิดราคาและตรึงไว้ ตาราง `price_quotes`

| ตรึงไว้ | เหตุผล |
|---|---|
| `branchId`, `memberId` และ snapshot สมาชิก (รหัส ชื่อ) | ใช้ข้ามสาขาหรือเปลี่ยนคนไม่ได้ |
| รายการ (สินค้า ตัวเลือกที่เป็น snapshot จำนวน ราคาต่อหน่วยรวมตัวเลือก) | แก้ราคาสินค้าระหว่างรอ QR ไม่ทำให้ยอดไม่ตรง |
| snapshot โปรโมชันที่เลือก (id ชื่อ ชนิด ค่า เพดาน) และ `discountSatang` | แก้หรือปิดโปรโมชันทีหลังไม่กระทบ |
| `vatMode`, `vatRateBp`, `vatSatang`, `totalSatang` | แก้ภาษีกลางทางไม่ทำให้เงินที่จ่ายแล้วไม่ตรงบิล |
| `orderId` (ถ้ามี) | ชำระออเดอร์ |
| `createdById`, `createdAt`, `expiresAt` | ตรวจย้อนหลัง |

สต็อกไม่ตรึง ตรวจและตัดตอนชำระตามเดิม ต้นทุนของสินค้าและตัวเลือกไม่ออกใน response

### สถานะ

| สถานะ | ความหมาย |
|---|---|
| `open` | หมดอายุ 15 นาทีหลังสร้าง (`QUOTE_VALID_FOR_MS`) ใช้กับเงินสดและบัตร |
| `reserved` | มี QR จองไว้ **ไม่หมดอายุ** จนกว่า QR จะถูก consume, cancel หรือ dismiss ซึ่งรองรับเงินที่มาถึงช้ากว่าเวลาที่หน้าจอรอ QR (`QR_VALID_FOR_MS` = 10 นาที ธนาคารไม่ได้ตั้งหมดอายุ) |
| `consumed` | สร้างบิลแล้ว ใช้ซ้ำไม่ได้ (`price_quotes.sale_id` ไม่ซ้ำ) |
| `cancelled` | ถูกยกเลิก หรือ QR ที่จองถูกยกเลิก/ dismiss (สร้างไม่สำเร็จ ปล่อยกลับเป็น `open` แทน) quote ที่ QR จองไว้ยังเก็บ `qr_reference` ไว้ ใช้ขายได้เฉพาะเมื่อ QR นั้นจ่ายแล้วและถูก claim ในบิลเดียวกัน เงินที่เข้ามาหลัง QR ถูกยกเลิกจึงได้ราคาที่ลูกค้าเห็น ส่วนการขอ QR ใหม่ต้องขอ quote ใหม่ |

`open` ที่หมดอายุถือเป็น `QUOTE_EXPIRED` ตอนใช้ ไม่ต้องมีงานตั้งเวลา quote ที่ค้างไม่มีผลต่อสต็อกหรือเงิน

### การเลือกโปรโมชัน

ตอนสร้าง quote ระบบอ่านโปรโมชันที่เปิดใช้ ประเมินด้วยเวลาปัจจุบันและสมาชิกของคำขอ แล้วเลือกอันที่ดีที่สุดผ่าน `pickBestPromotion` ถ้าไม่มีอันไหนตรงเงื่อนไข quote ยังถูกสร้าง โดย `promotion` เป็น `null` และส่วนลดเป็น 0 เพื่อให้ตรึงราคาสำหรับ QR ได้เหมือนกัน เวลาประเมินคือ `createdAt` ของ quote และถูกตรึงตามนั้น

## 4. การทำงานของ checkout

- คำขอ checkout (legacy และ v2) และ `pay-order` รับ `quoteId` ที่ไม่บังคับ ไม่ส่ง = ทำงานเหมือนเดิมทุกอย่าง มีเฉพาะส่วนลดกรอกเอง
- ถ้ามี `quoteId` ต้องไม่ส่ง `discountSatang > 0` ถ้าส่งทั้งคู่ ปฏิเสธ `PROMOTION_AND_DISCOUNT_CONFLICT`
- รายการ (หลังรวมสินค้า+ตัวเลือกซ้ำกันแบบเดียวกับที่ checkout ทำอยู่), `memberId` และสาขาในคำขอต้องตรงกับ quote ถ้าไม่ตรง `QUOTE_MISMATCH` โดย quote ยังใช้ได้
- ใช้ราคาต่อหน่วย ส่วนลด `vatMode` และ `vatRateBp` จาก quote ผ่านทางที่ `SaleCheckout` ใช้กับราคาที่ออเดอร์ quote ไว้อยู่แล้ว (`unitPriceSatang` ต่อบรรทัด) และส่ง snapshot โปรโมชันให้ `SaleEntity.complete` ไม่แก้ `calculateTotals`
- quote ที่มีสมาชิก ใช้ snapshot สมาชิกจาก quote และไม่ตรวจว่าสมาชิกยังเปิดใช้ เพราะตรวจตอนสร้าง quote แล้ว ไม่เช่นนั้นสมาชิกที่ถูกปิดระหว่างรอ QR จะทำให้เงินที่จ่ายแล้วสร้างบิลไม่ได้ (ข้อนี้ผ่อนกฎ "ตอนชำระตรวจว่าสมาชิกยังเปิดใช้" ของสมาชิกเฉพาะกรณีมี quote)
- ถ้าบิลใช้ QR ที่ quote จองไว้แต่คำขอไม่ส่ง `quoteId` (เช่น ใช้เงินที่มาถึงช้าจากรายการที่ยังไม่มีบิล) ตอบ `QUOTE_REQUIRED` พร้อม `quoteId` ใน `params` ให้ไคลเอนต์ส่งซ้ำด้วย quote นั้น QR ที่ quote จองไว้ใช้กับคำขอที่ไม่มี quote ไม่ได้ เพื่อไม่ให้ quote ค้างเป็น `reserved`
- ลำดับล็อก: ออเดอร์ → quote (`findByIdForUpdate`) → รายการชำระด้วย QR → สมาชิก → สินค้า (ลำดับสินค้าเดิม) คำสั่งยกเลิก/ปิดรายการ QR ล็อก quote ก่อนล็อก QR ด้วยลำดับเดียวกัน
- สร้างบิลแล้ว quote เป็น `consumed` และเก็บ `sale_id` ของบิลนั้น
- การเรียก quote ทั้งหมดอยู่ใน unit of work ของผู้เรียก ผ่าน port `IQuoteClaims`

## 5. ผลต่อ QR

- คำขอสร้าง QR (legacy และ v2) รับ `quoteId` ที่ไม่บังคับ ยอด QR ต้องไม่เกิน `totalSatang` ของ quote ถ้าเกิน `QUOTE_AMOUNT_MISMATCH` (ยอดน้อยกว่าได้ เพราะบิลแบ่งจ่ายหลายวิธีได้อยู่แล้ว) quote หนึ่งใบผูกกับ QR ได้ใบเดียว และ QR ที่สร้างจาก quote ใช้ได้เฉพาะกับ quote นั้น
- ในโหมดกะ การจอง quote อยู่ในขั้นจองรายการใน `shift_qr_attempts` ภายใต้การล็อกกะ (ขั้นที่ 1 ของ `CreateQrPaymentV2UseCase`) แล้วเรียกธนาคารนอก transaction ตามเดิม
- ธนาคารปฏิเสธหรือไม่ถึงธนาคาร (attempt `failed`) ปล่อย quote กลับเป็น `open` (ถ้ายังไม่หมดอายุ) หรือ `cancelled` ผลที่ไม่ทราบ (`unknown`) คง `reserved` จนกว่าจะ resolve
- QR ถูก cancel หรือ dismiss: quote เป็น `cancelled`
- QR ถูก claim ตอนสร้างบิล: quote เป็น `consumed` ใน transaction เดียวกับบิล
- เงินที่จ่ายแล้วผูกกับ quote ที่ `reserved` จึงสร้างบิลได้เสมอด้วยราคาที่ลูกค้าเห็นตอนสแกน แม้โปรโมชันหมดอายุ ถูกแก้ ราคาสินค้าเปลี่ยน หรือ VAT เปลี่ยน ต้องมีสต็อกพอตามเดิม ถ้าไม่พอ เจ้าของยัง dismiss ได้ตามกฎเดิมของ QR
- แก้ตะกร้าหรือสมาชิกหลังสร้าง QR: checkout จะ `QUOTE_MISMATCH` พนักงานต้องกลับไปตะกร้าเดิม หรือยกเลิก QR ก่อนขอ quote ใหม่
- ไม่ส่ง `quoteId` = QR แบบเดิมทั้งหมด (ยอดจากไคลเอนต์ ราคาสด)

## 6. ออเดอร์

- ขอ quote ด้วย `orderId` ได้ ระบบอ่านรายการ (ราคาที่ออเดอร์ quote ไว้) และสมาชิกจากออเดอร์ผ่าน port ของโมดูล orders ไม่รับ `lines` และ `memberId` ในคำขอนั้น
- ออเดอร์ของสาขาอื่นตอบ `ORDER_NOT_FOUND`
- ออเดอร์ที่มี quote ในสถานะ `reserved` แก้รายการ จำนวน สมาชิก ย้ายโต๊ะ รวมบิล แยกบิล หรือยกเลิกไม่ได้ จนกว่า QR จะถูก resolve: `ORDER_LOCKED_BY_QR_PAYMENT` ตรวจที่จุดเดียวคือ `save` ของ repository ออเดอร์ (decorator ที่ถามพอร์ต `IOrderEditLock` ซึ่งโมดูล quotes เป็นผู้ตอบ) หลัง use case ล็อกแถวออเดอร์แล้ว จึงครอบคลุมทุกคำสั่งที่แก้ออเดอร์ รวมถึงการเปลี่ยนป้ายชื่อ ส่วนการอ่านและการชำระ (ที่ใช้ quote นั้นเอง) ไม่ถูกกระทบ
- quote ที่ยัง `open` ของออเดอร์ไม่ล็อกออเดอร์ แต่จะ `QUOTE_MISMATCH` ถ้าออเดอร์เปลี่ยนก่อนชำระ

## 7. บิล

`sales` เพิ่ม `promotion_id` (FK nullable), และ `promotion` (jsonb snapshot: ชื่อ ชนิด ค่า เพดาน ยอดลด) ข้อมูลเดิมเป็น null (การผูกบิลกับ quote อยู่ที่ `price_quotes.sale_id`) บิลที่บันทึกแล้วห้ามแก้

- `discountSatang` ยังเป็นยอดลดรวมที่ใช้ในรายงานเดิม และเท่ากับยอดลดของโปรโมชันเมื่อใช้ quote
- ใบเสร็จและประวัติบิลแสดงชื่อโปรโมชันจาก snapshot ถ้าเป็น null ไม่แสดงอะไร
- ยกเลิกบิลไม่คืน quote เพราะไม่มีเพดานจำนวนครั้ง ไม่มีอะไรต้องคืน
- response ของบิลเพิ่ม `promotion` ที่เป็น null ได้ ไม่ส่งต้นทุนของตัวเลือก

## 8. API (ทั้งหมดใต้ `/api/v1` เพิ่มแบบ additive)

| เส้นทาง | ชนิด | สิทธิ์ | หน้าที่ |
|---|---|---|---|
| `GET /promotions` | query | เจ้าของ/แคชเชียร์ | `{ items, total }` รับ `limit` `offset` `isActive` |
| `GET /promotions/{id}` | query | เจ้าของ/แคชเชียร์ | รายละเอียด |
| `POST /promotions` | command | เจ้าของ | สร้าง |
| `PATCH /promotions/{id}` | command | เจ้าของ | แก้และเปิด/ปิดใช้ ไม่มี DELETE |
| `POST /quotes` | command | เจ้าของ/แคชเชียร์ | คิดราคาตะกร้า เลือกโปรโมชัน ตรึง |
| `GET /quotes/{id}` | query | เจ้าของ/แคชเชียร์ | อ่านอย่างเดียว ไม่เขียนข้อมูล |
| `POST /quotes/{id}/cancel` | command | เจ้าของ/แคชเชียร์ | ยกเลิก quote ที่ `open` ถ้า `reserved` ปฏิเสธ `QUOTE_NOT_OPEN` |

- `POST /quotes` รับ `{ lines: [{ productId, quantity, optionIds? }], memberId? }` หรือ `{ orderId }` สาขามาจาก `await branch()` ห้ามอ่าน header เอง คำขอซ้ำสร้าง quote ใหม่ได้ ไม่ต้องใช้ idempotency key เพราะ quote ที่ไม่ถูกใช้หมดอายุเอง
- เพิ่ม `quoteId` ที่ไม่บังคับใน checkout, `pay-order` และสร้าง QR ทั้ง legacy และ v2
- การเปลี่ยนสัญญาเป็นแบบเพิ่มช่อง ก่อนบันทึก `test/openapi-baseline.json` ใหม่ ต้องแจ้งเจ้าของโครงการ

### รหัสข้อผิดพลาดใหม่

| code | สถานะ | เมื่อ |
|---|---|---|
| `PROMOTION_NOT_FOUND` | 404 | ไม่พบโปรโมชัน |
| `QUOTE_NOT_FOUND` | 404 | ไม่พบ quote หรือเป็นของสาขาอื่น |
| `INVALID_PROMOTION` | 400 | ค่าไม่ผ่านกติกาในข้อ 1 |
| `PROMOTION_NAME_TAKEN` | 409 | ชื่อซ้ำ |
| `QUOTE_EXPIRED` | 409 | quote ที่ `open` หมดอายุ |
| `QUOTE_NOT_OPEN` | 409 | quote ถูกใช้ ยกเลิก หรือถูกจองโดย QR อื่น |
| `QUOTE_MISMATCH` | 409 | รายการ สมาชิก หรือสาขาไม่ตรง |
| `QUOTE_AMOUNT_MISMATCH` | 409 | `amountSatang` ของ QR เกินยอดสุทธิของ quote |
| `QUOTE_REQUIRED` | 409 | ใช้ QR ที่ quote จองไว้โดยไม่ส่ง `quoteId` (`params.quoteId` บอก quote) |
| `PROMOTION_AND_DISCOUNT_CONFLICT` | 409 | ส่ง `quoteId` พร้อม `discountSatang > 0` |
| `ORDER_LOCKED_BY_QR_PAYMENT` | 409 | แก้ออเดอร์ที่ quote ถูกจองโดย QR |

ข้อความภาษาไทยอยู่ใน domain error และต้องเพิ่มคำแปลใน `apps/web/src/locales/errors.ts`

## 9. สถาปัตยกรรม API

- `domains/promotion.domain.ts` (entity กฎ และสูตร) และ `domains/price-quote.domain.ts` ไม่ import ชั้นอื่น พร้อมไฟล์ทดสอบข้างกัน
- โมดูล `promotions` ตามต้นแบบ `categories`: `CreatePromotionUseCase`, `UpdatePromotionUseCase` (command) และ `ListPromotionsUseCase`, `GetPromotionUseCase` (query)
- โมดูล `quotes`: `CreateQuoteUseCase`, `CancelQuoteUseCase` (command), `GetQuoteUseCase` (query) อ่านโปรโมชันผ่าน port `IPromotionCatalog`, อ่านสินค้าและตัวเลือกผ่าน `IProductRepository` และ `ILineOptionsResolver`, อ่านออเดอร์ผ่าน port ของ orders
- port `IQuoteClaims` (lock, consume, reserveForQr, releaseByReference, cancelByReference, lockByReference, findReservedByReference) ให้ `SaleCheckout` และ `qr-payments` ใช้ ตามแบบ `IQrPaymentClaims`; port `IOrderEditLock` ของโมดูล orders ที่ quotes เป็นผู้ตอบ; port `IOrderQuoteSource` ของโมดูล quotes ที่ orders เป็นผู้ตอบ (ล็อกและอ่านรายการของออเดอร์) แต่ละโมดูลไม่แตะตารางของโมดูลอื่น
- repository ใช้ `currentExecutor()` อ่านที่ต้องล็อกชื่อลงท้าย `ForUpdate` ทุกคำสั่งที่เขียนหลายตารางอยู่ใน `IUnitOfWork.run()`
- ตาราง `promotions` และ `price_quotes` ใหม่ พร้อม migration และคอลัมน์ใหม่ของ `sales` (`promotion_id`, `promotion`) quote เก็บรหัสอ้างอิงของ QR ที่จองไว้เองใน `price_quotes.qr_reference` จึงไม่แก้ตาราง QR ข้อมูลเดิมไม่ถูกแตะ
- ลงทะเบียน DI ที่ `modules/di-registrations.ts`

## 10. หน้าเว็บ

- feature `promotions` ใหม่: หน้าจัดการสำหรับเจ้าของ ใช้ `DataTable` ทุกคอลัมน์ระบุ `priority` ฟอร์มใน dialog ช่วงวันใช้ `DatePicker` วันในสัปดาห์เป็นกลุ่มปุ่ม ช่วงเวลา และสวิตช์เปิด/ปิดใช้ แคชเชียร์เห็นรายการแต่แก้ไม่ได้ และ API ตรวจซ้ำเสมอ
- `features/promotions/index.ts` ส่งออกเฉพาะที่ `pos` ใช้ (query ของรายการและสูตร) feature นี้ห้าม import `pos`
- หน้าขาย: ตะกร้าแสดงโปรโมชันที่ตรงเงื่อนไขและยอดลดด้วยสูตรกลาง ปุ่ม "ยกเลิกโปรโมชัน" ก่อนกรอกส่วนลดเอง ช่องส่วนลดกรอกเองถูกปิดไว้จนกว่าจะกดปุ่มนี้ จึงไม่มีทางบวกซ้อนโดยไม่ตั้งใจ
- ขอ quote ตอนเปิดหน้าชำระ ยอดจากเซิร์ฟเวอร์เป็นหลัก ถ้าต่างจากตัวอย่างในตะกร้า ให้แสดงยอดของเซิร์ฟเวอร์ ถ้าพนักงานกรอกส่วนลดเอง ไม่ขอ quote และใช้ทางเดิม
- สร้าง QR ส่ง `quoteId` เมื่อมี และแสดงสถานะ "ล็อกเพราะรอ QR" ที่ตะกร้าและออเดอร์จนกว่าจะ resolve
- zustand เก็บเฉพาะ `quoteId` กับสถานะ "ปฏิเสธโปรโมชันแล้ว" ไม่คัดลอกข้อมูลโปรโมชัน และล้างตอนออกจากระบบ สลับสาขา หรือเริ่มตะกร้าใหม่ พร้อมตะกร้า
- query key ผ่าน key factory ของ feature mutation ที่ใช้ quote invalidate ผ่าน factory ของ `products` เมื่อชำระ
- ข้อความทั้งหมดผ่าน `t()` ใน `features/promotions/locales.ts` (th/en, `en` ใช้ `satisfies typeof th`) เงินและวันที่ผ่าน `useFormat()` ห้ามเขียน `฿` หรือหาร 100 เอง
- ใบเสร็จแสดงชื่อโปรโมชันจาก snapshot
- ใช้ได้ที่ 390, 768 และ 1366px ปุ่มและช่องกรอกสูง 44px skeleton ตอนโหลดครั้งแรก ข้อผิดพลาดมีปุ่มลองใหม่ และเพิ่มหน้าใหม่ในรายการ e2e/screenshots

## 11. เกณฑ์ยอมรับและการทดสอบ

1. **Domain/unit:** ปัดเศษ เพดาน ยอดขั้นต่ำ ส่วนลดไม่เกินยอดสินค้า วันเริ่ม/สิ้นสุดแบบรวม วันในสัปดาห์ ช่วงเวลา (รวมข้ามเที่ยงคืน) เขตเวลา สิทธิ์สมาชิก tie-break และทุกค่าที่ `INVALID_PROMOTION`
2. **Use case กับ mock port (`bun run test:unit` ไม่ต้องมีฐานข้อมูล):** ทุกกรณีสำเร็จและถูกปฏิเสธ
3. **HTTP/PostgreSQL:**
   - ใช้ quote เดียวพร้อมกันได้บิลเดียว
   - QR จ่ายหลังโปรโมชันหมดอายุหรือถูกปิด ยังได้ราคา quote
   - แก้ราคาสินค้าและ VAT กลางทางไม่กระทบเงินที่จ่ายแล้ว
   - ปิดสมาชิกระหว่างรอ QR ยังสร้างบิลได้
   - เปลี่ยนสมาชิกหรือตะกร้าแล้ว `QUOTE_MISMATCH` โดย quote ยังใช้ได้
   - ออเดอร์ที่มี quote จอง QR แก้ไม่ได้ ยกเลิก QR ปล่อยออเดอร์และ quote
   - แก้โปรโมชันหลังสร้าง quote ไม่เปลี่ยน quote หรือบิลเก่า
   - ยกเลิกบิลโปรโมชัน และ rollback เมื่อสร้างบิลล้มเหลวแล้ว quote ยัง `open`/`reserved` ตามเดิม
   - ทุก list คืน `{ items, total }` และบิลของสาขาอื่นตอบว่าไม่พบ
4. **Regression:** checkout, `pay-order` และ QR ที่ไม่ส่ง `quoteId` ทำงานเหมือนเดิมทั้งหมด (บิล VAT สต็อก กะ idempotency การ claim QR)
5. **Browser:** สร้าง/แก้/ปิดโปรโมชัน, ขายด้วยโปรโมชัน, ยกเลิกโปรโมชันแล้วกรอกเอง, QR ผ่าน quote, ชำระออเดอร์, logout/สลับสาขา, สิทธิ์แคชเชียร์ และข้อผิดพลาด
6. **ก่อนบอกว่าเสร็จ:** `bun run typecheck`, `bun run test`, `bun run lint`, `bun run openapi:check`, web build, `bun run e2e`, `bun run screenshots` และดูภาพ 390/768/1366px ด้วยตา
7. ทดสอบกับฐานข้อมูลทดสอบแยกและ SCB จำลองใน `apps/api/test/scb-server.ts` ห้ามเรียก SCB จริงหรือแตะฐานข้อมูล dev

## ข้อที่ผมเพิ่มเอง ขอให้ตรวจ

เรื่องเหล่านี้ไม่ได้ถูกถามในแชท ผมตัดสินเพื่อให้ดีไซน์ปิดครบ:

- ชื่อโปรโมชันห้ามซ้ำ (`PROMOTION_NAME_TAKEN`) เพื่อไม่ให้พนักงานสับสนสองรายการชื่อเดียวกัน
- โปรโมชันที่ได้ส่วนลด 0 สตางค์ถือว่าไม่ตรงเงื่อนไข
- quote ที่มีสมาชิกไม่ตรวจว่าสมาชิกยังเปิดใช้ตอนชำระ (ข้อ 4) เพื่อกันเงิน QR ค้าง
- ออเดอร์ที่ quote ถูกจองโดย QR ถูกล็อกจนกว่า QR จะ resolve (ข้อ 6)
- `POST /quotes` ไม่ใช้ idempotency key
- เวลาที่ใช้ประเมินโปรโมชันคือเวลาสร้าง quote และถูกตรึงตามนั้น
