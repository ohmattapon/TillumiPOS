# หน้าจอที่ใช้ได้ทุกขนาดจอ (รอบที่ 1 ของการปรับ design)

สถานะ: ร่างสำหรับให้เจ้าของโครงการตรวจ · branch `ohmattpon/responsive-layout` (แตกจาก `ohmattpon/local-image-storage` เพราะแก้หน้าจอที่ branch นั้นเปลี่ยนไปแล้ว: ฟอร์มสินค้าและ e2e)

## เป้าหมาย

แคชเชียร์ขายได้ครบบนมือถือและแท็บเล็ตแนวตั้ง และเจ้าของจัดการร้านได้บนมือถือ โดยวางกฎใน `DESIGN.md` และคอมโพเนนต์กลางที่หน้าใหม่ในอนาคต (ใบสั่งครัว สิทธิ์ละเอียด) ทำตามได้เลย ไม่ต้องออกแบบใหม่ทุกหน้า

เจ้าของเลือกแนวทาง "วางรากฐานก่อน": แก้โครงสร้าง layout และกฎ ไม่เปลี่ยนภาษาภาพ (สี ฟอนต์ การ์ด)

## สิ่งที่เห็นจากหน้าจอจริง (ถ่ายด้วย Chrome headless ที่ 390, 768, 1366 px)

| ขนาด | สภาพ |
|---|---|
| จอคอม 1366 | หน้าขายใช้ได้ดี ลำดับความสำคัญชัด การ์ดสินค้าที่ไม่มีรูปเสียครึ่งการ์ดให้ไอคอนรูปว่าง |
| แท็บเล็ต 768 | sidebar กางเต็ม 256px สินค้าเหลือคอลัมน์เดียว ช่องค้นหาถูกตัดจนอ่านไม่ออก หัวหน้าถูกตัด |
| มือถือ 390 | ขายไม่ได้: ตะกร้าทับรายการสินค้า ตารางของหน้าจัดการล้นขวาจนปุ่มการทำงานหลุดจอ |
| ทุกขนาด | dialog ชำระเงินและหน้าตั้งค่าดีอยู่แล้ว |

## การตัดสินใจ

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| ช่วงขนาดจอ | มือถือ < 640px, แท็บเล็ต 640–1023px, จอใหญ่ ≥ 1024px (Tailwind `sm`, `lg`) | ตรงกับอุปกรณ์จริงของร้าน และเป็น breakpoint ที่มีอยู่แล้วใน Tailwind |
| เมนูหลัก | จอใหญ่: sidebar กาง · แท็บเล็ต: แถบไอคอนเป็นค่าเริ่มต้น · มือถือ: แถบเมนูล่าง 4 ช่อง (ขาย, วันนี้, กะ, เมนู) | พื้นที่ของหน้าขายสำคัญกว่าเมนู แคชเชียร์ใช้แค่สามหน้าแรก |
| ตะกร้า | จอใหญ่: แผงขวาแบบเดิม · เล็กกว่านั้น: แถบตะกร้าติดล่าง (จำนวน, ยอดสุทธิ, ปุ่มชำระ) แตะแล้วเปิดตะกร้าเป็นแผงจากล่าง ทำได้ครบเหมือนแผงขวา | รายการสินค้าได้ความกว้างเต็มจอ และปุ่มชำระอยู่ใต้นิ้วเสมอ |
| การ์ดสินค้า | สินค้าที่ไม่มีรูปไม่แสดงช่องรูป เหลือชื่อ ราคา และยอดคงเหลือ | ร้านส่วนใหญ่ไม่มีรูปครบ ได้สินค้าต่อหน้าจอเกือบเท่าตัว |
| แถบหัวของหน้า | ปุ่มสูง 44px ทุกตัว บนมือถือปุ่มรองรวมในเมนู "เพิ่มเติม" และหัวข้อตัดบรรทัดได้ ไม่ถูกตัดกลางคำ | `DESIGN.md` กำหนด 44px อยู่แล้วแต่ปุ่มแถบหัวสูง 36px |
| ตาราง | คอมโพเนนต์กลาง `DataTable`: ≥ 640px เป็นตาราง < 640px เป็นรายการ คอลัมน์ประกาศ `priority` เป็น `primary` / `secondary` / `wide-only` ใช้กับห้าหน้าที่มีตาราง (สินค้า หมวดหมู่ สาขา ผู้ใช้ บิลวันนี้) | กฎเดียวกันทุกหน้า หน้าใหม่ได้มือถือมาเอง |
| ผังโต๊ะ | ≥ 640px แก้ผังด้วยการลากเหมือนเดิม · มือถือแสดงโต๊ะเป็นรายการ เพิ่ม เปลี่ยนชื่อ ปิดใช้ได้ แต่ไม่ลากตำแหน่ง พร้อมข้อความให้จัดผังบนจอใหญ่ | ลากบนผัง 1000×700 ด้วยนิ้วบนจอ 390px ไม่สมจริง |
| dialog บนมือถือ | กว้างเต็มจอ เนื้อหาเลื่อนได้ ปุ่มยืนยันและยกเลิกติดล่างเสมอ | ปุ่มยืนยันต้องไม่หลุดจอเมื่อแป้นพิมพ์เปิด |
| ความหนาแน่น | หน้าขาย: ชื่อสินค้าและบรรทัดในตะกร้า 16px · หน้าจัดการ: 14px เหมือนเดิม | คนขายยืนมองจอห่าง คนจัดการนั่งอ่านใกล้ |
| เปลี่ยนหน้า | ปุ่มไปหน้ากะใช้ router ของแอป ไม่โหลดหน้าใหม่ (`window.location.href`) | ไม่กระพริบและไม่โหลดซ้ำทุกครั้งที่เปิดร้าน |

## สิ่งที่ไม่เปลี่ยน

สี ฟอนต์ รูปทรงการ์ด dialog ชำระเงิน คีย์ลัด (F2, F9) และการสแกนบาร์โค้ดบนจอใหญ่ สัญญาของ API (งานนี้เป็นฝั่งเว็บล้วน)

## โครงสร้างในโค้ด

- `src/components/DataTable.tsx`: คอลัมน์ `{ id, header, cell, priority, align? }` แถว `onSelect?` และ `actions?` (เมนูการทำงานของแถว) แสดงเป็นตารางหรือรายการตามความกว้าง ด้วย CSS (`sm:`) ไม่ใช้ JavaScript วัดจอ จึงไม่กระพริบตอนโหลด
- `src/components/BottomNav.tsx` และการตั้งค่า `Sidebar` ใน `app/AppSidebar.tsx` (ค่าเริ่มต้นย่อบนแท็บเล็ต ซ่อนบนมือถือ)
- `features/pos/components`: `CartBar` (แถบล่าง) ใช้ `CartPanel` เดิมเป็นเนื้อหาในแผงจากล่าง (`ui/sheet`) ไม่เขียนตะกร้าซ้ำสองชุด
- ข้อความใหม่ทั้งหมดผ่าน `t()` ในไฟล์ `locales.ts` ของ feature นั้น หรือ `locales/common.ts` สำหรับเมนูล่าง
- ตรรกะที่ไม่ผูกกับ React (เช่นการแบ่งคอลัมน์ตาม priority) อยู่ในฟังก์ชันล้วนพร้อมทดสอบข้างไฟล์

## การทดสอบ

- e2e ขายครบหนึ่งบิลที่ 390px: แตะสินค้า → แถบตะกร้าแสดงยอด → เปิดตะกร้าแก้จำนวน → ชำระ → ใบเสร็จ
- e2e เปิดทุกหน้าที่ 390, 768, 1366 px และตรวจว่า `document.documentElement.scrollWidth <= innerWidth` (ไม่มีหน้าไหนล้นแนวนอน) และเป้ากดที่มองเห็นทุกตัวสูงอย่างน้อย 44px บนหน้าขาย
- e2e เดิมทั้งหมด (26) ต้องผ่านโดยไม่แก้ความหมายของการตรวจ ปรับได้เฉพาะ locator ที่ย้ายที่
- `bun run screenshots`: เก็บสคริปต์ถ่ายภาพที่ใช้ในรอบนี้ (ฐานข้อมูลแยก `pos_e2e_shots` ไม่แตะฐานข้อมูล dev) ไว้ตรวจด้วยตาก่อน merge งานหน้าจอ ภาพไม่ถูก commit
- ทดสอบฟังก์ชันล้วนของ `DataTable` ด้วย `bun test`
