# ใบสั่งครัวและจอครัว

สถานะ: ร่างรอรีวิวของเจ้าของโครงการ · roadmap ข้อ 9 พร้อมงานรอบ design 2 · branch `ohmattpon/kitchen-tickets` (แตกจาก `main`)

## เป้าหมาย

แคชเชียร์ส่งรายการในออเดอร์ไปครัวหรือบาร์ตามสถานีได้ ครัวเห็นรายการใหม่บนจอภายใน 3 วินาที กดทำเสร็จได้ และรายการที่ลดหรือยกเลิกหลังส่งไปแล้วขึ้นบนจอทันที ส่วนหน้าแรกของร้านเลือกได้ว่าจะเป็นหน้าขายหรือผังโต๊ะ

## การตัดสินใจ

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| สถานี | ของร้านทั้งร้าน ใช้ร่วมทุกสาขาเหมือนหมวดหมู่ หมวดหนึ่งผูกได้หนึ่งสถานี หมวดที่ไม่ผูกไม่ส่งครัว | เมนูใช้ร่วมกันอยู่แล้ว ไม่ต้องแก้ฟอร์มสินค้า |
| การส่ง | แคชเชียร์กดส่งครัวเอง แต่ละครั้งเป็นหนึ่งรอบ รายการที่ยังไม่เคยส่งถูกจัดเป็นหนึ่งใบต่อสถานี | ร้านอาหารส่งเป็นรอบ เพิ่มหลายรายการก่อนส่งได้ |
| จอครัว | หน้า `/kitchen` เลือกสถานีได้ ดึงข้อมูลใหม่ทุก 3 วินาทีด้วย TanStack Query (`refetchInterval`) ไม่ใช้ SSE | ไม่ต้องมีบริการเพิ่ม ทำงานได้กับ Docker เดิม และ 3 วินาทีพอสำหรับครัว |
| ทำเสร็จ | ครัวกดทำเสร็จทั้งใบ ไม่กดรายบรรทัด | ลดการกด |
| ลดหรือลบหลังส่ง | จำนวนที่ส่งแล้วส่วนที่เกินจากระดับใหม่ถูกตั้งเป็น "ยกเลิก N" บนใบ (ตัดจากใบที่ใหม่สุดก่อน) จนครัวกดเสร็จ เพิ่มจำนวนกลับเป็นส่วนที่ยังไม่ส่ง | ครัวหยุดทำได้ทันที |
| ยกเลิกออเดอร์ | ทุกรายการที่ส่งแล้วขึ้นว่ายกเลิก | ออเดอร์ที่ยกเลิกไม่ควรถูกทำ |
| ชำระแล้ว | ใบที่ค้างยังอยู่บนจอจนครัวกดเสร็จ | อาหารยังต้องทำ |
| หมายเหตุต่อบรรทัด | เก็บในรายการของออเดอร์ พิมพ์บนใบ แก้ได้เฉพาะบรรทัดที่ยังไม่เคยส่ง | จอครัวต้องตรงกับที่ส่งไป |
| สต็อก | ไม่ตัดตอนส่งครัว | ตามกติกาเดิมของออเดอร์ |
| การพิมพ์ | ไม่พิมพ์ใบสั่งออกเครื่องพิมพ์ | นอกขอบเขตตามสเปกใบเสร็จ |
| ย้ายโต๊ะ | ทำได้ตามปกติ จอครัวอ่านโต๊ะปัจจุบันจากออเดอร์ | ไม่กระทบรายการที่ส่งแล้ว |
| รวมบิล | ทำไม่ได้ถ้าต้นทางหรือปลายทางมีใบค้าง ใบที่เสร็จแล้วของต้นทางย้ายไปปลายทาง | ครัวไม่เห็นรายการหาย และจำนวนที่ส่งแล้วไม่ถูกนับซ้ำ |
| แยกบิล | ทำไม่ได้ถ้าออเดอร์มีใบค้าง หรือรายการที่แยกเคยส่งครัวแล้ว | แยกจำนวนที่ส่งแล้วระหว่างออเดอร์ยังไม่ทำ (ดูคำถามเปิด) |

## ข้อมูล

migration `0014_kitchen` (ตาราง `kitchen_*` เป็นของโมดูล `kitchen` เท่านั้น):

- `kitchen_stations`: `id`, `name` (ไม่ซ้ำ), `sort_order`, `is_active`, timestamps ไม่มีการลบ ปิดใช้ได้
- `kitchen_category_stations`: `category_id` (PK, FK `categories`), `station_id` (FK `kitchen_stations`) หมวดที่ไม่มีแถวคือไม่ส่งครัว
- `kitchen_tickets`: `id`, `branch_id`, `order_id` (FK `orders`), `station_id`, `round_no`, `status` (`pending` | `done`), `sent_by_id`, `done_by_id` (null ได้), `done_at` (null ได้), timestamps ไม่ซ้ำ `(order_id, station_id, round_no)` ดัชนี `(branch_id, station_id, status)`
- `kitchen_ticket_lines`: `id`, `ticket_id` (FK cascade), `product_id`, `product_name`, `options_key`, `options` (jsonb snapshot), `note` (null ได้), `quantity` (จำนวนที่ส่ง), `voided_quantity` (ค่าเริ่มต้น 0) ตรวจ `0 <= voided_quantity <= quantity`
- `order_items.note` (null ได้)
- `shop_settings.home_view` เป็น enum `till` | `tables` ค่าเริ่มต้น `till` (โมดูล `settings`)

**การนับ** รายการของออเดอร์ระบุด้วย `(product_id, options_key)` ซึ่งไม่ซ้ำในออเดอร์อยู่แล้ว

- ส่งแล้วสุทธิ = ผลรวม `quantity - voided_quantity` ของบรรทัดครัวที่อยู่ในใบของออเดอร์นั้นและตรงคีย์
- ส่งได้ = จำนวนรายการของออเดอร์ − ส่งแล้วสุทธิ (ถ้าน้อยกว่าศูนย์ถือเป็นศูนย์)
- ลดจำนวนรายการลงต่ำกว่าส่งแล้วสุทธิ: เพิ่ม `voided_quantity` ของบรรทัดครัวที่ใหม่สุดก่อนจนถึงระดับใหม่
- ลบรายการ: ยกเลิกส่วนที่ส่งแล้วสุทธิทั้งหมด
- ยกเลิกออเดอร์: ยกเลิกส่วนที่ส่งแล้วสุทธิทุกรายการ

ทุกคำสั่งที่แก้ออเดอร์ล็อกแถวออเดอร์ก่อนแล้วทำการนับในธุรกรรมเดียวกัน ทำให้กดส่งสองครั้งพร้อมกันไม่เกิดใบซ้ำ

## โดเมน

- `KitchenStationEntity`: ตรวจชื่อ (1–50 ตัวอักษร) โยน `INVALID_KITCHEN_STATION`
- `KitchenTicketEntity`: สร้างจากรายการที่จะส่ง ต้องมีอย่างน้อยหนึ่งบรรทัดที่จำนวนเป็นจำนวนเต็มบวก เมธอด `markDone(actor)` ทำได้เฉพาะใบ `pending` (`KITCHEN_TICKET_NOT_PENDING`)
- ฟังก์ชันล้วนใน `domains/kitchen.domain.ts`: `sentNet(lines)`, `unsentQuantity(orderQty, sentNet)`, `planVoids(tickets, newQty)` และ `groupByStation(lines, stationOf)` ทดสอบครบทุกกรณีขอบ
- `OrderEntity` เพิ่ม `setLineNote(lineId, note)` ส่วนการตรวจใบค้างและการเคยส่งครัวอยู่ใน use case รวมและแยกบิล

## API

โมดูลใหม่ `kitchen` ใต้ `/api/v1` ทุกเส้นทางอ่านสาขาจาก `await branch()`

| Use case | ชนิด | เส้นทาง | สิทธิ์ |
|---|---|---|---|
| `ListKitchenStations` | query | `GET /catalog/kitchen-stations` | ผู้ใช้ที่ล็อกอิน |
| `CreateKitchenStation` | command | `POST /catalog/kitchen-stations` | เจ้าของ |
| `UpdateKitchenStation` | command | `PATCH /catalog/kitchen-stations/:id` (ชื่อ ลำดับ เปิดปิด) | เจ้าของ |
| `SetCategoryStation` | command | `PUT /catalog/categories/:id/kitchen-station` `{ stationId }` (`null` = ไม่ส่งครัว) | เจ้าของ |
| `ListKitchenTickets` | query | `GET /kitchen/tickets?stationId=&status=pending&limit&offset` คืน `{items,total}` | ผู้ใช้ที่ล็อกอิน |
| `MarkKitchenTicketDone` | command | `POST /kitchen/tickets/:id/done` | ผู้ใช้ที่ล็อกอิน |
| `SendOrderToKitchen` | command | `POST /orders/:id/kitchen-send` คืนใบที่สร้าง | ผู้ใช้ที่ล็อกอิน |
| `SetOrderLineNote` | command | `PATCH /orders/:id/lines/:lineId/note` `{ note }` | ผู้ใช้ที่ล็อกอิน |

- `GET /orders/:id` และรายการออเดอร์เพิ่มช่อง `note` และ `sentQuantity` (ส่งแล้วสุทธิ) ต่อบรรทัด
- เส้นทางตั้งค่าร้านเดิมรับ `homeView` เพิ่ม การผูกหมวดกับสถานีใช้ `PUT .../kitchen-station` ไม่แก้ `PATCH /catalog/categories/:id`
- v1 เพิ่มอย่างเดียว ไม่เปลี่ยนสัญญาเดิม
- baseline OpenAPI ต้องบันทึกใหม่ (เพิ่มอย่างเดียว) โดยแจ้งเจ้าของโครงการก่อน

**ขอบเขตโมดูล (hexagonal)**

- `SendOrderToKitchen`, `MarkKitchenTicketDone`, `ListKitchenTickets` อยู่ในโมดูล `kitchen` แต่ละ use case เป็นไฟล์เดียว
- `SendOrderToKitchen` อ่านและล็อกออเดอร์ผ่านพอร์ต `IOrderRepository` ของ orders และอ่านหมวดของสินค้าผ่านพอร์ตของ products ห้ามแตะตาราง `orders`, `order_items`, `categories`, `products` ตรง
- การแก้ออเดอร์ (ลด ลบ ยกเลิก รวม) เรียกพอร์ต `IKitchenTicketWriter` ที่โมดูล kitchen implement ผ่าน token ใน `modules/tokens.ts` ไม่เรียก adapter ของ kitchen ตรง
- ออเดอร์ตอบ `sentQuantity` ผ่านพอร์ต `IKitchenSentQuantities` ของ kitchen (อ่านอย่างเดียว)
- สถานีและการผูกหมวดอยู่ในโมดูล kitchen ไม่ได้เพิ่มคอลัมน์ `station_id` ในตาราง `categories` เพราะทำให้โมดูล categories รู้เรื่องครัว

## เว็บ

- feature ใหม่ `kitchen`
  - หน้า `/kitchen`: เลือกสถานี (เก็บใน query string `?station=`) แสดงใบค้างเป็นการ์ด เรียงจากเก่าไปใหม่ บรรทัดที่ยกเลิกขีดฆ่าและเขียนว่า "ยกเลิก N" ปุ่มทำเสร็จสูง 44px ดึงข้อมูลทุก 3 วินาทีผ่าน `kitchenKeys` และ `refetchInterval`
  - หน้า `/kitchen-stations` (เจ้าของ): จัดการสถานี และเลือกสถานีให้แต่ละหมวด
  - ฟังก์ชันล้วนใน `lib/` (`groupByStation`, `ticketSummary`) พร้อมไฟล์ทดสอบข้างกัน
- `pos` (ตะกร้าของออเดอร์ที่เปิดอยู่): ปุ่ม **ส่งครัว (N)** แสดงจำนวนรายการที่ยังไม่ส่ง ช่องหมายเหตุต่อบรรทัด และป้าย "ส่งแล้ว N" ตามค่า `sentQuantity`
- `orders`: mutation ของคำสั่งใหม่ผ่าน `features/orders/api.ts` ตัวเดียว
- `settings`: ตัวเลือก "หน้าแรก" (หน้าขาย / ผังโต๊ะ) ค่าเริ่มต้นหน้าขาย
- `tables`: export คอมโพเนนต์ผังโต๊ะแบบอ่านอย่างเดียวให้ `app/App.tsx` ใช้เป็นหน้าแรกเมื่อ `homeView = tables` แตะโต๊ะเปิดออเดอร์ได้ตามเดิม
- `categories`: ช่องเลือกสถานีในฟอร์มหมวดหมู่ (ใช้ `kitchenKeys` จาก `features/kitchen/index.ts`)
- ข้อความทั้งหมดผ่าน `t()` ไทยและอังกฤษ ตามสถานะของ `features/<name>/locales.ts`

**design รอบ 2**

- หน้าแรกเป็นผังโต๊ะเมื่อเลือก `tables` (ดูด้านบน)
- ฟอร์มยาวใน dialog ประมาณเก้าตัว: ปุ่มยืนยันอยู่นอกพื้นที่เลื่อนของฟอร์ม โดยโครงเป็น `<form>` ที่ `flex-col` มีพื้นที่เนื้อหาเลื่อนได้เป็นลูกชั้นแรก และแถวปุ่มเป็นลูกอีกชั้นที่ไม่อยู่ในพื้นที่เลื่อน ทำให้ปุ่มติดล่างของ dialog เสมอ ไม่ใช้ `sticky` ภายในฟอร์ม (ตาม AGENTS.md) รายการฟอร์มที่แก้จะไล่ในแผนงาน
- ทุกหน้าใหม่ใช้ได้ที่ 390, 768 และ 1366px ตาม `DESIGN.md`

## นอกขอบเขต

เสียงแจ้งเตือนและ push แบบทันที, เวลาทำอาหารและการแจ้งเกินเวลา, การส่งทีละคอร์ส, พิมพ์ใบสั่งออกเครื่องพิมพ์ครัว, การตัดวัตถุดิบหรือสูตรอาหาร, การแยกจำนวนที่ส่งแล้วระหว่างออเดอร์, การย้ายใบค้างไปสถานีอื่น, ใบสั่งย้อนหลังแก้ไขได้

## คำถามเปิดสำหรับการรีวิว

ผมเลือกค่าเริ่มต้นไว้ก่อน ถ้าไม่เห็นด้วยบอกได้:

1. **แยกบิลรายการที่ส่งแล้วไม่ได้** เป็นข้อจำกัดที่กระทบมากที่สุด ถ้าต้องการให้แยกได้ ต้องเพิ่มการแยกจำนวนที่ส่งแล้วระหว่างออเดอร์
2. **รวมและแยกถูกบล็อกเมื่อมีใบค้าง** แคชเชียร์ต้องรอให้ครัวกดเสร็จก่อน
3. **หมายเหตุแก้ไม่ได้หลังส่ง** เพื่อให้จอครัวตรงกับที่ส่ง
4. **หน้าแรกของร้านเดิมเป็นหน้าขาย** และร้านต้องเปลี่ยนเองในการตั้งค่า

## การทดสอบ

- unit: entity, ฟังก์ชันล้วนของการนับและการยกเลิก, use case ทุกคำสั่งครอบคลุมทุกกรณีที่ถูกปฏิเสธ (`bun run test:unit`)
- integration: `src/__tests__/integration/kitchen.integration.test.ts` กับ PostgreSQL จริง รวมกรณีกดส่งสองครั้งพร้อมกัน และการลดหลังส่ง
- web: ฟังก์ชันล้วนพร้อมไฟล์ทดสอบข้างกัน (`bun run test`)
- e2e: ครอบคลุมส่งครัว ครัวกดเสร็จ การยกเลิกขึ้นบนจอ ตั้งหน้าแรกเป็นผังโต๊ะ และภาพหน้าจอที่ 390, 768, 1366px

## เสร็จเมื่อ

- แคชเชียร์ส่งรายการเป็นรอบ ครัวเห็นใบบนจอสถานีของตัวเองภายใน 3 วินาที และกดทำเสร็จได้
- ลดหรือยกเลิกรายการหลังส่ง จอครัวขึ้นว่ายกเลิกโดยไม่ต้องรีเฟรช และส่งซ้ำได้เฉพาะจำนวนที่ยังไม่ส่ง
- ออเดอร์ที่ชำระแล้วยังมีใบค้างบนจอจนครัวกดเสร็จ
- รวมและแยกทำตามกติกาในตารางการตัดสินใจ และออเดอร์ของสาขาอื่นถูกปฏิเสธ
- `typecheck`, `test`, `lint`, `openapi:check` (หลังได้รับอนุมัติให้บันทึก baseline) และ `e2e` ผ่าน
