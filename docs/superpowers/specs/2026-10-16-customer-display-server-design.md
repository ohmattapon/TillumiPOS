# จอลูกค้าผ่านเซิร์ฟเวอร์ — แบบออกแบบ

สถานะ: ร่างสำหรับตรวจ · ต่อจาก `specs/2026-10-14-customer-display-design.md` · branch `ohmattpon/customer-display-server` (แตกจาก `main`)

## 1. เป้าหมาย

จอลูกค้ารุ่นแรกส่งข้อมูลด้วย `BroadcastChannel` จึงใช้ได้เฉพาะเบราว์เซอร์และโปรไฟล์เดียวกับหน้าขาย งานนี้ให้จอลูกค้าเป็นเครื่องอื่นได้ (แท็บเล็ต จอของคอมอีกเครื่อง มือถือ) โดยส่งสถานะการขายผ่านเซิร์ฟเวอร์

ขอบเขตที่ผู้ใช้เลือกแล้ว:

| เรื่อง | ที่เลือก |
|---|---|
| การส่งไปจอ | SSE (Server-Sent Events) เซิร์ฟเวอร์ส่งทางเดียว |
| การจับคู่ | รหัส 6 หลัก ต่อเครื่องขาย |
| ของเดิม | คงการส่งแบบเบราว์เซอร์เดียวกันไว้เป็นทางสำรอง |

ไม่อยู่ในงานนี้: จอที่มีรายการสินค้าให้ลูกค้ากดเอง (ทางเดียวเท่านั้น) โฆษณาหรือสไลด์ตอนว่าง หลายเซิร์ฟเวอร์พร้อมกัน

## 2. ภาพรวมการทำงาน

1. เปิด `/customer` บนอุปกรณ์ใดก็ได้ จอขอ session จากเซิร์ฟเวอร์และแสดง **รหัสจับคู่ 6 หลัก**
2. แคชเชียร์กรอกรหัสนั้นที่หน้าขาย (เมนู "จอลูกค้า") เซิร์ฟเวอร์ผูก session ของจอเข้ากับเครื่องขายของแคชเชียร์
3. หน้าขายส่งสถานะ (ว่าง กำลังขาย ชำระเงิน ชำระแล้ว) ไปที่เซิร์ฟเวอร์ทุกครั้งที่เปลี่ยน เซิร์ฟเวอร์เก็บสถานะล่าสุดไว้และส่งต่อให้จอทุกจอที่ผูกกับเครื่องขายนั้นทาง SSE
4. จอที่เพิ่งเปิดหรือต่อใหม่ได้สถานะล่าสุดทันที ไม่ต้องรอให้หน้าขายส่งอีก

เครื่องขายคือ `register` ในโหมดกะ ถ้าร้านอยู่ในโหมดเดิมที่ไม่มีเครื่องขาย ใช้สาขาแทน (หนึ่งสาขาหนึ่งจอชุดเดียว) ในเอกสารนี้เรียกรวมว่า **เป้าหมายของจอ** (`displayTarget`)

## 3. สัญญา API

ทุกเส้นทางอยู่ใต้ `/api/v1` เป็นการเพิ่มอย่างเดียว

| เส้นทาง | ชนิด | สิทธิ์ | หน้าที่ |
|---|---|---|---|
| `POST /customer-display/sessions` | command | ไม่ต้องล็อกอิน (จำกัดอัตรา) | จอขอ session คืน `{ sessionId, token, code, expiresAt }` |
| `GET /customer-display/stream?token=` | query (SSE) | ถือ token ของ session | จอรับเหตุการณ์ `waiting`, `paired`, `state`, `unpaired` พร้อม heartbeat |
| `POST /customer-display/pair` | command | เจ้าของ/แคชเชียร์ | `{ code, registerId? }` ผูก session กับเป้าหมาย |
| `PUT /customer-display/state` | command | เจ้าของ/แคชเชียร์ | หน้าขายส่งสถานะล่าสุด `{ registerId?, envelope }` |
| `DELETE /customer-display/pair` | command | เจ้าของ/แคชเชียร์ | `{ registerId? }` ถอดจอทั้งหมดของเป้าหมาย |
| `GET /customer-display/pair` | query | เจ้าของ/แคชเชียร์ | จำนวนจอที่ผูกอยู่กับเป้าหมายนี้ ให้หน้าขายแสดง "เชื่อมต่อแล้ว" |

`token` ใน query ของ SSE เป็นความจำเป็นของ `EventSource` ที่ตั้ง header เองไม่ได้ ตัวมันอ่านได้เฉพาะสตรีมของ session นั้น และถูกเพิกถอนทันทีที่ถอดจอหรือ session หมดอายุ

`envelope` ใช้รูปเดียวกับของเดิมในเว็บ (`v`, `seq`, `at`, `locale`, `currency`, `shopName`, `state`) เซิร์ฟเวอร์ตรวจรูปด้วย schema และไม่เชื่อตัวเลขเงินที่ไม่ใช่จำนวนเต็มสตางค์

## 4. สถาปัตยกรรม (Hexagonal + CQRS)

โมดูลใหม่ `apps/api/src/modules/customer-display`:

| ชั้น | สิ่งที่มี |
|---|---|
| `domains/` | `display-session.domain.ts`: session และสถานะ (`waiting` → `paired` → `ended`), รหัส 6 หลัก, กติกาหมดอายุ, ห้ามผูกซ้ำ |
| `applications/ports` | `IDisplaySessionStore` (เก็บ session และสถานะล่าสุด), `IDisplayStream` (ส่งเหตุการณ์ให้จอ), `IPairingCodeGenerator`, `IClock` ที่มีอยู่ |
| `applications/usecases` | `StartDisplaySessionUseCase` (command), `PairDisplayUseCase` (command), `PublishDisplayStateUseCase` (command), `UnpairDisplayUseCase` (command), `GetDisplayPairingUseCase` (query), `OpenDisplayStreamUseCase` (query) |
| `adapters/controllers` | `customer-display.controller.ts` (Elysia, SSE ด้วย generator response) |
| `adapters` | `in-memory-display-hub.ts` ทำทั้ง store และ stream ในหน่วยความจำของโปรเซส |

กฎ:
- สถานะการขายไม่ใช่ข้อมูลของร้านที่ต้องคงอยู่ จึง **ไม่ลงฐานข้อมูล** เก็บในหน่วยความจำเท่านั้น รีสตาร์ตเซิร์ฟเวอร์จอจะต่อ SSE ใหม่เองและรอสถานะถัดไปจากหน้าขาย
- ข้อมูลที่ส่งมีเท่าที่อยู่บนใบเสร็จ ห้ามเพิ่มช่องข้อมูลภายในลง `envelope`
- ถ้าต้องมีหลายเซิร์ฟเวอร์ ให้เปลี่ยน adapter เป็น Redis pub/sub โดยไม่แตะ use case (Redis เป็นตัวเลือกอยู่แล้วใน `shared/adapters`)

## 5. ความปลอดภัย

- รหัสจับคู่ 6 หลักสุ่ม ใช้ได้ครั้งเดียว หมดอายุ 10 นาที ถ้ายังไม่ถูกผูก
- กรอกรหัสผิดเกิน 5 ครั้งต่อผู้ใช้ล็อก 15 นาที (แบบเดียวกับรหัสตั้งค่าครั้งแรก)
- `POST /sessions` จำกัดจำนวน session ที่รอผูกพร้อมกันทั้งระบบ (`MAX_WAITING_SESSIONS` = 200) กันการสร้างจำนวนมาก ไม่จำกัดต่อ IP เพราะร้านหลายเครื่องอยู่หลังเราเตอร์เดียวกัน
- เป้าหมายของจอต้องอยู่ในสาขาของผู้กด (ผ่าน `branch()` ของ `auth`) สาขาอื่นตอบว่าไม่พบ
- จอที่ผูกแล้วไม่เห็นอะไรนอกจากสถานะของเป้าหมายตัวเอง ไม่เรียก API อื่น และไม่มีทางเข้าถึงข้อมูลของร้าน
- สถานะ `paying` มีรูป QR ซึ่งเป็นข้อมูลที่ลูกค้าต้องเห็นอยู่แล้ว ไม่เก็บลงดิสก์และไม่เขียนลง log

## 6. ฝั่งเว็บ

- `DisplayChannel` ที่มีอยู่เป็น interface (`post`, `subscribe`, `close`) จึงเพิ่ม `openServerChannel()` ที่ส่งด้วย `PUT /state` และรับด้วย `EventSource` โดยไม่ต้องแก้ตัวแปลงสถานะหรือหน้าจอ
- หน้า `/customer`:
  - ยังไม่ผูก: แสดงรหัสจับคู่ใหญ่และข้อความสั้น "ให้พนักงานกรอกรหัสนี้ที่หน้าขาย"
  - ผูกแล้ว: แสดงสถานะการขายเหมือนเดิม
  - ถ้าได้รับข้อความทางเบราว์เซอร์เดียวกัน (ของเดิม) ก็แสดงต่อได้ โดยทางที่ใหม่กว่าชนะตามลำดับ `seq`
- หน้าขาย เมนู "จอลูกค้า": เพิ่มรายการ "เชื่อมต่อจอ" เปิด dialog กรอกรหัส 6 หลัก แสดงสถานะ "เชื่อมต่อแล้ว (n จอ)" และปุ่ม "ถอดจอ" รายการเดิมที่เปิดหน้าต่างใน เบราว์เซอร์เดียวกันยังอยู่
- หน้าขายส่งสถานะทั้งสองทางเมื่อมีจอผูกอยู่ ถ้าส่งทางเซิร์ฟเวอร์ไม่สำเร็จ ลองใหม่เบื้องหลังโดยไม่ขวางการขาย และไม่แสดงข้อผิดพลาดต่อลูกค้า
- ข้อความทั้งหมดผ่าน `t()` (th/en) ไม่มีสีหรือรูปแบบใหม่ ใช้ token เดิมของ DESIGN.md

## 7. ข้อจำกัดที่ยอมรับ

- เซิร์ฟเวอร์ทำงานเดียวเท่านั้น (ตามชุดติดตั้งปัจจุบัน) และสถานะหายเมื่อรีสตาร์ต
- จอต้องเข้าถึงเซิร์ฟเวอร์ได้ในเครือข่ายเดียวกับหน้าขาย หรือผ่านโดเมนเดียวกัน
- SSE ผ่านพร็อกซีที่ buffer ไว้อาจช้า Caddy ที่ใช้อยู่ปิดการ buffer ให้ `text/event-stream` อยู่แล้ว ต้องตรวจในการลองติดตั้ง
- หนึ่งเป้าหมายมีได้หลายจอ ทุกจอเห็นเหมือนกัน

## 8. การทดสอบและเกณฑ์ยอมรับ

- entity: รหัสหมดอายุ ใช้ครั้งเดียว ห้ามผูกซ้ำ ผิดเกิน 5 ครั้งถูกล็อก
- use case: ทดสอบกับ port จำลองจาก `__tests__/mocks.ts` ทุกกรณีสำเร็จและถูกปฏิเสธ รวมสาขาอื่นตอบไม่พบ
- adapter ในหน่วยความจำ: ผู้ติดตามหลายจอได้สถานะเดียวกัน จอที่ต่อทีหลังได้สถานะล่าสุด ถอดจอแล้วสตรีมปิด
- HTTP กับ PostgreSQL จริง: ลำดับเต็ม สร้าง session → ผูก → ส่งสถานะ → อ่านสตรีมได้ → ถอดจอ และกรณีรหัสผิด
- เว็บ: ตัวแปลงที่เลือกทางส่ง (ทางใหม่กว่าชนะตาม `seq`) เป็นฟังก์ชันล้วนพร้อมเทสต์
- e2e: สองบริบทเบราว์เซอร์ที่ไม่ใช้ BroadcastChannel ร่วมกัน จอเห็นรายการที่หน้าขายเพิ่ม
- OpenAPI baseline เพิ่มเส้นทางใหม่ ตรวจว่าเพิ่มอย่างเดียว และต้องแจ้งเจ้าของก่อนบันทึก baseline ใหม่
- `typecheck`, `lint`, `test` และ `openapi:check` ผ่านก่อนจบงาน

## 9. ลำดับการทำ

1. entity และกฎการจับคู่ พร้อมเทสต์
2. ports, use case และ adapter ในหน่วยความจำ พร้อมเทสต์
3. controller (รวม SSE), ลงทะเบียน DI, OpenAPI และเทสต์ HTTP
4. `openServerChannel()` และตัวเลือกทางส่งในเว็บ พร้อมเทสต์
5. หน้า `/customer` (แสดงรหัส) และ dialog กรอกรหัสที่หน้าขาย
6. e2e, ภาพหน้าจอ, เอกสารใน `AGENTS.md` และ `docs/summary.md`
