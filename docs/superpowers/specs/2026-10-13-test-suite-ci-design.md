# ชุดทดสอบอัตโนมัติและ CI: เอกสารออกแบบ

- วันที่: 2026-10-13
- ชิ้นงานที่ 1 ใน `docs/superpowers/roadmap.md`
- สถานะ: อนุมัติให้ลงมือ พร้อมข้อปรับปรุงจาก review

## เป้าหมาย

ทุกครั้งที่แก้โค้ดส่วนเงิน สต็อก หรือสิทธิ์ มีคำสั่งเดียวที่บอกได้ว่าพฤติกรรมเดิมยังถูกต้อง ทั้งในเครื่องผู้พัฒนาและบน GitHub ชิ้นงานถัดไปในแผน (ตั้งค่าร้าน สาขา ออเดอร์ค้าง) แก้โค้ดส่วนเหล่านี้ทั้งหมด จึงต้องมีชุดทดสอบนี้ก่อน

## สิ่งที่อยู่นอกขอบเขต

- ทดสอบหน้าเว็บผ่านเบราว์เซอร์อัตโนมัติ
- ทดสอบ Worker ใน `apps/media` (ทดสอบเฉพาะฝั่ง API ที่เรียกมัน โดยใช้ตัวจำลอง)
- วัดความครอบคลุมของโค้ดเป็นตัวเลข และทดสอบประสิทธิภาพ
- แก้พฤติกรรมของระบบ ถ้าการทดสอบเจอบั๊ก ให้บันทึกและแก้เป็นงานแยก ยกเว้นบั๊กที่ทำให้เขียนการทดสอบไม่ได้

## แนวทาง

ทดสอบแบบ integration กับ PostgreSQL จริง โดยเรียก API ผ่าน HTTP

แนวทางที่ไม่เลือก:

- ฐานข้อมูลจำลองในหน่วยความจำ (PGlite): ใช้ไดรเวอร์คนละตัวกับของจริง และทดสอบการล็อกแถวตอนขายพร้อมกันไม่ได้
- จำลองชั้นฐานข้อมูล: ไม่ได้ทดสอบ SQL และ transaction ซึ่งเป็นจุดเสี่ยงที่สุด

## โครงสร้าง

### ฐานข้อมูลทดสอบ

- ใช้ PostgreSQL ตัวเดียวกับตอนพัฒนา (container `db` ใน `docker-compose.yml`, พอร์ต 5433) แต่แยกฐานข้อมูลชื่อ `pos_test` ข้อมูลพัฒนาในฐานข้อมูล `pos` ต้องไม่ถูกแตะ
- ก่อนการทดสอบแรก ระบบสร้าง `pos_test` ถ้ายังไม่มี แล้วรัน migration ทั้งหมดจาก `apps/api/drizzle`
- ก่อนแต่ละกรณีทดสอบ ล้างทุกตารางและรีเซ็ตเลขลำดับ เพื่อให้แต่ละกรณีไม่ขึ้นกับกรณีอื่น
- ตัวป้องกัน: ปฏิเสธ URL ที่ไม่ใช่ `pos_test` บน `localhost:5433` แบบตรงตัว ก่อน truncate ต้องตรวจ `current_database()` บน cached client จริงว่าเป็น `pos_test` แม้ mutable env ถูกแก้ให้ดูถูกต้อง

### การตั้งค่า

- ไฟล์ `apps/api/.env.test` เก็บค่าสำหรับทดสอบ และ commit เข้า repo ได้ เพราะมีแต่ค่าในเครื่องที่ไม่ใช่ความลับ (`bun --env-file=.env.test test` โหลดไฟล์นี้อย่างชัดเจน และ `bunfig.toml` ปิดการโหลด `.env` อัตโนมัติ)
- ค่าในไฟล์: `DATABASE_URL` ชี้ `pos_test`, `JWT_SECRET` ค่าทดสอบ, `MEDIA_TOKEN` ค่าทดสอบ, `VAT_RATE_BP=700`
- `MEDIA_URL` ไม่อยู่ในไฟล์ ขั้นตอนเตรียมตั้งให้ชี้ตัวจำลองที่เก็บรูปก่อนโหลดแอป

### ตัวจำลองที่เก็บรูป

เซิร์ฟเวอร์ HTTP ในหน่วยความจำ เปิดบนพอร์ตสุ่ม ทำตามสัญญาเดียวกับ Worker ใน `apps/media`:

- `PUT /<key>` ต้องมี `Authorization: Bearer <MEDIA_TOKEN>` เก็บไฟล์ ตอบ 201
- `GET /<key>` ตอบไฟล์ หรือ 404
- `DELETE /<key>` ต้องมี token ลบไฟล์ ตอบ 204

การทดสอบต้องไม่ส่งคำขอใดไปยัง Cloudflare

### วิธีเรียก API

- เปิดแอปบนพอร์ตสุ่มหนึ่งครั้งต่อการรัน แล้วเรียกผ่าน Eden client แบบมี type (`treaty<App>`) ตัวเดียวกับที่หน้าเว็บใช้ การเปลี่ยนสัญญา API ที่ทำให้หน้าเว็บพังจะทำให้การทดสอบ compile ไม่ผ่านด้วย
- ตัวช่วยสำหรับเตรียมข้อมูล: สร้างผู้ใช้ตามบทบาทแล้วล็อกอินเป็น client ที่ถือ cookie, สร้างหมวดหมู่, สร้างสินค้าพร้อมสต็อกตั้งต้น
- ตัวช่วยเตรียมข้อมูลเรียกผ่าน service ของแต่ละโมดูล ยกเว้น test fixture ขอบเวลา: อนุญาต SQL หลัง guard เพื่อกำหนด timestamp ตรงมิลลิวินาทีที่แน่นอน ห้ามบันทึกการปัด microseconds เป็น production bug หรือ `test.failing`

### ตำแหน่งไฟล์

- โครงทดสอบร่วม: `apps/api/test/` (เตรียมฐานข้อมูล, ตัวจำลองที่เก็บรูป, ตัวช่วยเตรียมข้อมูล)
- การทดสอบของแต่ละโมดูลอยู่ข้างโค้ดของโมดูลนั้น ตามแบบของ `sales/pricing.test.ts` ที่มีอยู่ เช่น `modules/sales/sales.test.ts`
- การทดสอบ unit เดิมของ `pricing.ts` คงไว้ตามเดิม

## พฤติกรรมที่ต้องทดสอบ

จำนวนเงินทั้งหมดเป็นสตางค์ อัตรา VAT ในการทดสอบคือ 7% แบบรวมในราคา

### ล็อกอินและสิทธิ์

1. ล็อกอินถูกต้องได้ cookie และ `GET /auth/me` คืนผู้ใช้ที่ไม่มีรหัสผ่านปน
2. รหัสผ่านผิด หรือไม่มีผู้ใช้ ตอบ 401 ด้วยข้อความเดียวกัน
3. เรียกเส้นทางที่ต้องล็อกอินโดยไม่มี cookie ตอบ 401
4. แคชเชียร์เรียกเส้นทางของเจ้าของร้านตอบ 403: จัดการผู้ใช้ เพิ่มหรือแก้สินค้า รับเข้าและปรับสต็อก ยกเลิกบิล สรุปยอดขาย และอัปโหลดรูป
5. ผู้ใช้ที่ถูกปิดการใช้งานล็อกอินไม่ได้ และ cookie ที่ได้ไว้ก่อนหน้าใช้ไม่ได้ทันที
6. ปิดการใช้งานหรือลดสิทธิ์เจ้าของร้านคนสุดท้ายตอบ 409

### สินค้า

7. สร้างสินค้าแล้วค้นด้วยชื่อ SKU และบาร์โค้ดเจอ
8. SKU หรือบาร์โค้ดซ้ำตอบ 409
9. สินค้าที่ปิดการขายไม่อยู่ในรายการปกติ แต่อยู่เมื่อขอรวมที่ปิดการขาย
10. คำค้นที่มีอักขระ `%` และ `_` ถูกตีความเป็นตัวอักษร ไม่ใช่ wildcard

### สต็อก

11. รับเข้าเพิ่มยอดคงเหลือ และบันทึกรายการเคลื่อนไหวพร้อมยอดหลังรับ
12. ปรับยอดบันทึกส่วนต่างที่มีเครื่องหมาย และยอดคงเหลือเท่ากับจำนวนที่นับได้
13. ปรับยอดเป็นจำนวนเท่าเดิมตอบ 400
14. รับเข้าหรือปรับยอดสินค้าที่ไม่นับสต็อกตอบ 400

### การขาย

15. ขายสำเร็จ: ยอดรวม ส่วนลด ยอดสุทธิ VAT ยอดรับ และเงินทอนถูกต้อง สต็อกลดตามจำนวน และมีรายการเคลื่อนไหวประเภทขายที่อ้างเลขใบเสร็จ
16. สินค้าเดียวกันที่ส่งมาหลายบรรทัดถูกรวมเป็นบรรทัดเดียว
17. บิลเก็บชื่อและราคา ณ เวลาขาย: แก้ชื่อและราคาสินค้าหลังขายแล้ว บิลเดิมไม่เปลี่ยน
18. เลขใบเสร็จของวันเดียวกันเรียงต่อเนื่องไม่ข้าม รวมถึงเมื่อมีการขายที่ล้มเหลวคั่นกลาง
19. สต็อกไม่พอตอบ 409 และสต็อกกับเลขใบเสร็จไม่เปลี่ยน
20. สินค้าที่ไม่นับสต็อกขายได้ไม่จำกัดจำนวน และไม่มีรายการเคลื่อนไหว
21. ขายสินค้าที่ปิดการขายตอบ 409 และขายสินค้าที่ไม่มีอยู่ตอบ 400 ทั้งสองกรณีสต็อกและเลขใบเสร็จไม่เปลี่ยน
22. ชำระไม่ครบตอบ 400 และชำระเกินด้วยช่องทางที่ไม่ใช่เงินสดตอบ 400
23. ส่วนลดมากกว่ายอดรวมตอบ 400
24. ชำระหลายช่องทางที่รวมกันพอดียอดสำเร็จ
25. ขายพร้อมกัน: ส่ง 20 คำขอพร้อมกัน คำขอละ 5 ชิ้น กับสต็อก 48 ชิ้น ต้องสำเร็จ 9 คำขอ ที่เหลือตอบ 409 สต็อกคงเหลือ 3 และเลขใบเสร็จไม่ซ้ำ

### ยกเลิกบิล

26. ยกเลิกแล้วสถานะเปลี่ยน สต็อกคืนครบ และมีรายการเคลื่อนไหวประเภทยกเลิก
27. ยกเลิกบิลเดิมซ้ำตอบ 409 และสต็อกไม่คืนซ้ำ
28. บิลที่ยกเลิกไม่ถูกนับในสรุปยอดขาย

### สรุปยอดขาย

29. จำนวนบิล ยอดขาย VAT ส่วนลด และกำไรขั้นต้นตรงกับบิลในช่วงเวลา
30. ยอดเงินสดในสรุปหักเงินทอนแล้ว
31. บิลนอกช่วงเวลาไม่ถูกนับ

### รูปสินค้า

32. อัปโหลดแล้วสินค้ามี `imageUrl` และไฟล์อยู่ในตัวจำลอง
33. อัปโหลดทับแล้วไฟล์เก่าถูกลบจากตัวจำลอง
34. ลบรูปแล้ว `imageUrl` เป็นค่าว่าง และไฟล์ถูกลบ
35. ไฟล์ที่เนื้อหาไม่ใช่รูปตอบ 422 แม้ประกาศชนิดเป็นรูป
36. เมื่อที่เก็บรูปใช้ไม่ได้ การอัปโหลดตอบ 502 และสินค้าไม่เปลี่ยน

## คำสั่งและ CI

- `bun run test` ที่ root รันการทดสอบทั้งหมดของ API ต้องเปิดฐานข้อมูลด้วย `bun run db:up` ก่อน ถ้าต่อฐานข้อมูลไม่ได้ ต้องแจ้งข้อความที่บอกให้รันคำสั่งนี้ ไม่ใช่ค้างหรือแสดง stack trace ยาว
- เพิ่ม `bun run lint` ที่ root
- GitHub Actions ไฟล์เดียว รันเมื่อ push เข้า branch หลักและเมื่อเปิดหรืออัปเดต pull request:
  1. ติดตั้งด้วย `bun install --frozen-lockfile`
  2. typecheck ทุกแพ็กเกจ
  3. lint
  4. ทดสอบกับ PostgreSQL 17 ที่เปิดเป็น service ของ job บนพอร์ต 5433 เพื่อใช้ `.env.test` เดียวกับในเครื่อง
- CI ไม่ใช้ความลับใด ๆ และไม่เรียก Cloudflare

## เกณฑ์ว่าเสร็จ

- พฤติกรรมทั้ง 36 ข้อมีการทดสอบ และผ่านทั้งหมดในเครื่อง
- รันชุดทดสอบซ้ำสองรอบติดกันได้ผลเหมือนกัน
- SHA256 fingerprint ของ schema, data ทุกตาราง และ sequence values ใน `pos` ตรงกับ baseline ที่บันทึกก่อนเริ่ม ไม่ใช้จำนวนแถวเก่าของบางตาราง
- จำลอง CI จาก clean checkout ของ committed HEAD พร้อม frozen install ใหม่ คัดลอกเฉพาะ `.dev.vars.example` ไม่ใช้ ignored `.env` หรือ node_modules เดิม
- ทดลองทำให้โค้ดผิดหนึ่งจุด (ตัดการล็อกแถวออกจากการขาย) แล้วข้อ 25 ต้องล้มเหลว จากนั้นคืนโค้ดเดิม
- CI ผ่านบน GitHub อย่างน้อยหนึ่งครั้ง ซึ่งต้อง push โดยเจ้าของโครงการ

## ความเสี่ยงที่รู้อยู่

- ข้อ 25 ขึ้นกับจังหวะเวลา ถ้าผลไม่คงที่ ให้ตรวจที่ผลรวม (จำนวนที่สำเร็จ สต็อกคงเหลือ และเลขใบเสร็จไม่ซ้ำ) ซึ่งต้องคงที่เสมอไม่ว่าคำขอใดชนะ
- ข้อ 18 ขึ้นกับวันที่ ถ้ารันคร่อมเที่ยงคืนตามเขตเวลาร้าน เลขจะเริ่มใหม่ การทดสอบต้องเทียบเฉพาะบิลที่มีส่วนวันที่ของเลขใบเสร็จตรงกัน
