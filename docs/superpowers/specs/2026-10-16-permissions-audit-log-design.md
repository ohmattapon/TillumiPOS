# สิทธิ์ละเอียดและบันทึกการกระทำ

วันที่: 2026-10-16 สถานะ: รอเจ้าของโครงการรีวิว ชิ้นงานที่ 12 ใน `roadmap.md`

## เป้าหมาย

เจ้าของร้านกำหนดได้ว่าใครทำอะไรได้ (ยกเลิกบิล ปรับสต็อก แก้ราคา ดูรายงาน ฯลฯ) ด้วยบทบาทที่ตั้งเองได้ และย้อนดูได้ว่าใครทำอะไรกับเงิน สต็อก และสิทธิ์ เมื่อไร ที่สาขาไหน ค่าก่อนและหลังคืออะไร

เกณฑ์ว่าเสร็จ:

- เจ้าของสร้างบทบาท (เช่น "ผู้จัดการ") ติ๊กสิทธิ์ แล้วกำหนดให้ผู้ใช้ได้ และสิทธิ์มีผลทันทีโดยผู้ใช้ไม่ต้องล็อกอินใหม่
- หลังอัปเกรด ผู้ใช้เดิมทุกคนทำได้เท่าที่เคยทำได้ ไม่มากไม่น้อยกว่าเดิม
- การกระทำสำคัญทุกตัวในรายการข้างล่างมีแถวใน `audit_logs` ที่เขียนในธุรกรรมเดียวกับการกระทำนั้น
- API ปฏิเสธการกระทำที่ไม่มีสิทธิ์เองทุกจุด เว็บซ่อนปุ่มเป็นแค่ความสะดวก

## ขอบเขต

ทำ: สิทธิ์ราย function, บทบาทที่ตั้งเอง (หนึ่งผู้ใช้หนึ่งบทบาท), audit log แบบเขียนอย่างเดียว, หน้าเว็บจัดการบทบาทและดูประวัติ

ไม่ทำ (รอบนี้): สิทธิ์ต่อสาขา, หลายบทบาทต่อคน, log ทุกคำสั่งที่เปลี่ยนข้อมูล, เก็บ log ตามอายุหรือส่งออก, รหัสผู้จัดการอนุมัติหน้าเครื่อง

## 1. สิทธิ์ (permission)

รายการสิทธิ์ตายตัวอยู่ในโค้ดที่ `domains/permission.vo.ts` (ไม่มี zod หรือ framework) การขายปกติ (เปิดบิล รับชำระ ออเดอร์ โต๊ะ ครัว กะของตัวเอง) ใช้ `auth: true` เหมือนเดิมและไม่ต้องมีสิทธิ์พิเศษ สิทธิ์ครอบเฉพาะสิ่งที่วันนี้จำกัดไว้ให้เจ้าของ

| สิทธิ์ | ครอบคลุม (เส้นทางเดิมที่เป็น `auth: ['owner']`) |
|---|---|
| `sales.void` | ยกเลิกบิล (v1, v2), บันทึกคืนเงินสด |
| `qr.dismiss` | ปิดรายการ QR ที่จ่ายแล้วแต่ไม่มีบิล |
| `reports.read` | สรุปยอดขาย รายงานย้อนหลัง สินค้าขายดี เปรียบเทียบสาขา ส่งออก |
| `products.write` | เพิ่ม/แก้สินค้า อัปโหลด/ลบรูป |
| `categories.write` | เพิ่ม/แก้หมวดหมู่ |
| `modifiers.write` | กลุ่มตัวเลือก ตัวเลือก และการผูกกับสินค้า |
| `promotions.write` | สร้าง/แก้/เปิดปิดโปรโมชัน |
| `members.write` | แก้ไขสมาชิกและสถานะ (เพิ่มสมาชิกยังเป็น `auth: true`) |
| `inventory.receive` | รับสินค้าเข้าสต็อก |
| `inventory.adjust` | ปรับยอดสต็อกให้ตรงกับที่นับ |
| `tables.write` | เพิ่ม/แก้/ปิดโต๊ะ |
| `kitchen.write` | สถานีครัวและการผูกหมวดกับสถานี |
| `registers.manage` | จุดขาย (register) |
| `branches.manage` | เพิ่ม/แก้/ปิดสาขา |
| `branches.switch` | เลือกทำงานในสาขาอื่น และเห็นรายการสาขาทั้งหมด (`X-Branch-Id`) |
| `shifts.override` | ปิด/ยกเลิกการนับกะที่คนอื่นเริ่ม |
| `settings.write` | แก้การตั้งค่าร้าน |
| `users.manage` | ดูรายชื่อและเพิ่ม/แก้ผู้ใช้ |
| `roles.manage` | สร้าง/แก้/ลบบทบาท |
| `audit.read` | ดูประวัติการกระทำ |

กฎ:

- `Permission` เป็น union ของสตริงข้างบน และมี `PERMISSIONS` เป็นรายการเรียงเป็นกลุ่มสำหรับหน้าเว็บ เพิ่มสิทธิ์ใหม่ต้องเพิ่มที่นี่ที่เดียว
- บทบาทระบบ `owner` ได้ทุกสิทธิ์รวมที่เพิ่มในอนาคต โดยไม่ต้องมีแถวใน `role_permissions` (`can()` ตอบว่าใช่เสมอ)
- ชื่อสิทธิ์ที่เก็บในฐานข้อมูลแต่ไม่อยู่ในรายการแล้ว (ถอดออกทีหลัง) ถูกข้ามตอนอ่าน ไม่ทำให้ error

## 2. บทบาท (role)

ตารางใหม่ (`infrastructure/database/schema/roles.ts`):

- `roles`: `id`, `name` (ไม่ซ้ำ ไม่เกิน 60 ตัวอักษร), `system_key` (`owner` | `cashier` | null), `created_at`, `updated_at`
- `role_permissions`: `role_id`, `permission` (PK ทั้งคู่)
- `users.role_id` เพิ่มเข้ามา (NOT NULL หลัง backfill)

บทบาทระบบ (ใส่ใน migration):

- **เจ้าของร้าน** (`system_key = owner`): ได้ทุกสิทธิ์ แก้ชื่อ แก้สิทธิ์ และลบไม่ได้
- **แคชเชียร์** (`system_key = cashier`): ไม่มีสิทธิ์พิเศษ (ตรงกับพฤติกรรมวันนี้) เจ้าของแก้สิทธิ์ได้ ลบไม่ได้

กฎ:

- กฎ "ต้องเหลือเจ้าของที่ใช้งานอยู่อย่างน้อยหนึ่งคน" ใน `UserEntity` ยังอยู่ และนิยามเป็น "ผู้ใช้ที่มีบทบาท `owner`"
- ลบบทบาทที่ตั้งเองได้เมื่อไม่มีผู้ใช้ถือ ไม่งั้น `ROLE_IN_USE` (409)
- ชื่อซ้ำ `ROLE_NAME_TAKEN` (409), แก้/ลบบทบาทระบบที่ห้าม `ROLE_PROTECTED` (409)
- การแก้สิทธิ์ของบทบาทที่ตั้งเอง: ส่งชุดสิทธิ์ทั้งชุด แทนที่ทั้งหมด (เหมือน `PUT /products/:id/modifier-groups`)

## 3. การบังคับสิทธิ์

- `auth.plugin.ts`: macro รับเพิ่ม `{ can: Permission }` (และ `true` เดิม) `auth: ['owner']` ถูกแทนด้วย `auth: { can: '...' }` ทุกจุด และเลิกรับ `UserRole[]`
- `AuthorizeSessionUseCase` โหลดบทบาทและสิทธิ์ของผู้ใช้ทุกคำขอ (query เดียว join) แล้วส่ง `actor` ที่มี `can(permission)`; ผู้ใช้ที่ถูกปิดใช้หรือสิทธิ์ที่ถูกถอดมีผลคำขอถัดไปทันที
- use case ที่เช็ก `actor.role !== 'owner'` เปลี่ยนเป็น `actor.can('...')` และโยน `DomainForbiddenError` พร้อมข้อความไทยเดิมแต่บอกสิทธิ์ที่ขาด (code ใหม่ `PERMISSION_DENIED` มี `params.permission`; เว็บแปลใน `locales/errors.ts`)
- `resolve-branch` และ `list-branches` ใช้ `branches.switch`; ผู้ใช้ที่ไม่มีสิทธิ์ยังถูกจำกัดสาขาตัวเองและบิลของสาขาอื่นยังตอบว่าไม่พบ
- ช่อง `role` เดิมใน API v1 ('owner' | 'cashier') คงไว้และไม่เปลี่ยนความหมาย: เป็น 'owner' เมื่อบทบาทคือ `owner` นอกนั้นเป็น 'cashier' (ฝั่งเว็บและไคลเอนต์เดิมจึงไม่พัง) ฟิลด์ใหม่ที่เพิ่ม (additive): `roleId`, `roleName`, `permissions` ใน `/auth/me` และ `roleId` ใน create/update user (`role` ที่ส่งมาแบบเดิมยังรับ และแปลงเป็นบทบาทระบบที่ตรงกัน)

## 4. บันทึกการกระทำ (audit log)

ตาราง `audit_logs` (`infrastructure/database/schema/audit-logs.ts`):

| คอลัมน์ | ความหมาย |
|---|---|
| `id` | bigserial |
| `at` | เวลาที่เกิด (timestamptz) |
| `actor_id` | ผู้กระทำ ว่างได้ (ล็อกอินล้มเหลว) |
| `actor_name` | ชื่อที่แสดงของผู้กระทำ ณ ตอนนั้น (หรือชื่อผู้ใช้ที่พยายามล็อกอิน) |
| `branch_id` | สาขาที่ทำงานอยู่ ว่างได้ |
| `action` | ชื่อเหตุการณ์ เช่น `sale.void` |
| `entity_type`, `entity_id` | สิ่งที่ถูกกระทำ เช่น `sale`, `412` |
| `summary` | ข้อความสั้นอ่านง่าย (ไทย) |
| `before`, `after` | jsonb ค่าก่อน/หลังเฉพาะช่องที่เปลี่ยน ว่างได้ |
| `reason` | เหตุผลที่ผู้ใช้กรอก ถ้ามี |

เหตุการณ์ (`action`):

| action | เมื่อไร |
|---|---|
| `sale.void`, `sale.cash_refund` | ยกเลิกบิล, คืนเงินสด |
| `qr.dismiss` | ปิดรายการ QR |
| `product.create`, `product.update` | สร้าง/แก้สินค้า (บันทึกเฉพาะช่องที่เปลี่ยน โดยราคา ต้นทุน และสถานะใช้งานเป็นตัวหลัก) |
| `stock.receive`, `stock.adjust` | รับของ/ปรับสต็อก (before/after เป็นยอด) |
| `shift.override_close` | ผู้อื่นปิด/ยกเลิกการนับกะแทน |
| `user.create`, `user.update` | สร้าง/แก้ผู้ใช้ (บทบาท สถานะ ชื่อ) ไม่เก็บรหัสผ่านหรือ hash |
| `role.create`, `role.update`, `role.delete` | บทบาทและชุดสิทธิ์ (before/after เป็นรายการสิทธิ์) |
| `settings.update` | การตั้งค่าร้าน |
| `auth.login_failed` | ล็อกอินล้มเหลว (ชื่อผู้ใช้ที่ลอง ไม่เก็บรหัสผ่าน) |

หลักการ:

- port `IAuditLog.record(entry)` ใน `modules/audit/applications/ports`; use case ของโมดูลอื่นเรียกผ่านโทเคนของ port ไม่แตะตาราง; adapter Drizzle ใช้ `currentExecutor()` จึงอยู่ในธุรกรรมเดียวกับคำสั่ง (ธุรกรรมถอยกลับ log ก็ถอยด้วย)
- ข้อยกเว้นเดียว: `auth.login_failed` ไม่มีธุรกรรมของคำสั่ง จึงเขียนเดี่ยว ๆ และความล้มเหลวของการเขียน log นั้นห้ามทำให้การล็อกอินพังเป็น 500 (กลืนและ log ลง console)
- ไม่มี use case หรือเส้นทางที่แก้หรือลบแถวของ `audit_logs` และไม่มี `UPDATE`/`DELETE` ใน adapter
- `before`/`after` ห้ามมีความลับ (รหัสผ่าน token `qrPaymentId` ของธนาคารอื่นนอกจาก id) และใหญ่ได้ไม่เกิน 8 KB (เกินให้เก็บเฉพาะช่องที่เปลี่ยน)
- อ่านผ่าน `GET /api/v1/audit-logs` (query ล้วน ต้อง `audit.read`): `limit`/`offset`, กรอง `from`/`to` (ตามวันของร้าน), `actorId`, `action`, `entityType`, `entityId` คืน `{ items, total }` เรียงใหม่สุดก่อน

## 5. สถาปัตยกรรมและการวางโมดูล

- `domains/permission.vo.ts`, `domains/role.domain.ts` (+test), `domains/audit-entry.vo.ts` (+test) ไม่พึ่ง framework
- โมดูลใหม่ `modules/roles` (use case: `ListRolesUseCase`, `GetRoleUseCase` เป็น query; `CreateRoleUseCase`, `UpdateRoleUseCase`, `DeleteRoleUseCase` เป็น command) และ `modules/audit` (`RecordAuditUseCase` ไม่มี: ใช้ port ตรง; `ListAuditLogsUseCase` เป็น query)
- `modules/users`: เพิ่ม port `IRoleDirectory` (ตอบว่าบทบาทมีอยู่/เป็นเจ้าของหรือไม่) แทนการ import โมดูล roles ตรง; `users.role_id` เขียนโดยโมดูล users
- ตั้งแต่ migration นี้ `userRole` enum คงไว้ในฐานข้อมูล (v1 ยังอ่านได้) และ repository เขียน `role` ตามบทบาทเสมอ เพื่อไม่ให้สองที่ขัดกัน

## 6. Migration และความเข้ากันได้

- migration ใหม่: สร้างตาราง, แทรกบทบาทระบบสองอัน, backfill `users.role_id` จาก `users.role`, ตั้ง NOT NULL, สร้างตาราง `audit_logs` และดัชนี `(at desc)`, `(actor_id, at)`, `(action, at)`
- เพิ่มอย่างเดียว ไม่ลบหรือเปลี่ยนชนิดคอลัมน์เดิม จึงรันกับฐานที่มีข้อมูลได้ (รวมฐาน demo) และถอยกลับโดยแอปรุ่นเก่ายังทำงานได้ (มันอ่าน `users.role` ซึ่งยังถูกเขียนอยู่)
- OpenAPI v1: เส้นทางใหม่ (`/roles`, `/audit-logs`) กับฟิลด์ใหม่ใน `/auth/me` และ user เท่านั้น ต้องแจ้งเจ้าของโครงการก่อนบันทึก baseline ใหม่
- `seed.ts`, `seed-demo.ts` และ `complete-setup.usecase.ts` สร้างผู้ใช้ด้วยบทบาทระบบ `owner`/`cashier` ผ่าน key

## 7. เว็บ

- feature ใหม่ `roles` (หน้า `/roles`): รายการบทบาท, dialog สร้าง/แก้พร้อมช่องติ๊กสิทธิ์จัดกลุ่ม, ลบ ปุ่มกดสูง 44px และใช้ `DataTable` พร้อม `priority`
- feature ใหม่ `audit` (หน้า `/audit`): `DataTable` ของ log กรองตามช่วงวัน ผู้กระทำ และชนิดเหตุการณ์ แถวขยายดูค่าก่อน/หลัง
- feature `users`: เลือกบทบาทจากรายการ `roles` แทน dropdown owner/cashier
- `auth`: เก็บ `permissions` จาก `/auth/me`; ฟังก์ชัน `can(permission)` ส่งออกจาก `@/features/auth` ใช้ซ่อนเมนูใน `AppSidebar` และปุ่ม (ยกเลิกบิล ปรับสต็อก ฯลฯ) ที่ผู้ใช้ไม่มีสิทธิ์ ค่าทั้งหมดอ่านจาก query ไม่คัดลอกลง store
- ข้อความทั้งหมดผ่าน `t()` ไทย/อังกฤษ; รหัสข้อผิดพลาดใหม่ (`PERMISSION_DENIED`, `ROLE_IN_USE`, `ROLE_NAME_TAKEN`, `ROLE_PROTECTED`, `ROLE_NOT_FOUND`) แปลใน `locales/errors.ts`
- ต้องใช้ได้ที่ 390/768/1366px, เพิ่มสองหน้าใน e2e รายการตรวจล้นแนวนอน และรัน `bun run screenshots`

## 8. การทดสอบ

- entity/value object: `Permission` (รายการไม่ซ้ำ), `RoleEntity` (บทบาทระบบแก้ไม่ได้, ชื่อ, ชุดสิทธิ์), `AuditEntry` (ตัดค่าที่ใหญ่เกิน, ห้ามมีความลับ)
- use case กับ port จำลองใน `__tests__/mocks.ts`: สร้าง/แก้/ลบบทบาททุกกรณีที่ถูกปฏิเสธ, ผู้ใช้ไม่มีสิทธิ์ถูก `PERMISSION_DENIED` ในทุกคำสั่งที่เปลี่ยน, คำสั่งเขียน audit ถูกเรียกพร้อมค่าก่อน/หลังที่ถูกต้อง
- integration (PostgreSQL จริง): ผู้จัดการที่ได้ `sales.void` ยกเลิกบิลได้และแคชเชียร์ไม่ได้, ถอดสิทธิ์แล้วมีผลคำขอถัดไป, ธุรกรรมที่ล้มเหลวไม่ทิ้ง log, log ของบิลที่ยกเลิกมีค่าก่อน/หลังและผู้กระทำ, เจ้าของสุดท้ายถอดบทบาทไม่ได้, ไม่มีทางแก้/ลบ log
- ชุดทดสอบเดิมทั้งหมดผ่านโดยไม่แก้ assertion (พิสูจน์ว่าผู้ใช้เดิมไม่เสียสิทธิ์)

## ความเสี่ยงและข้อสงสัยที่ยังเปิดอยู่

- `auth.login_failed` อาจโตเร็วถ้ามีคนเดารหัสต่อเนื่อง รอบนี้ยังไม่มีการเก็บตามอายุ จึงจำกัดด้วยการล็อก 15 นาทีของการล็อกอินที่มีอยู่ ถ้าพบว่าโตเกินไปให้เพิ่มการลบตามอายุเป็นงานแยก
- ผู้ใช้เดิมของร้านที่ตั้ง `role = cashier` แต่ใช้ฟังก์ชันที่ API เปิดให้ทุกคน (เช่น เพิ่มสมาชิก) ยังทำได้เหมือนเดิมเพราะเป็น `auth: true`
