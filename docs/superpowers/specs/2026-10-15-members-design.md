# สมาชิกและประวัติซื้อ — แบบออกแบบรุ่นแรก

วันที่: 2026-10-15

สถานะ: รอตรวจแบบออกแบบก่อนเขียนแผนลงมือและโค้ด

## ขอบเขตที่ผู้ใช้เลือกแล้ว

- ข้อมูลสมาชิก ประวัติซื้อ และโปรโมชั่นสมาชิกก่อน ยังไม่มีแต้ม
- ใช้แนวทางโปรโมชั่นที่เสนอเป็นค่าเริ่มต้น: ลดเป็นบาทหรือเปอร์เซ็นต์ กำหนดยอดขั้นต่ำและช่วงเวลาได้ ใช้กับทุกคนหรือเฉพาะสมาชิก
- คำว่า `ok` ล่าสุดใช้เป็นการให้จัดทำแบบออกแบบตามแนวทางแนะนำ ไม่ถือเป็นการยืนยันกติกาการเงินที่ยังไม่เคยเสนอ

## แบ่งงาน

1. `ohmattpon/members`: สมาชิก ผูกสมาชิกกับออเดอร์/บิล และประวัติซื้อ ตามเอกสารนี้
2. `ohmattpon/promotions`: โปรโมชั่นและการคำนวณส่วนลด หลังสมาชิกเข้า `main` แล้ว ออกแบบและตรวจแยกก่อนลงมือ

การแยกนี้ทำให้แต่ละ branch มี feature เดียวและไม่ต้องแก้โปรโมชั่นพร้อมกับข้อมูลสมาชิก ยังไม่เพิ่มแต้ม ระดับสมาชิก ซื้อแถม คูปอง หรือแอปที่ลูกค้าสมัครเอง

## 1. ข้อมูลสมาชิกและสิทธิ์

ข้อเสนอกติกาต่อไปนี้ต้องได้รับการตรวจจากผู้ใช้:

- สมาชิกใช้ร่วมทุกสาขาภายในร้านที่ติดตั้งระบบเดียวกัน
- เก็บชื่อ เบอร์โทร รหัสสมาชิก สถานะเปิดใช้ วันสร้างและแก้ไข รหัสสมาชิกสร้างโดยระบบและแก้ไม่ได้
- ชื่อ 1–120 ตัวอักษรหลังตัดช่องว่างหัวท้าย ไม่เก็บวันเกิด เลขประจำตัวประชาชน ที่อยู่ หรือรหัสผ่านในรุ่นแรก
- เบอร์โทรจำเป็นและห้ามซ้ำ รวมสมาชิกที่ปิดใช้แล้ว เพื่อไม่ให้สร้างคนใหม่ทับประวัติเดิม
- ตัดช่องว่าง ขีด และวงเล็บออกก่อนตรวจ รับตัวเลข 8–15 หลักและเครื่องหมาย `+` เฉพาะด้านหน้า รูปแบบมือถือไทย `+66` หรือ `66` ที่ตามด้วยเลข 9 หลักทำให้เป็น `0` นำหน้า เพื่อให้ค้นหาและตรวจค่าซ้ำแบบเดียวกัน ไม่มี OTP และไม่อ้างว่ายืนยันเจ้าของเบอร์แล้ว
- เจ้าของและแคชเชียร์สมัคร ค้นหา และเลือกสมาชิกขายได้ เจ้าของเท่านั้นที่แก้ข้อมูลและเปิด/ปิดใช้
- ปิดใช้ได้แต่ลบไม่ได้ สมาชิกที่ปิดใช้ยังดูประวัติได้ แต่เลือกผูกกับการขายหรือออเดอร์ใหม่ไม่ได้
- ถ้ามีการแก้เบอร์ใหม่แล้วพบค่าซ้ำ ให้ปฏิเสธอย่างชัดเจน ไม่รวมคนหรือย้ายบิลให้เอง

## 2. การขายและออเดอร์

- ขายโดยไม่เลือกสมาชิกได้ตามเดิม
- ตะกร้าเก็บเฉพาะ `memberId` และอ่านรายละเอียดจาก TanStack Query ไม่คัดลอกข้อมูลเซิร์ฟเวอร์ไปเป็นสถานะถาวรใน zustand
- เปลี่ยนสาขา ออกจากระบบ หรือเริ่มตะกร้าใหม่ต้องล้างสมาชิกพร้อมตะกร้า
- บิลใหม่ผูกสมาชิกได้หนึ่งคน บิลที่บันทึกแล้วห้ามเพิ่ม เปลี่ยน หรือลบสมาชิกย้อนหลัง
- `SaleCheckout` ตรวจสมาชิกผ่าน port ของโมดูลสมาชิกภายใน unit of work เดิม และเก็บรหัส/ชื่อสมาชิก ณ ตอนขายไว้เป็น snapshot
- การอ่านสมาชิกเพื่อ checkout ใช้ port ที่ลงท้าย `ForUpdate` เพื่อให้การแก้ชื่อหรือปิดใช้พร้อมกันไม่เปลี่ยนข้อมูลกลางการขาย ลำดับล็อกคือออเดอร์ (ถ้ามี) → สมาชิก → สินค้า โดยคงลำดับล็อกสินค้าของระบบเดิม
- บิลเก่าและบิลไม่ระบุสมาชิกใช้ค่า `null` การแก้ชื่อหรือปิดสมาชิกไม่เปลี่ยน snapshot หรือบิลเดิม
- ไม่เก็บเบอร์โทรใน snapshot ใบเสร็จ และไม่ส่งเบอร์หรือประวัติซื้อไปจอลูกค้า
- ใบเสร็จของบิลสมาชิกแสดงรหัสและชื่อสมาชิกจาก snapshot
- บิลที่ยกเลิกยังอยู่ในประวัติและแสดงสถานะยกเลิก แต่ไม่นับเป็นยอดซื้อสุทธิหรือจำนวนครั้งที่ซื้อสำเร็จ
- สมาชิกไม่ทำให้ราคาสินค้า สูตร VAT สต็อก เลขใบเสร็จ การคืนเงิน หรือยอด QR เปลี่ยนใน feature แรกนี้

ออเดอร์ค้าง:

- ออเดอร์เก็บ `memberId` ได้ และเปลี่ยน/ล้างสมาชิกได้เฉพาะตอนยังเปิดอยู่ โดยล็อกแถวออเดอร์ก่อนแก้
- ตอนชำระตรวจว่าสมาชิกยังเปิดใช้อยู่ หากปิดไปแล้วให้แจ้งพนักงานเลือกคนใหม่หรือล้างสมาชิกอย่างชัดเจน ไม่เปลี่ยนเป็นลูกค้าทั่วไปเอง
- แยกบิล: ออเดอร์ใหม่รับสมาชิกเดิมมาด้วย สมาชิกของทั้งสองออเดอร์ยังแก้ได้ตามกฎออเดอร์เปิด
- รวมบิล: ถ้าทั้งสองมีสมาชิกคนละคนให้ปฏิเสธและให้พนักงานจัดสมาชิกก่อน ถ้ามีสมาชิกเพียงฝั่งเดียวให้ใช้คนนั้น ถ้ามีคนเดียวกันให้คงไว้
- การรวมยังล็อกออเดอร์เรียง id เหมือนเดิม และราคาที่ออเดอร์ quote ไว้ไม่เปลี่ยน

## 3. ประวัติซื้อและหน้าจอ

- เมนูสมาชิกมีค้นหาชื่อ/เบอร์/รหัส แบ่งหน้า สมัครสมาชิก และแสดงสถานะ
- รายละเอียดสมาชิกแสดงข้อมูลและประวัติซื้อในสาขาที่เลือกอยู่ พร้อมยอดซื้อและจำนวนครั้งที่สำเร็จของตัวกรองเดียวกัน
- ประวัติใช้ `limit`/`offset` และตัวกรองช่วงวัน/สถานะ แสดงเลขบิล วันเวลา ยอด และสถานะ เปิดรายละเอียดบิลเดิมได้
- แคชเชียร์เห็นประวัติเฉพาะสาขาที่มีสิทธิ์ เจ้าของเปลี่ยนสาขาด้วยตัวเลือกสาขาเดิมได้ รุ่นแรกไม่มีหน้ารวมประวัติทุกสาขาในคำขอเดียว
- หน้าขายมีปุ่มเลือกสมาชิก ค้นหา/สมัครใน dialog และล้างการเลือกได้ ก่อนเปิดหน้าชำระ
- หน้าสมาชิกใช้ได้ทั้งเจ้าของและแคชเชียร์ แต่ซ่อนปุ่มแก้/ปิดใช้ตามสิทธิ์และ API ตรวจซ้ำเสมอ
- ใช้ shadcn, semantic tokens, ไทย/อังกฤษ และธีมเดิม ปุ่มอย่างน้อย 44px ตารางใช้ `DataTable` และช่วงวันใช้ `DatePicker` ที่มีอยู่
- โหลดครั้งแรกมี skeleton; ข้อผิดพลาดมีลองใหม่; แยกกรณีไม่พบสมาชิกกับเชื่อมต่อไม่ได้ ไม่แสดงรายการว่างแทนข้อผิดพลาด

## 4. ขอบเขตสถาปัตยกรรมและ API

- `domains/member.domain.ts` และ value object เบอร์โทรเป็นฟังก์ชัน/ข้อมูลล้วน
- โมดูล `members` ตามต้นแบบ `categories`: use case แบบ command/query, input `unknown` + zod, repository หลัง port, DI token และ domain errors ภาษาไทยพร้อม code คงที่
- โมดูล sales อ่านข้อมูลสมาชิกผ่าน port เท่านั้น โมดูล orders ผูกสมาชิกผ่าน port เดียวกัน
- ประวัติซื้ออยู่หลัง port ที่โมดูล sales เป็นผู้ตอบ โมดูล members ไม่อ่านตาราง sales โดยตรง
- repository ใช้ `currentExecutor()` และคำสั่งที่เขียนหลายตารางอยู่ใน `IUnitOfWork.run()`
- เพิ่ม `members`, nullable FK `member_id` ของ orders/sales และ nullable snapshot สมาชิกของ sales พร้อมดัชนีที่รองรับการค้นหาและประวัติตามสาขา ห้ามลบข้อมูลบิลเดิม
- เพิ่มคำสั่งสมัคร/แก้สมาชิก query รายการ/รายละเอียด และ query ประวัติซื้อภายใต้ `/api/v1/members`
- เพิ่มการเปลี่ยนสมาชิกของออเดอร์เปิด และ optional member input ใน checkout ทั้ง legacy/v2 โดยคำขอเดิมที่ไม่ส่งสมาชิกยังทำงานเหมือนเดิม
- ประวัติรับ `branchId` ชัดเจนจาก `await branch()` และทุก list คืน `{ items, total }` ไม่คืน array เปล่า
- การเพิ่ม response fields เป็นแบบ additive บิล/ออเดอร์ที่ไม่มีสมาชิกมีค่า nullable สม่ำเสมอ ต้องแจ้งขอบเขตสัญญา API ก่อนบันทึก OpenAPI baseline ใหม่

## 5. ขอบเขตโปรโมชั่นในงานถัดไป

ข้อเสนอเริ่มต้นสำหรับตรวจในแบบออกแบบโปรโมชั่น:

- ลดท้ายบิลเป็นบาทหรือเปอร์เซ็นต์ ตั้งยอดขั้นต่ำ วันเริ่ม/สิ้นสุดตามเขตเวลาร้าน และสิทธิ์ทุกคน/สมาชิก
- เริ่มจากโปรโมชั่นเดียวต่อบิล เลือกที่ลดให้มากที่สุดโดยอัตโนมัติ พร้อมชื่อและยอดส่วนลดให้พนักงานเห็น
- ส่วนลดกรอกเองกับโปรโมชั่นไม่บวกซ้อนกัน ถ้าจะใช้ส่วนลดกรอกเองให้ยืนยันยกเลิกโปรโมชั่นของบิลนั้น
- สูตรคำนวณตรวจบนเซิร์ฟเวอร์ ยอดขั้นต่ำเทียบยอดสินค้ารวมตัวเลือกก่อนส่วนลดและ VAT ที่บวกเพิ่ม ปัดจำนวนเงินเป็นสตางค์ตามกฎเดียวกันและไม่ให้ส่วนลดเกินยอดสินค้า
- ก่อนสร้าง QR ต้องมีราคาที่เซิร์ฟเวอร์ยืนยันและตรึงไว้ การแก้สมาชิก/ตะกร้าหลังสร้าง QR ต้องไม่ทำให้เงินที่จ่ายแล้วสูญหายหรือถูกเปลี่ยนกลับเป็น pending
- แบบออกแบบโปรโมชั่นต้องกำหนดอายุและการผูก quote กับตะกร้า/สมาชิก/สาขา วิธีรับเงินที่มาถึงหลังหมดเวลา การใช้ QR ได้ครั้งเดียว และการยกเลิกบิล ก่อนเขียนโค้ดส่วนนั้น

หัวข้อนี้เป็นขอบเขตของ feature ถัดไป ไม่เพิ่ม quote engine หรือเปลี่ยนกฎชำระเงินใน branch สมาชิก

## 6. เกณฑ์ยอมรับและตรวจงาน

1. Domain/unit: เบอร์หลายรูปแบบเท่ากัน, ค่าซ้ำ/ไม่ถูกต้อง, สิทธิ์, ปิดใช้, snapshot, และกติกาสมาชิกตอนรวม/แยกออเดอร์
2. Use cases กับ mock ports: สมัคร ค้นหา แก้สถานะ ผูกสมาชิก ขายปกติ/ชำระออเดอร์ และทุกกรณีปฏิเสธ ไม่ต้องมีฐานข้อมูล
3. HTTP/PostgreSQL: สมัครเบอร์เดียวพร้อมกันได้คนเดียว, rollback การขายที่ล้มเหลว, ประวัติตามสาขา/วัน/สถานะและ pagination, ราคาสมาชิกไม่เปลี่ยนบิลเก่า และบิลยกเลิกไม่นับยอด
4. Checkout regression: ลูกค้าทั่วไป ราคาออเดอร์เดิม VAT สต็อก shift/idempotency และการ claim QR ใช้กฎเดิมทั้งหมด
5. Browser: สมัครจาก POS, เลือก/ล้างสมาชิก, ขายและดูประวัติ, ชำระออเดอร์สมาชิก, logout/สลับสาขา, ข้อผิดพลาดและสิทธิ์แคชเชียร์
6. root typecheck/test, lint, web build, OpenAPI และ screenshots 390/390×500/768/1366px พร้อมตรวจภาพจริง
7. การทดสอบใช้ฐานข้อมูลทดสอบแยกและ SCB จำลองตาม harness เดิม ไม่แก้ข้อมูล dev หรือเรียกธนาคารจริง
