# โต๊ะ

สถานะ: ร่างสำหรับลงมือทำ · roadmap ข้อ 8 · branch `ohmattpon/tables` (แตกจาก `main`)

## เป้าหมาย

ร้านอาหารจัดผังโต๊ะจริงของร้านได้ เปิดออเดอร์ตามโต๊ะ เห็นว่าโต๊ะไหนว่างหรือมีลูกค้าพร้อมยอด และย้ายโต๊ะ รวมบิล แยกบิลตามรายการได้ ฐานนี้ใช้ต่อกับใบสั่งครัว (ข้อ 9)

## การตัดสินใจ

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| โครงสร้าง | โต๊ะเป็น aggregate ใหม่ (`dining_tables`) ออเดอร์ชี้ด้วย `orders.table_id` และคำสั่งย้าย/รวม/แยกเป็นคำสั่งของออเดอร์ | ใช้โครงเดิมของออเดอร์ (ล็อกแถว, `lineId` คงที่จากข้อ 7) ไม่ต้องเพิ่ม aggregate "ใบโต๊ะ" |
| ขอบเขตของโต๊ะ | เป็นของสาขา ชื่อห้ามซ้ำในสาขา จัดการโดยเจ้าของ | ผังของแต่ละสาขาต่างกัน |
| ผัง | ผังจริงที่ลากวางตำแหน่งได้เอง: `x`, `y`, `width`, `height` เป็นจำนวนเต็มในหน่วยของผัง (ผังกว้าง 1000 สูง 700) | เจ้าของเลือกเอง ลากด้วย pointer events ให้ใช้ได้ทั้งเมาส์และจอสัมผัส |
| ออเดอร์ต่อโต๊ะ | โต๊ะหนึ่งมีออเดอร์เปิดได้หลายใบ | การแยกบิลสร้างออเดอร์ใหม่ที่โต๊ะเดียวกัน |
| สถานะโต๊ะ | คำนวณจากออเดอร์เปิด (ว่าง / มีลูกค้า พร้อมจำนวนออเดอร์และยอด) ไม่เก็บเป็นคอลัมน์ | กันสถานะค้างผิดจากความจริง |
| ย้ายโต๊ะ | เปลี่ยน `table_id` ของออเดอร์ทั้งใบ ย้ายไปโต๊ะที่มีออเดอร์เปิดอยู่แล้วได้ ออเดอร์ยังแยกกัน | รวมเป็นอีกคำสั่งที่ชัดเจน |
| รวมบิล | ย้ายบรรทัดของออเดอร์ต้นทางเข้าปลายทาง บรรทัดที่สินค้าและชุดตัวเลือกเหมือนกันบวกจำนวน คงราคาที่ quote ของปลายทาง ต้นทางเป็นสถานะ `merged` พร้อม `merged_into_id` | แยกจาก "ยกเลิก" ชัดเจน รายงานยกเลิกไม่ปน |
| แยกบิล | แยกตามรายการ: เลือกบรรทัดและจำนวน สร้างออเดอร์ใหม่ที่โต๊ะเดียวกันโดยถือราคาที่ quote ไว้ ห้ามแยกจนออเดอร์เดิมไม่เหลือรายการ | เจ้าของเลือกแบบนี้ ไม่แตะการออกบิล (หนึ่งออเดอร์ได้หนึ่งบิล) |
| การปิดโต๊ะ | โต๊ะปิดใช้ได้แต่ลบไม่ได้ และปิดไม่ได้ถ้ามีออเดอร์เปิดอยู่ | บิลเก่าอ้างถึงได้ |
| สัญญา API | v1 เพิ่มอย่างเดียว (เส้นทางใหม่ ช่องใหม่ และค่า `merged` ใน enum สถานะ) | client เดิมที่ไม่ส่ง `tableId` ทำงานเหมือนเดิม |

## ข้อมูล

ตารางใหม่ (migration `0013_tables`):

- `dining_tables`: `id`, `branch_id`, `name`, `zone` (null ได้), `seats`, `x`, `y`, `width`, `height`, `sort_order`, `is_active`, timestamps; unique `(branch_id, name)`

คอลัมน์ใหม่:

- `orders.table_id` (null ได้, FK `dining_tables`), `orders.merged_into_id` (null ได้, FK `orders`); enum `order_status` เพิ่มค่า `merged`

ออเดอร์เดิมได้ `table_id` เป็น null จึงไม่ต้องย้ายข้อมูล `label` เดิมยังอยู่ไว้ใช้กับออเดอร์ที่ไม่มีโต๊ะ

## โดเมน

- `DiningTableEntity`: ตรวจชื่อ (1–50), ที่นั่ง (จำนวนเต็ม 1–99), ตำแหน่งและขนาด (จำนวนเต็ม อยู่ในผัง ขนาดไม่ต่ำกว่าค่าต่ำสุด) โยน `DomainError` รหัส `INVALID_TABLE`
- `OrderEntity` เพิ่ม `tableId`, `mergedIntoId`, เมธอด:
  - `moveToTable(tableId | null)`
  - `absorb(source: OrderEntity)` รวมบรรทัดของ `source` เข้าตัวเอง
  - `markMerged(intoId)` ต้นทางเปลี่ยนเป็น `merged`
  - `splitOff(selection, nextLabel)` คืนคู่ (ออเดอร์เดิมที่เหลือ, ข้อมูลออเดอร์ใหม่) ตรวจ: บรรทัดมีอยู่ จำนวนไม่เกิน และต้องเหลืออย่างน้อยหนึ่งรายการ
  - ทุกเมธอดต้องการออเดอร์ที่เปิดอยู่ (`ORDER_NOT_OPEN`) และรวมเข้าตัวเองไม่ได้ (`ORDER_MERGE_SAME`)
- สถานะ `merged` เป็นสถานะปิด แก้ชำระ ยกเลิกไม่ได้ และต้องมี `mergedIntoId`

## API (โมดูลใหม่ `tables`, ใต้ `/api/v1`)

| Use case | ชนิด | เส้นทาง | สิทธิ์ |
|---|---|---|---|
| `ListTables` | query | `GET /catalog/tables` คืน `{items,total}` พร้อม `openOrders` และ `openTotalSatang` ของสาขาที่ทำงานอยู่ | ผู้ใช้ที่ล็อกอิน |
| `CreateTable` | command | `POST /catalog/tables` | เจ้าของ |
| `UpdateTable` | command | `PATCH /catalog/tables/:id` (ชื่อ โซน ที่นั่ง ตำแหน่ง ขนาด ลำดับ เปิด/ปิด) | เจ้าของ |
| `MoveOrderToTable` | command | `POST /orders/:id/move` `{ tableId }` | ผู้ใช้ที่ล็อกอิน |
| `MergeOrders` | command | `POST /orders/:id/merge` `{ sourceOrderId }` | ผู้ใช้ที่ล็อกอิน |
| `SplitOrder` | command | `POST /orders/:id/split` `{ lines: [{ lineId, quantity }], label? }` คืนออเดอร์ใหม่ | ผู้ใช้ที่ล็อกอิน |

- `POST /orders` รับ `tableId`; คำตอบของออเดอร์เพิ่ม `tableId`, `mergedIntoId`
- รวมและแยกล็อกแถวออเดอร์ทั้งสองใบตามลำดับ id ภายใน unit of work เดียว ออเดอร์ของสาขาอื่นตอบ `ORDER_NOT_FOUND` และโต๊ะต้องอยู่สาขาเดียวกับออเดอร์
- รหัสผิดพลาดใหม่ (เพิ่มคำแปลใน `locales/errors.ts`): `TABLE_NOT_FOUND`, `TABLE_INACTIVE`, `TABLE_HAS_OPEN_ORDERS`, `INVALID_TABLE`, `ORDER_SPLIT_EMPTY`, `ORDER_SPLIT_QUANTITY`, `ORDER_MERGE_SAME`
- baseline OpenAPI ต้องบันทึกใหม่ (เพิ่มอย่างเดียว) โดยแจ้งเจ้าของโครงการก่อน

## เว็บ

- feature ใหม่ `tables`:
  - หน้า `/tables`: เจ้าของแก้ผัง ลากวาง ดึงมุมปรับขนาด เพิ่ม แก้ ปิดโต๊ะ (บันทึกตำแหน่งเมื่อปล่อย) ส่วนแคชเชียร์เห็นผังแบบอ่านอย่างเดียวพร้อมสถานะ
  - แตะโต๊ะ: เลือกออเดอร์ของโต๊ะนั้นหรือเปิดใหม่ แล้วไปทำงานต่อในหน้าขาย
- `pos`: ตะกร้าของออเดอร์ที่เปิดอยู่มีปุ่ม ย้ายโต๊ะ / รวมบิล / แยกบิล เป็น dialog แยก
- `orders`: mutation ของคำสั่งใหม่ผ่าน `features/orders/api.ts` ตัวเดียว
- ฟังก์ชันล้วนสำหรับพิกัด (แปลงพิกัดหน้าจอเป็นหน่วยผัง จำกัดไม่ให้ออกนอกผัง ขนาดต่ำสุด) มีการทดสอบ
- ข้อความผ่าน `t()` ไทยและอังกฤษ

## นอกขอบเขต

จองโต๊ะ จับเวลา แยกบิลแบบหารเท่า ชำระหลายโต๊ะพร้อมกัน กำหนดพนักงานประจำโต๊ะ หลายชั้น/หลายผังต่อสาขา รูปทรงนอกจากสี่เหลี่ยม

## เสร็จเมื่อ

- เจ้าของวางและปรับโต๊ะบนผังได้ และผังคงอยู่หลังโหลดใหม่
- แคชเชียร์เห็นสถานะโต๊ะ เปิดออเดอร์ที่โต๊ะ ย้าย รวม และแยกบิลได้ ยอดรวมของออเดอร์ทั้งหมดไม่เปลี่ยนจากการรวมหรือแยก
- ชำระออเดอร์ที่แยกออกมาแล้วได้บิลถูกต้อง และออเดอร์ที่ `merged` แก้ไม่ได้
- ปิดโต๊ะที่มีออเดอร์เปิดไม่ได้ และออเดอร์/โต๊ะของสาขาอื่นถูกปฏิเสธ
- `typecheck`, `test`, `lint`, `openapi:check` (หลังได้รับอนุมัติให้บันทึก baseline) และ `e2e` ผ่าน
