# รายงานแบบละเอียด

หน้ารายงานตอนนี้มีตัวเลขสรุป กราฟยอดขายรายวัน ช่องทางชำระเงิน สินค้าขายดี แท็บโปรโมชัน และส่งออก Excel เจ้าของร้านอยากดูรายละเอียดได้มากแบบระบบระดับองค์กร: เห็นตัวเลขแล้วกดลงไปดูต่อจนถึงบิลที่เป็นต้นเหตุ และมีมุมมองเพิ่ม เช่น ยอดขายตามโปรโมชัน และยอดซื้อของสมาชิก

หน้าตัวอย่างที่คุยกันไว้อยู่ที่ `.superpowers/brainstorm/` (ไม่ commit)

## เป้าหมาย

- **เทียบกับช่วงก่อนหน้า:** ตัวเลขสรุปทุกตัวแสดง % ที่เปลี่ยนไปเทียบกับช่วงก่อนหน้าที่ยาวเท่ากัน เช่น 1–28 ต.ค. เทียบกับ 3–30 ก.ย.
- **ตัวกรองที่ใช้กับทุกแท็บ:** ช่วงวัน, หมวดหมู่, พนักงาน (คนขาย), และสมาชิกหรือไม่ใช่สมาชิก
- **แท็บแยกมุมมอง:**
  1. **ภาพรวม:** ตัวเลขสรุปแบบเดิม พร้อมการเทียบ กราฟรายวัน สัดส่วนยอดของสมาชิกกับลูกค้าทั่วไป และสัดส่วนบิลที่ใช้โปรโมชัน
  2. **สินค้า:** จำนวน ยอดขาย ต้นทุน กำไร และ % กำไรต่อสินค้า เรียงได้ทุกคอลัมน์ แยกแพ็คกับชิ้น
  3. **หมวดหมู่:** ยอดขาย กำไร % กำไร และสัดส่วนของยอดรวม
  4. **ช่วงเวลา:** ตารางวันในสัปดาห์ × ชั่วโมง (ยอดขายและจำนวนบิล) ตามเขตเวลาร้าน
  5. **พนักงาน:** ยอดขาย จำนวนบิล ยอดเฉลี่ยต่อบิล จำนวนบิลที่ยกเลิก และส่วนลดที่ให้ไป ต่อคนขาย
  6. **สมาชิก:** สมาชิกแต่ละคนซื้อกี่บิล ยอดเท่าไร ซื้อครั้งล่าสุดเมื่อไร แต้มที่ได้และแต้มที่ใช้ และสรุปสมาชิกใหม่ในช่วงนั้นที่ซื้อแล้ว
  7. **โปรโมชัน:** แต่ละโปรใช้กี่บิล ส่วนลดที่ให้ไป ยอดขาย (รวมและไม่รวม VAT) ยอดเฉลี่ยต่อบิล และรหัสคูปองที่ใช้ (ต่อยอดจากรายงานโปรโมชันเดิม)
  8. **ชำระเงิน:** ยอดต่อช่องทาง จำนวนบิล และสัดส่วน
  9. **ส่วนลดและยกเลิก:** บิลที่ยกเลิก พร้อมผู้ยกเลิก เหตุผล และเวลา ส่วนลดท้ายบิลที่พิมพ์เองต่อคน และส่วนลดจากแต้ม
  10. **บิลทั้งหมด:** รายการบิลตามตัวกรอง ค้นจากเลขบิลได้
- **เจาะลงได้ทุกจุด:** กดแท่งวัน, แถวสินค้า, หมวด, ช่องในตารางเวลา, พนักงาน, สมาชิก, โปรโมชัน หรือช่องทางชำระ จะเห็นรายละเอียดของสิ่งนั้น (ตัวเลขสรุปของมัน และรายการบิลที่เกี่ยวข้อง) และกดบิลจะเปิดใบเสร็จด้วย `SaleDetailDialog` ที่มีอยู่แล้ว
- **รายละเอียดสินค้า:** ยอดรายวันของสินค้านั้น ตัวเลือกเสริมที่ขายคู่ ช่วงเวลาที่ขายดี และสัดส่วนที่สมาชิกซื้อ
- **ส่งออก Excel:** ส่งออกแท็บและตัวกรองที่เลือกอยู่ ใช้ `export-workbook.ts` ที่มีอยู่แล้วเป็นฐาน

## ไม่ทำ

- แดชบอร์ดที่ปรับแต่งเองได้ หรือการลากวางกราฟ
- การทำนายยอดขาย และ AI วิเคราะห์ยอด
- รายงานที่ส่งอีเมลตามเวลา และการสมัครรับรายงาน
- รายงานสต็อกและการเคลื่อนไหวของสต็อก (เป็นงานแยก)
- รายงานรวมหลายสาขา ระบบมีสาขาเดียวคือ `MAIN`
- กราฟหลายแบบซ้อนกันเพื่อความสวย ตาม `DESIGN.md` ("Calm" ไม่มีไล่สี ไม่มี animation ตกแต่ง)

## ห้ามเกิด

- ตัวเลขในหน้ารายงานไม่ตรงกับตัวเลขบนบิล หรือแท็บต่างกันให้ยอดรวมไม่เท่ากันในตัวกรองเดียวกัน
- บิลที่ยกเลิกถูกนับในยอดขาย (นับเฉพาะในแท็บส่วนลดและยกเลิก)
- รายงานเก่าเปลี่ยนไปเพราะมีคนแก้ชื่อสินค้า ราคา หรือโปรโมชันทีหลัง
- หน้ารายงานช้าจนใช้ไม่ได้เมื่อมีบิลเป็นปี ช่วงวันยังจำกัดไม่เกิน 366 วันเหมือนเดิม
- route ของ `v1` ที่ใช้อยู่เปลี่ยนรูปแบบคำตอบ

## ข้อจำกัด

- **ข้อมูล ณ ตอนขาย:** ใช้ค่าที่เก็บบนบิล (ชื่อสินค้า, SKU, ราคา, ต้นทุน, โปรโมชัน, ข้อมูลสมาชิก, ชื่อคนขาย, ตัวเลือก, แพ็ค) ไม่ประกอบประวัติจากข้อมูลหลักปัจจุบัน ตามหลักใน `AGENTS.md`
- **หมวดหมู่ไม่มีบนบรรทัดบิล:** `sale_items` ยังไม่เก็บหมวด จึงเพิ่มคอลัมน์ `category_id` แบบ nullable เก็บตอนขายใน `SaleCheckout` *(การตัดสินใจของผม)* กฎคือ **บรรทัดเก็บหมวดที่ใช้ตอนขายไว้เสมอ ไม่ย้อนไปใช้หมวดปัจจุบันของสินค้า** บรรทัดที่ขายก่อนอัปเดตนี้ไม่มีหมวด จึงขึ้นใต้ "ไม่มีหมวดหมู่" บรรทัดเก็บเฉพาะ id ของหมวด ไม่เก็บชื่อ รายงานอ่านชื่อปัจจุบันของหมวดนั้น (หมวดที่ถูกลบแล้วแสดงเป็น "หมวดหมู่ที่ลบแล้ว") migration ต้องเป็นแบบเพิ่มอย่างเดียว
- **สถาปัตยกรรม:** use case แบบ query หนึ่งตัวต่อมุมมอง ใน `sales` module ตามรูปแบบ `get-sales-report.usecase.ts` ข้อมูลอ่านผ่าน port ของ module เอง ข้อมูลสมาชิกอ่านจากค่าที่เก็บบนบิล ไม่ import ภายในของ module `members` ถ้าต้องใช้ข้อมูลที่ไม่มีบนบิล (เช่น วันสมัครสมาชิก) ให้ประกาศ port แคบใน `sales` และให้ `members` เป็นผู้ implement
- **API:** route ใหม่อยู่ใต้ `/api/v1/sales/reports/...` แบบเพิ่มอย่างเดียว ทุกรายการคืน `{ items, total }` ผ่าน `page()` พร้อม `limit` และ `offset` และต้องบอกเจ้าของโครงการก่อนบันทึก OpenAPI baseline ใหม่
- **สิทธิ์:** ทุก route ใช้ `reports.read` เหมือนเดิม (ดูส่วนที่ตัดสินใจแล้ว)
- **เวลา:** ทุกการแบ่งตามวันและชั่วโมงคิดตาม `timeZone` ของร้าน
- **เงิน:** satang เป็นจำนวนเต็มตลอด สูตรใดที่ทั้งเว็บและเซิร์ฟเวอร์ใช้ (เช่น % เปลี่ยนแปลง, % กำไร) เป็นฟังก์ชัน pure ที่มีเทสต์
- **หน้าจอ:** ใช้ `DataTable` พร้อม `priority` ทุกคอลัมน์ ทำงานที่ 390, 768 และ 1366px ข้อความทั้งหมดผ่าน `t()` ทั้งไทยและอังกฤษ

## ส่วนที่ตัดสินใจแล้ว

- รวมทุกอย่างที่เสนอ และยอดตามโปรโมชันกับยอดของสมาชิก (เจ้าของ)
- โครงหน้าแบบในหน้าตัวอย่าง: แถบช่วงวันกับการเทียบอยู่บนสุด แถวแท็บ และตัวเลขสรุปพร้อม % เปลี่ยนแปลง (เจ้าของตอบ "ok" ต่อหน้าตัวอย่าง)
- การเจาะลงเปิดในหน้าเดิม มี breadcrumb กลับขึ้นไป *(การตัดสินใจของผม)*
- ตัวกรองหมวดหมู่ พนักงาน และสมาชิก ใช้ร่วมกันทุกแท็บ และอยู่ใน URL เพื่อให้ refresh หรือส่งลิงก์ต่อได้ *(การตัดสินใจของผม)*

- **ยอดต่อสินค้าและหมวดกระจายส่วนลดท้ายบิลและ VAT ตามสัดส่วน** เพื่อให้ทุกแท็บรวมแล้วเท่ากับภาพรวมในตัวกรองเดียวกัน ส่วนลดของบิล (รวมส่วนลดจากแต้ม) กระจายลงแต่ละบรรทัดตามสัดส่วน `lineTotalSatang` ปัดเศษ satang ด้วยวิธี largest remainder ให้ผลรวมเท่ายอดบิลพอดี แล้วคิด VAT ต่อบรรทัดแบบเดียวกัน สูตรนี้เป็นฟังก์ชัน pure ตัวเดียวใน `domains/` มีเทสต์ และไม่แตะ `calculateTotals` เมื่อกรองหมวด บิลที่มีหลายหมวดนับเฉพาะส่วนของหมวดนั้น จำนวนบิลนับบิลที่มีสินค้าในหมวดนั้นอย่างน้อยหนึ่งบรรทัด และแท็บชำระเงินกระจายยอดตามสัดส่วนเดียวกัน หน้าจอบอกไว้ว่ายอดต่อสินค้าหักส่วนลดท้ายบิลแล้ว จึงอาจไม่ตรงกับราคาบนใบเสร็จ *(เจ้าของตอบ "ok" ต่อทางเลือกที่ผมแนะนำ)*
- **บรรทัดของบิลเก่าที่ยังไม่มีส่วนแบ่ง:** เมื่อ migrate ระบบเติม `allocated_total_satang` และ `allocated_vat_satang` ของบรรทัดเก่าให้เองโดยอัตโนมัติ (แบ่งทีละชุดตาม id) คำตอบของภาพรวม `GET /api/v1/sales/reports/` มีฟิลด์ `unallocatedLines` (จำนวนเต็ม) นับบรรทัดของบิลที่สำเร็จในช่วงวันและตัวกรองเดียวกันที่ส่วนแบ่งยังเป็น null เป็นฟิลด์เพิ่มใน `v1` ถ้ามากกว่า 0 แท็บสินค้าและหมวดหมู่แสดงข้อความ (`role="status"`) ว่ายอดอาจต่างจากภาพรวมจนกว่าขั้นตอนอัปเดตของร้านจะเติมให้ *(การตัดสินใจของผม)*
- **ต้นทุนและกำไรเห็นได้ทุกคนที่มี `reports.read`** เหมือนตอนนี้ ไม่เพิ่มสิทธิ์ใหม่ จะได้ไม่ต้องเปลี่ยนคำตอบของ route เดิม ถ้าต้องการจำกัดภายหลัง เพิ่มเป็นงานแยกได้ *(การตัดสินใจของผม เจ้าของตอบแค่ "ok")*
- **บิลที่ยกเลิกนับในวันที่ขาย** ไม่ใช่วันที่ยกเลิก ตรงกับรายงานตอนนี้ที่แบ่งตาม `created_at` *(การตัดสินใจของผม)*
- **"บิลยกเลิก" ในแท็บพนักงาน** คือบิลที่คนนั้นขายแล้วถูกยกเลิก ส่วนแท็บส่วนลดและยกเลิกแสดงผู้ยกเลิกด้วย ชื่อผู้ยกเลิกไม่ได้เก็บบนบิล จึงอ่านผ่าน port แคบใน `sales` ที่ module `users` implement *(การตัดสินใจของผม)*
- **แพ็คในแท็บสินค้า** แยกเป็นแถวต่อสินค้าและขนาดแพ็ค ชื่อแถวเป็นชื่อสินค้าพร้อมขนาด เช่น "น้ำดื่ม (ลัง 12)" จาก `pack_size` จำนวนแสดงทั้งเป็นแพ็คและเป็นชิ้น ไม่เพิ่มคอลัมน์ snapshot ของแพ็ค *(การตัดสินใจของผม)*
- **ส่งออก Excel** ส่งออกทุกแถวที่ตรงตัวกรองของแท็บหรือมุมมองเจาะลงที่เปิดอยู่ โดยดึงทีละหน้าในเบราว์เซอร์แบบ `collect-pages.ts` ตอนนี้ ไม่เพิ่ม route ส่งออก และใช้ขีดจำกัดแถวของ Excel ที่มีอยู่ *(การตัดสินใจของผม)*

## ให้ผู้สร้างตัดสินใจเอง

- รูปแบบ query ของแต่ละมุมมอง และ index ที่ต้องเพิ่ม
- ลำดับการทำงาน ซึ่งควรแบ่งเป็นหลาย PR เช่น (1) ตัวกรองกับการเทียบ (2) สินค้ากับหมวด (3) เวลากับพนักงาน (4) สมาชิกกับโปรโมชัน (5) ส่วนลดกับยกเลิก และบิล (6) การเจาะลงและส่งออก
- รูปแบบกราฟและตารางความร้อนของแท็บช่วงเวลา ภายใต้ `DESIGN.md`
