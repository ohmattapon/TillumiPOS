# ออเดอร์ค้างและจ่ายทีหลัง

สถานะ: ร่างสำหรับลงมือทำ · roadmap ข้อ 6 · branch `ohmattpon/open-orders`

## เป้าหมาย

ร้านอาหารเปิดออเดอร์ เพิ่มและลบรายการไปเรื่อย ๆ แล้วค่อยชำระตอนจบ ส่วนการขายแบบค้าปลีกที่กดชำระจบในขั้นตอนเดียว (`POST /sales`) ต้องทำงานเหมือนเดิมทุกอย่าง ออเดอร์ที่ชำระแล้วกลายเป็นบิลขายธรรมดา จึงใช้ใบเสร็จ การยกเลิกบิล และสรุปยอดชุดเดิมได้เลย

## การตัดสินใจ

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| ออเดอร์กับบิลขาย | แยกเป็นคนละ aggregate ออเดอร์ชำระแล้วออกบิลขายหนึ่งใบ (`orders.sale_id`) | บิลขายแก้ไม่ได้ ออเดอร์ต้องแก้ได้ จึงไม่ควรเป็นก้อนเดียวกัน และการรายงานเดิมไม่ต้องเปลี่ยน |
| สต็อก | ไม่กันของตอนเพิ่มรายการ ตัดสต็อกตอนชำระเท่านั้น | ออเดอร์ที่ยกเลิกไม่มีอะไรต้องคืน การจองสต็อกเป็นของหลังรุ่นแรก |
| ราคา | เก็บราคาและชื่อสินค้า ณ ตอนเพิ่มรายการ และใช้ราคานั้นตอนชำระ | ลูกค้าจ่ายตามราคาที่สั่ง แม้เมนูเปลี่ยนราคากลางคัน (ข้อ 7 ตัวเลือกเสริมต้องการราคาต่อบรรทัดอยู่แล้ว) |
| รายการซ้ำสินค้าเดิม | รวมเป็นบรรทัดเดียว คงราคาของครั้งแรก | ใบเสร็จอ่านง่าย และชำระผ่านตัวคำนวณเดิมได้ |
| ภาษีและส่วนลด | คำนวณตอนชำระด้วยการตั้งค่าร้านขณะนั้น และเก็บลงบิลเหมือนการขายปกติ | ใช้ `calculateTotals` ตัวเดียวกัน |
| การชำระ | ใช้ตัวคิดเงินเดียวกับ `POST /sales` (port `ISaleCheckout`) | กฎเงิน สต็อก เลขใบเสร็จ อยู่ที่เดียว |
| สิทธิ์ | พนักงานทุกคนเปิด แก้ ชำระ และยกเลิกออเดอร์ของสาขาตนได้ | ยังไม่มีเงินเข้าจนกว่าจะชำระ จึงไม่ต้องจำกัดเหมือนการยกเลิกบิล |
| สาขา | ออเดอร์ผูกกับสาขาที่เปิด ออเดอร์ของสาขาอื่นตอบว่าไม่พบ | ตามกฎสาขาของข้อ 5 |
| ป้ายชื่อ | ช่อง `label` ข้อความอิสระ (เช่น "โต๊ะ 4") ไม่บังคับ | ข้อ 8 จะเพิ่มโต๊ะจริงทีหลัง ไม่ต้องรอ |
| สถานะ | `open` → `paid` หรือ `cancelled` ปิดแล้วแก้ไม่ได้ | ง่ายและไม่กำกวม |

## ข้อมูล

- `orders`: `id`, `branch_id`, `label`, `status` (`open|paid|cancelled`), `opened_by_id`, `opened_by_name`, `sale_id`, `cancel_reason`, `cancelled_by_id`, `created_at`, `updated_at`
- `order_items`: `order_id`, `product_id`, `product_name`, `sku`, `unit_price_satang`, `quantity` และไม่ซ้ำสินค้าเดียวกันในออเดอร์เดียว

## API (ใต้ `/api/v1/orders`, ทุกเส้นทางต้องล็อกอิน)

| เส้นทาง | ทำอะไร |
|---|---|
| `GET /orders?status=open` | รายการออเดอร์ของสาขา (ค่าเริ่มต้น `open`) พร้อมยอดรวม |
| `POST /orders` | เปิดออเดอร์ (`label?`, `items?`) |
| `GET /orders/:id` | รายละเอียด |
| `PATCH /orders/:id` | เปลี่ยนป้ายชื่อ |
| `POST /orders/:id/items` | เพิ่มสินค้า (รวมกับบรรทัดเดิม) |
| `PATCH /orders/:id/items/:productId` | ตั้งจำนวน (1 ขึ้นไป) |
| `DELETE /orders/:id/items/:productId` | เอารายการออก |
| `POST /orders/:id/cancel` | ยกเลิกออเดอร์พร้อมเหตุผล |
| `POST /orders/:id/pay` | ชำระและออกบิลขาย คืนบิลขาย (รูปเดียวกับ `POST /sales`) |

ข้อผิดพลาดใหม่: `ORDER_NOT_FOUND` 404, `ORDER_ITEM_NOT_FOUND` 404, `ORDER_NOT_OPEN` 409, `ORDER_EMPTY` 400, `INVALID_ORDER` 400

## เว็บ

- หน้าขายมีแท็บ "ออเดอร์ค้าง" แสดงรายการออเดอร์ที่เปิดอยู่ของสาขา เลือกเพื่อทำงานต่อ หรือยกเลิกได้
- ตะกร้ามีปุ่ม "เก็บเป็นออเดอร์ค้าง" (ตั้งป้ายชื่อได้) แล้วล้างตะกร้า
- เมื่อทำงานกับออเดอร์ ตะกร้าแสดงรายการของออเดอร์จากเซิร์ฟเวอร์ การเพิ่ม ลดจำนวน และลบรายการเรียก API โดยตรง ปุ่มชำระเรียก `POST /orders/:id/pay`
- การขายขั้นตอนเดียวใช้ตะกร้าในเครื่องเหมือนเดิม

## นอกขอบเขต

โต๊ะและย้าย/รวม/แยกบิล (ข้อ 8), ใบสั่งครัว (ข้อ 9), ตัวเลือกเสริม (ข้อ 7), การจองสต็อก, ชำระบางส่วน, ส่วนลดรายบรรทัด

## เสร็จเมื่อ

- ทดสอบของการขายแบบเดิมผ่านโดยไม่แก้ assertion (ยกเว้นตัวสร้างตัวคิดเงินในไฟล์ทดสอบ unit)
- เปิดออเดอร์ เพิ่ม ลบ ชำระ แล้วได้บิลที่สต็อก VAT เลขใบเสร็จ และสรุปยอดถูกต้องเหมือนขายขั้นตอนเดียว
- ชำระซ้ำหรือแก้ออเดอร์ที่ปิดแล้วไม่ได้ ชำระพร้อมกันสองคำขอสำเร็จเพียงหนึ่ง
- ออเดอร์ของสาขาอื่นเข้าถึงไม่ได้
- `openapi:check` ผ่านหลังบันทึก baseline ใหม่
