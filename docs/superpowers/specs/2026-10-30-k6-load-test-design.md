# Load test ด้วย k6

เจ้าของร้านอยากรู้ว่าระบบรับโหลดได้แค่ไหน และอะไรพังก่อน โดยให้ครอบคลุมที่สุด ไม่ใช่แค่ยิง endpoint ซ้ำๆ แต่ต้องจำลองวันขายจริง ตรวจว่าข้อมูลยังถูกต้องหลังโดนโหลดหนัก และเก็บเป็นชุดที่รันซ้ำได้เพื่อเทียบก่อน/หลังแก้โค้ด

ข้อสมมติที่เป็นของผม (ไม่ได้ถามเจ้าของร้าน ให้ตรวจตอนอ่าน): ขนาดร้านเป้าหมายคือสาขาเดียว (MAIN) สูงสุด 10 เครื่องคิดเงิน รันบนเครื่องเดียวกับฐานข้อมูล ตามที่ AGENTS.md ระบุว่าระบบมี instance เดียว

## เป้าหมาย

- **หาเพดาน:** จำนวนเครื่องคิดเงินที่ขายพร้อมกันได้ก่อน latency หรือ error เกินเกณฑ์ และจุดแรกที่พัง (CPU ของ API, connection ของฐานข้อมูล, lock ของสต็อก, query รายงาน)
- **จำลองวันขายจริง:** ชุดผสมที่คนละบทบาททำพร้อมกัน ไม่ใช่ endpoint เดี่ยว
- **พิสูจน์ความถูกต้องภายใต้โหลด:** หลังรันจบ ตรวจ invariant ในฐานข้อมูลว่าไม่มีเลขใบเสร็จซ้ำ สต็อกไม่ติดลบและตรงกับ ledger เงินที่ชำระรวมตรงกับยอดบิล คำสั่งที่ส่ง idempotency key ซ้ำออกบิลเดียว แต้มสมาชิกตรง ledger
- **วัดทรัพยากร:** CPU/หน่วยความจำของ API และจำนวน connection ฐานข้อมูลระหว่างรัน เพื่อบอกได้ว่าคอขวดอยู่ตรงไหน
- **รันซ้ำและเทียบได้:** ข้อมูลตั้งต้นกำหนดแน่นอน ผลสรุปเป็นไฟล์ JSON ที่เทียบกับรอบก่อนได้

## ไม่ทำ

- ไม่ทดสอบธนาคารจริง SCB/KBank ใช้เฉพาะ fake bank ใน `server/test/` (ตามกฎใน AGENTS.md)
- ไม่ทดสอบ Cloudflare Workers, ความช้าของเครือข่ายอินเทอร์เน็ต และการเรนเดอร์ของเว็บในเบราว์เซอร์ (นั่นคือ e2e)
- ไม่ทดสอบหลาย instance ของ API เพราะระบบออกแบบให้มี instance เดียว (PIN guard และจอลูกค้าเก็บในหน่วยความจำ)
- ไม่ให้ผ่าน/ไม่ผ่านบล็อก PR: load test ช้าและผันผวนตามเครื่อง

## ห้ามเด็ดขาด (anti-goals)

- ห้ามชี้ไปที่ฐานข้อมูลพัฒนา (`pos`), ฐานข้อมูลของร้านจริง, หรือ URL ที่ไม่ใช่เครื่องนี้ ทั้งตัวรันและสคริปต์ k6 ต้องปฏิเสธเอง
- ห้ามมีรหัสผ่านหรือ connection string ในไฟล์ที่ commit ค่าทั้งหมดส่งผ่าน environment ตอนรัน
- ห้ามแก้พฤติกรรมของ API หรือ OpenAPI เพื่อให้ load test ผ่าน ถ้าเจอคอขวดให้รายงาน แล้วแก้เป็นงานแยก

## ที่ทำงานและความปลอดภัยของข้อมูล

- ตัวรัน `bun load/run.ts` สร้างฐานข้อมูลใหม่ชื่อ `pos_load` (หรือขึ้นต้น `pos_load`) บน PostgreSQL ที่ 127.0.0.1:5434 ลบทิ้งแล้วสร้างใหม่ทุกครั้งที่รัน แล้ว migrate และใส่ข้อมูล เหมือนที่ `e2e/run.ts` ทำกับ `pos_e2e`
- ตัวรันปฏิเสธถ้าชื่อฐานข้อมูลไม่ขึ้นต้น `pos_load` หรือโฮสต์ไม่ใช่ `127.0.0.1`/`localhost`
- ตัวรันเปิด API ของตัวเองบนพอร์ตว่าง (`CHECKOUT_MODE=shifts`, `MEDIA_STORAGE=local` ในโฟลเดอร์ชั่วคราว, `COOKIE_SECURE=false`) และเปิด fake bank จาก `server/test/kbank-server.ts` ให้ฝั่งธนาคาร เมื่อจบหรือโดนขัดจังหวะ ปิด process ทั้งหมด
- **ต้องได้รับอนุญาตจากเจ้าของร้านก่อนใช้:** ชื่อฐานข้อมูล `pos_load*` ใหม่บนพอร์ต 5434 (คำอนุญาตเดิมครอบคลุม `pos_test` และ `pos_e2e*` เท่านั้น) และการติดตั้ง k6

## เครื่องมือ

- **k6** เป็นไบนารีแยก ไม่ใช่แพ็กเกจ npm ติดตั้งในเครื่องผ่าน `winget install Grafana.k6` (ต้องขออนุญาตก่อนดาวน์โหลด) ใน CI ใช้ `grafana/setup-k6-action` และตรึงเวอร์ชัน
- สคริปต์เขียนด้วย TypeScript ที่ k6 รันได้โดยตรง (ต้องใช้ k6 รุ่นที่รองรับ TypeScript) อยู่ใน `load/` ที่รากของ repo ตามแนวเดียวกับ `e2e/`
- ตัวรันเป็น Bun ตามโปรเจกต์ ไม่เพิ่ม dependency ใหม่ใน `package.json`

## โครงสร้าง

```
load/
  run.ts              ตัวรัน: ฐานข้อมูล, API, fake bank, k6, เก็บทรัพยากร, ตรวจ invariant, สรุปผล
  seed.ts             ข้อมูลตั้งต้นจำนวนมาก (กำหนดแน่นอน)
  invariants.ts       คำสั่ง SQL ตรวจความถูกต้องหลังรัน
  k6/
    lib/              auth (login ครั้งเดียวต่อ VU), client, ข้อมูลสุ่มแบบกำหนดแน่นอน, checks
    scenarios/        หนึ่งไฟล์ต่อสถานการณ์
    profiles/         smoke, load, stress, spike, soak
  results/            (git-ignored) ผลสรุปต่อรอบ
```

## ข้อมูลตั้งต้น

ขนาดเริ่มต้นเป็นของผม ปรับได้ด้วย environment:

| รายการ | จำนวน |
|---|---|
| สินค้า | 2,000 (มีบาร์โค้ด, แพ็ก, ตัวเลือกเสริมบางส่วน, ติดตามสต็อกส่วนใหญ่) |
| หมวดหมู่ | 30 |
| สมาชิก | 5,000 (มีแต้ม) |
| โปรโมชัน | 20 (ลดตรง, บันเดิล, คูปอง, จำกัดจำนวนครั้ง) |
| บิลย้อนหลัง | 100,000 กระจายใน 12 เดือน (เพื่อให้รายงานมีของให้คำนวณจริง) |
| ผู้ใช้ | เจ้าของ 1, แคชเชียร์ 20 พร้อม PIN |
| เครื่องคิดเงิน | 10 |

บิลย้อนหลังสร้างด้วย SQL ชุดเดียว (`generate_series`) ผ่านเส้นทางเดียวกับ `backfillSaleLines` เพื่อให้ `allocated_*` ครบ ไม่ยิงผ่าน API เพราะช้าเกินไป

## สถานการณ์

หนึ่งไฟล์ต่อหนึ่งสถานการณ์ แต่ละอันใช้ได้เดี่ยวๆ และประกอบเป็นชุดผสมได้

1. **auth**: login พร้อมกัน, `/auth/me`, สลับพนักงานด้วย PIN สถานการณ์นี้ทดสอบ rate limit (login ผิดหลายครั้ง, PIN ผิด 5 ครั้งล็อก 15 นาที) กับผู้ใช้เฉพาะของมันเท่านั้น สถานการณ์อื่นใช้ session ที่ login ไว้ก่อน เพื่อไม่ให้ตัวล็อกบิดผลวัด
2. **catalog**: รายการสินค้า, ค้นหา, ค้นด้วยบาร์โค้ดและบาร์โค้ดแพ็ก, หมวดหมู่, ตัวเลือกเสริม (หนักแบบอ่านอย่างเดียว)
3. **checkout**: ขายขั้นตอนเดียวในโหมดกะ เปิดกะ → สร้าง quote → ขาย (เงินสด, PromptPay, ผสม) → ปิดกะ ใช้ idempotency key เสมอ
4. **orders**: เปิดออเดอร์, เพิ่ม/แก้บรรทัด, ย้ายโต๊ะ, รวมบิล, แยกบิล, จ่าย
5. **qr**: ขอ QR จาก fake bank, โพลสถานะ, refresh, callback จาก fake bank, ยกเลิก, และกรณีผลไม่แน่ชัด (`unknown`)
6. **reports**: overview, สินค้า, หมวดหมู่, พนักงาน, โปรโมชัน กับช่วงวันหลายขนาด (วัน, เดือน, ปี) และตัวกรองต่างๆ รวมถึงการดึงหลายหน้าต่อเนื่องแบบที่ส่งออก Excel ทำ
7. **members**: ค้นสมาชิก, ใช้แต้ม, ปรับแต้ม, ประวัติแต้ม
8. **stock**: รับสินค้า (ทีละรายการและเป็นชุด), ปรับยอด, รายการ low stock
9. **display**: สตรีม SSE ของจอลูกค้าหลายจอพร้อมกันระหว่างมีการขาย
10. **contention** (เน้นความถูกต้อง): เครื่องคิดเงินจำนวนมากขายสินค้าตัวเดียวกันที่สต็อกน้อย, ยกเลิกบิลพร้อมกับขาย, ส่ง idempotency key เดียวกันซ้ำพร้อมกัน, ปิดกะระหว่างมี QR ค้าง
11. **shop-day**: ชุดผสมแบบสมจริง 10 เครื่องคิดเงินขาย + เจ้าของเปิดรายงาน + จอลูกค้า + รับสินค้าเป็นครั้งคราว ในอัตราตามช่วงเช้า/พีคเที่ยง/บ่าย

## โปรไฟล์ (รูปแบบโหลด)

- **smoke**: 1 VU, 1 นาที ใช้ยืนยันว่าสคริปต์และสภาพแวดล้อมถูกต้อง
- **load**: shop-day ที่โหลดตามเป้า 10 เครื่องคิดเงิน ราว 10 นาที
- **stress**: เพิ่มโหลดเป็นขั้นจนเกินเกณฑ์ เพื่อหาเพดานและจุดแรกที่พัง
- **spike**: กระโดดจากโหลดต่ำเป็นสูงทันที แล้วกลับ ดูการฟื้นตัว
- **soak**: โหลดปานกลาง 30–60 นาที ดู memory/connection รั่วและ latency ที่ค่อยๆ แย่ลง

## เกณฑ์ (threshold)

ค่าตั้งต้นของผม ให้ปรับหลังรอบแรก:

- อ่าน (catalog, สมาชิก): p95 < 300 ms
- ขาย/จ่ายออเดอร์: p95 < 800 ms
- รายงาน: p95 < 3 วินาที (ช่วงหนึ่งเดือน) และ < 8 วินาที (ช่วงหนึ่งปี)
- อัตรา error ของคำขอที่ควรสำเร็จ < 1% (ไม่นับ 409/400 ที่เป็นผลที่คาดไว้ เช่นสต็อกไม่พอในสถานการณ์ contention)
- ทุก invariant หลังรันต้องผ่าน 100%
- รอบแรกบันทึกเป็น baseline ไม่ตัดสินว่าล้ม รอบถัดไปเทียบกับ baseline

## ตรวจความถูกต้องหลังรัน (invariant)

`load/invariants.ts` รัน SQL หลัง k6 จบ ถ้าข้อใดไม่ผ่านถือว่ารอบนั้นล้มต่อให้ latency ดี:

- เลขใบเสร็จไม่ซ้ำ
- ไม่มีสต็อกติดลบในสินค้าที่ติดตามสต็อก และ `branch_stock` เท่ากับผลรวมของ ledger
- ผลรวมการชำระของแต่ละบิลเท่ากับยอดรวมของบิล
- คู่ (actor, action, idempotency key) เดียวกันมีบิลได้ไม่เกินหนึ่ง
- `member_point_movements` รวมแล้วตรงกับ `members.points_balance` และไม่มีบิลที่ได้/คืนแต้มซ้ำ
- ไม่มี QR ที่จ่ายแล้วแต่ไม่มีบิลและไม่ได้ dismiss ค้างอยู่ นอกจากที่สถานการณ์ตั้งใจสร้าง
- กะที่ปิดแล้วมี `shift_summaries` และตัวเลขตรงกับบิล

## เก็บทรัพยากรและสรุปผล

- ตัวรันสุ่มวัด CPU/หน่วยความจำของ process API ทุก 2 วินาที และ `pg_stat_activity` (จำนวน connection, lock ที่รอ) เก็บเป็นอนุกรมเวลา
- k6 ส่งสรุปเป็น JSON (`--summary-export`) ต่อสถานการณ์ ตัวรันรวมเป็น `load/results/<เวลา>-<โปรไฟล์>.json` พร้อมผล invariant และกราฟอนุกรมทรัพยากร และพิมพ์ตารางสั้นๆ ที่อ่านได้บนเทอร์มินัล
- คำสั่งเทียบกับผลรอบก่อน (`bun load/compare.ts a.json b.json`) บอกว่า metric ไหนแย่ลงเกินกี่ %

## คำสั่ง

เพิ่มใน `package.json`: `load:smoke`, `load:shop-day`, `load:stress`, `load:spike`, `load:soak`, และ `load` (ส่งโปรไฟล์/สถานการณ์เป็นอาร์กิวเมนต์) เพิ่มคำอธิบายใน `docs/` และบรรทัดใน AGENTS.md ตารางคำสั่ง

## CI

- ไม่รันใน PR ปกติ
- เพิ่ม workflow `workflow_dispatch` ที่รัน smoke และ shop-day ขนาดเล็กบน runner ตัวเลขใน CI ใช้ดูแนวโน้ม ไม่ใช่ตัดสินล้ม เพราะ runner ผันผวน ยกเว้น invariant ที่ต้องผ่านเสมอ

## ความเสี่ยงที่รู้อยู่แล้ว

- เครื่องเดียวกันรันทั้ง k6, API และฐานข้อมูล ตัวเลขจึงเป็นขอบล่างของเครื่องจริง ให้บันทึกสเปกเครื่องไว้ในไฟล์ผล
- fake bank ไม่ช้าเหมือนธนาคารจริง สถานการณ์ QR จึงวัดฝั่งเราเท่านั้น และให้ fake bank ใส่ความหน่วงที่ตั้งได้
- PIN guard และตัวล็อก login อยู่ในหน่วยความจำ ต้องแยกผู้ใช้ของสถานการณ์ auth ออกจากผู้ใช้ที่ใช้ขาย
- การรันซ้ำหลายรอบอาจทำให้ฐานข้อมูลเปลี่ยนสถิติ ตัวรัน `analyze` หลังใส่ข้อมูลตั้งต้นทุกครั้ง

## สิ่งที่ผู้สร้างตัดสินใจเองได้

โครงสร้างของ helper ใน `k6/lib`, รูปแบบคีย์สุ่มแบบกำหนดแน่นอน, ชื่อ metric เฉพาะ (Trend/Counter) ต่อสถานการณ์, รูปแบบกราฟในสรุป
