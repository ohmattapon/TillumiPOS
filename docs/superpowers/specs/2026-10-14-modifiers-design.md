# ตัวเลือกเสริมของสินค้า

สถานะ: ร่างสำหรับลงมือทำ · roadmap ข้อ 7 · branch `ohmattpon/modifiers` (ต่อจาก `ohmattpon/receipts-users-categories`)

## เป้าหมาย

ร้านอาหารและเครื่องดื่มตั้งกลุ่มตัวเลือก เช่น "ระดับความหวาน" และ "ท็อปปิง" ครั้งเดียว ผูกกับหลายสินค้าได้ ตัวเลือกมีราคาเพิ่มและต้นทุนของตัวเอง แคชเชียร์เลือกตอนขาย และยอดบิลกับกำไรคิดตัวเลือกถูกต้อง ฐานนี้ใช้ต่อกับโต๊ะ (ข้อ 8) และใบสั่งครัว (ข้อ 9)

## การตัดสินใจ

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| ขอบเขตของกลุ่ม | สร้างกลุ่มครั้งเดียว ผูกได้หลายสินค้า (many-to-many) | ร้านที่มีหลายเมนูใช้ตัวเลือกซ้ำกัน แก้ราคาท็อปปิงครั้งเดียวมีผลทุกเมนู |
| กฎของกลุ่ม | `required` (บังคับเลือกอย่างน้อย 1) และ `maxSelections` (1 = เลือกอย่างเดียว, สูงสุด 20) | ครอบคลุม "ระดับหวาน (บังคับ 1)" และ "ท็อปปิง (0 ถึง 3)" ด้วยชนิดเดียว ไม่มีขั้นต่ำอื่น |
| ราคาและต้นทุน | ตัวเลือกมี `priceSatang` และ `costSatang` ไม่ติดลบ ใส่ 0 ได้ | กำไรของบิลที่มีท็อปปิงต้องไม่สูงเกินจริง ส่วนลดใช้ส่วนลดของบิลตามเดิม |
| การเก็บบนบรรทัด | snapshot ตัวเลือกเป็น JSON (`options`) บนบรรทัดออเดอร์และบรรทัดบิล | ไม่ join ตอนอ่านบิล ใบเก่าไม่เปลี่ยนเมื่อแก้หรือปิดตัวเลือก ตารางแยกต่อบรรทัดยังไม่จำเป็นเพราะรายงานตัวเลือกอยู่นอกขอบเขต |
| ตัวระบุบรรทัด | `productId` + ชุด `optionId` ที่เรียงแล้ว (`options_key`) | สินค้าเดียวกันตัวเลือกต่างกันต้องแยกบรรทัด ชุดเดียวกันรวมบรรทัด |
| ราคาของบรรทัด | `unitPriceSatang` = ราคาสินค้า + ผลรวมราคาตัวเลือก ต้นทุนบรรทัดบิลบวกต้นทุนตัวเลือกด้วย | `lineTotal`, subtotal, VAT และ `calculateTotals` ใช้ตามเดิมโดยไม่แก้สูตร |
| การตรวจกฎ | เซิร์ฟเวอร์ตรวจตอนเพิ่มรายการและตอนขายขั้นตอนเดียว ใช้ฟังก์ชันล้วนในโดเมนตัวเดียว ไม่ตรวจซ้ำตอนชำระออเดอร์ | ออเดอร์ชำระด้วยราคาและตัวเลือกที่ quote ไว้ ตามกฎของออเดอร์อยู่แล้ว |
| สต็อก | ตัวเลือกไม่ตัดสต็อก | สูตรอาหารและวัตถุดิบอยู่นอกขอบเขต |
| การลบ | ตัวเลือกและกลุ่มปิดใช้ได้ ลบไม่ได้ | บิลและออเดอร์เก่าอ้างถึงได้ เหมือนหมวดหมู่ |
| สาขา | กลุ่ม ตัวเลือก และการผูกกับสินค้าใช้ร่วมทุกสาขา | เหมือนรายการสินค้า หมวดหมู่ และราคา |
| สัญญา API | v1 เพิ่มอย่างเดียว ไม่ขึ้นรุ่นใหม่ | client เดิมที่ไม่ส่ง `options` ทำงานเหมือนเดิม |

## ข้อมูล

ตารางใหม่ (migration `0012_modifiers`):

- `modifier_groups`: `id`, `name`, `required`, `max_selections`, `sort_order`, `is_active`, timestamps
- `modifier_options`: `id`, `group_id`, `name`, `price_satang`, `cost_satang`, `sort_order`, `is_active`, timestamps
- `product_modifier_groups`: `product_id`, `group_id`, `sort_order` (คีย์หลักคู่ `product_id`+`group_id`)

คอลัมน์ใหม่:

- `order_items.options` (jsonb, ค่าเริ่มต้น `[]`) และ `order_items.options_key` (text, ค่าเริ่มต้น `''`) เปลี่ยน unique จาก `(order_id, product_id)` เป็น `(order_id, product_id, options_key)`
- `sale_items.options` (jsonb, ค่าเริ่มต้น `[]`)

แถวเดิมได้ค่าเริ่มต้น จึงเป็นบรรทัดไม่มีตัวเลือก ไม่ต้องย้ายข้อมูล

รูปแบบ snapshot ต่อตัวเลือก: `{ groupId, groupName, optionId, name, priceSatang, costSatang }`

## โดเมน

- `ModifierGroup` และ `ModifierOption`: entity มีการตรวจชื่อ (1–100 ตัวอักษร) `maxSelections` (1–20) ราคาและต้นทุนเป็นจำนวนเต็มสตางค์ไม่ติดลบและไม่เกิน `MAX_AMOUNT_SATANG`
- `resolveLineOptions(groups, selectedOptionIds)` ฟังก์ชันล้วน ได้รับกลุ่ม (พร้อมตัวเลือก) ที่ผูกกับสินค้า และ id ที่เลือก ผลลัพธ์คือรายการ snapshot เรียงตามกลุ่ม พร้อมผลรวมราคา ผลรวมต้นทุน และ `optionsKey` โยน `DomainError` เมื่อ:
  - `MODIFIER_NOT_AVAILABLE`: ตัวเลือกไม่อยู่ในกลุ่มที่ผูกกับสินค้านี้ หรือตัวเลือกหรือกลุ่มถูกปิดใช้
  - `MODIFIER_REQUIRED`: กลุ่มที่ `required` ไม่มีรายการเลือก
  - `MODIFIER_TOO_MANY`: เลือกเกิน `maxSelections` ของกลุ่ม
  - `MODIFIER_DUPLICATE`: เลือกตัวเลือกซ้ำ
- `OrderItem` เพิ่ม `lineId`, `options`, `optionsKey` และ `mergeLines` รวมด้วย `productId` + `optionsKey` การเพิ่มจำนวนและการลบรับ `lineId`
- `SaleItem` เพิ่ม `options` และ `SaleCheckout` ใช้ผลของ `resolveLineOptions` บวกเข้า `unitPriceSatang` และ `unitCostSatang`

## API (โมดูลใหม่ `modifiers`, ใต้ `/api/v1`)

| Use case | ชนิด | เส้นทาง | สิทธิ์ |
|---|---|---|---|
| `ListModifierGroups` | query | `GET /modifier-groups` คืน `{items,total}` พร้อมตัวเลือกในกลุ่ม | ผู้ใช้ที่ล็อกอิน |
| `CreateModifierGroup` | command | `POST /modifier-groups` | เจ้าของ |
| `UpdateModifierGroup` | command | `PATCH /modifier-groups/:id` | เจ้าของ |
| `CreateModifierOption` | command | `POST /modifier-groups/:id/options` | เจ้าของ |
| `UpdateModifierOption` | command | `PATCH /modifier-options/:id` | เจ้าของ |
| `SetProductModifierGroups` | command | `PUT /products/:id/modifier-groups` ส่ง id กลุ่มตามลำดับ แทนที่ทั้งชุด | เจ้าของ |

การเปลี่ยนในเส้นทางเดิม (เพิ่มอย่างเดียว):

- สินค้า: คำตอบเพิ่ม `modifierGroupIds`
- ออเดอร์: `POST /orders/:id/items` รับ `options` (รายการ `optionId` ไม่ส่งคือไม่มีตัวเลือก) คำตอบของบรรทัดเพิ่ม `lineId` และ `options` เพิ่ม `PATCH` และ `DELETE /orders/:id/lines/:lineId` เส้นทาง `/items/:productId` เดิมทำงานกับบรรทัดที่ไม่มีตัวเลือก
- ขายขั้นตอนเดียว (`POST /sales` และ v2): บรรทัดรับ `options` แบบเดียวกัน คำตอบบิลเพิ่ม `options` ต่อบรรทัด
- รหัสข้อผิดพลาดใหม่เพิ่มในเว็บที่ `locales/errors.ts`

OpenAPI baseline ของ v1 และ v2 ต้องบันทึกใหม่ (เพิ่มอย่างเดียว) โดยแจ้งเจ้าของโครงการก่อน

## เว็บ

- feature ใหม่ `modifiers`: หน้า `/modifiers` (เจ้าของเท่านั้น) จัดการกลุ่มและตัวเลือก
- `products`: ฟอร์มสินค้าเลือกกลุ่มที่ผูก
- `pos`: กดสินค้าที่มีกลุ่ม เปิด dialog เลือกตัวเลือกและกดเพิ่มได้เมื่อครบกฎ สินค้าที่ไม่มีกลุ่มเพิ่มทันทีเหมือนเดิม ตะกร้าเก็บ `productId`, `optionIds`, `quantity` และอ่านราคาจาก query ตามกฎเดิม ฟังก์ชันล้วนคำนวณราคาบรรทัดและตัวระบุบรรทัดมีการทดสอบ
- `sales`, `orders`: ใบเสร็จและรายการแสดงตัวเลือกเป็นบรรทัดย่อยใต้สินค้า ราคาฐานของบรรทัดคือราคารวมลบราคาตัวเลือก
- ข้อความผ่าน `t()` ไทยและอังกฤษ

## นอกขอบเขต

ตัวเลือกตัดสต็อกหรือสูตรอาหาร, ตัวเลือกที่ติ๊กไว้ล่วงหน้า, ตัวเลือกราคาติดลบ, หมายเหตุพิมพ์เองต่อบรรทัด (ไปกับใบสั่งครัว ข้อ 9), รายงานตัวเลือกขายดี, จำนวนต่อตัวเลือก (เช่น ช็อต x2)

## เสร็จเมื่อ

- เจ้าของสร้างกลุ่มและตัวเลือก ผูกกับสินค้า และปิดใช้ได้จากหน้าเว็บ
- แคชเชียร์เลือกตัวเลือกตอนขายและตอนเพิ่มลงออเดอร์ ยอดบิลและกำไรรวมตัวเลือก ใบเสร็จแสดงตัวเลือก
- สินค้าเดียวกันที่ตัวเลือกต่างกันแยกบรรทัด ชุดเดียวกันรวมบรรทัด
- กฎบังคับเลือก จำนวนสูงสุด ซ้ำ ผิดกลุ่ม และปิดใช้ ถูกบังคับที่เซิร์ฟเวอร์
- บิลและออเดอร์เก่า และ client v1 ที่ไม่ส่ง `options` ทำงานเหมือนเดิม
- `typecheck`, `test`, `lint`, `openapi:check` (หลังได้รับอนุมัติให้บันทึก baseline) และ `e2e` ผ่าน
