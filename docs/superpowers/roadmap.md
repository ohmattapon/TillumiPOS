# TillumiPOS Roadmap

ปรับปรุงล่าสุด: 2026-10-19 (งานพิมพ์ LAN อยู่บน PR #75, สาขาเหลือสาขาเดียว, ครัวถูกรื้อแล้ว)

## งานที่เพิ่มตามการใช้งานจริง

งานรายงานย้อนหลังรวมเข้า `main` แล้ว มีช่วงวัน ยอดขายและกำไร สินค้าขายดี เปรียบเทียบสาขา และส่งออก Excel รายละเอียดและนิยามตัวเลขอยู่ใน [รายงานย้อนหลัง](../sales-reports.md)

## เป้าหมาย

POS แบบ open source ที่ร้านอื่นนำไปติดตั้งใช้เองได้

- รองรับทั้งร้านค้าปลีกและร้านอาหารในรุ่นแรก
- ชุด Docker เดียวกันรันได้ทั้งบนเครื่องในร้านและบนคลาวด์
- ไทยก่อน แต่ข้อความ สกุลเงิน และอัตราภาษีแยกออกจากโค้ด เพื่อเพิ่มภาษาอื่นได้โดยไม่รื้อ

## วิธีทำงาน

แต่ละชิ้นงานผ่านหนึ่งรอบ: spec (`docs/superpowers/specs/`) → แผนลงมือทำ (`docs/superpowers/plans/`) → ลงมือทำ
ชิ้นถัดไปเริ่มเมื่อชิ้นก่อนหน้าใช้งานได้และทดสอบผ่าน กฎการทำงานอยู่ใน `AGENTS.md`

## ช่วงที่ 1: แกนที่แก้ทีหลังแพง

| # | ชิ้นงาน | เหตุผลของลำดับ | เสร็จเมื่อ | สถานะ |
|---|---|---|---|---|
| 1 | ชุดทดสอบอัตโนมัติของการขายและสต็อก พร้อม CI | ทุกชิ้นหลังจากนี้แก้โค้ดส่วนเงินและสต็อก | ทดสอบรันกับ PostgreSQL จริงด้วยคำสั่งเดียว และรันทุกครั้งที่ push | เสร็จและรวมเข้า `main` แล้ว |
| 2 | ย้ายโครงสร้าง API เป็น Hexagonal | ยิ่งมีโค้ดมาก การย้ายยิ่งแพง และฟีเจอร์ถัดไปควรเขียนบนโครงใหม่ตั้งแต่ต้น | การทดสอบของชิ้นที่ 1 ผ่านครบโดยไม่แก้ assertion และไม่เหลือ `service.ts` | เสร็จและรวมเข้า `main` แล้ว |
| 3 | ปรับสัญญา API ก่อนเผยแพร่ | เปลี่ยนสัญญาหลังมีผู้ใช้คือการทำของคนอื่นพัง | ข้อผิดพลาดเป็น RFC 9457 โดยคงช่อง `code`, รายการคืนพร้อมข้อมูลแบ่งหน้า, เส้นทางอยู่ใต้ `/api/v1` | เสร็จและรวมเข้า `main` แล้ว |
| 4 | การตั้งค่าร้านและโครงรองรับหลายภาษา | VAT เขตเวลา และข้อความไทยฝังอยู่ในโค้ด | ชื่อร้าน เลขผู้เสียภาษี สกุลเงิน อัตราและวิธีคิดภาษีตั้งได้จากหน้าเว็บ ข้อความทั้งหมดอยู่ในไฟล์ภาษา | เสร็จและรวมเข้า `main` แล้ว (ไทย/อังกฤษ, THB และสกุลอื่น, VAT รวม/แยก/ไม่คิด, เก็บกติกาภาษีไว้กับแต่ละบิล) |
| 5 | สาขาเดียว | สต็อก บิล เลขใบเสร็จ และผู้ใช้ผูกกับสาขา | เสร็จและรวมเข้า `main` แล้ว (ย่อเหลือสาขาเดียว `MAIN`: สร้างเพิ่มไม่ได้ ปิดไม่ได้ ไม่มีหน้าจอจัดการสาขา) |
| 6 | ออเดอร์ค้างและจ่ายทีหลัง | ร้านอาหารต้องเปิดออเดอร์ เพิ่มรายการ แล้วค่อยจ่าย ซึ่งเปลี่ยนโครงสร้างการขาย | เปิดออเดอร์ค้าง เพิ่มและลบรายการ แล้วชำระได้ โดยการขายแบบค้าปลีกยังทำได้ในขั้นตอนเดียว | เสร็จและรวมเข้า `main` แล้ว (ออเดอร์เป็น aggregate แยก ชำระผ่านตัวคิดเงินเดียวกับการขายปกติ) |

## งานปรับ design (นอกลำดับ roadmap)

| รอบ | ชิ้นงาน | สถานะ |
|---|---|---|
| 1 | หน้าจอที่ใช้ได้ทุกขนาดจอ: ตารางกลาง `DataTable`, เมนูล่างและแถบตะกร้าบนมือถือ, dialog เลื่อนได้, ผังโต๊ะเป็นรายการบนมือถือ, กฎในไฟล์ `DESIGN.md` | รวมเข้า `main` แล้ว |
| 2 | หน้าแรกเป็นผังโต๊ะสำหรับร้านอาหาร | รวมเข้า `main` แล้ว (ตั้ง "หน้าแรก" ได้ในหน้าตั้งค่า; ฟอร์มเลื่อนเฉพาะฟิลด์) |
| 3 | ถามประเภทร้านตอนตั้งค่าครั้งแรก (คาเฟ่ ร้านอาหาร ค้าปลีก อื่นๆ) แล้วซ่อนเมนูที่ไม่ได้ใช้ | รวมเข้า `main` แล้ว (สวิตช์โต๊ะกับตัวเลือกเสริม ครัวถูกรื้อออกไปแล้วจึงไม่มีสวิตช์ครัว) |

## หลังรุ่นแรก

ลำดับกำหนดตามเสียงผู้ใช้: จัดซื้อและโอนสินค้าระหว่างสาขา, รายงานย้อนหลัง, โปรโมชัน, ชำระเงินอัตโนมัติ (QR ของ SCB ที่ยืนยันยอดเอง เครื่องรูดบัตร), สมาชิกและแต้ม, ขายได้เมื่อเน็ตหลุดพร้อมซิงก์, e-Tax Invoice และเชื่อมระบบบัญชี

ที่เสร็จและรวมเข้า `main` แล้ว: รายงานย้อนหลัง, โปรโมชัน (ลดท้ายบิลพร้อม quote ตรึงราคา), QR ของ SCB (Thai QR Tag 30 พร้อมยืนยันยอดเอง), สมาชิก, สลับคนขายด้วย PIN, จอลูกค้าผ่าน server (SSE), สไลด์ และใบรับสินค้า ส่วนเครื่องรูดบัตรยังไม่ทำ ค่า `SCB_*` อยู่ใน `.env` ของเจ้าของโครงการ ห้ามอยู่ใน `.env.example`
