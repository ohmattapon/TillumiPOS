## Ground truth (verified by reading the code, not assumed)

- `server/src/domains/modifier.domain.ts` — `ModifierGroupEntity`, `ModifierOptionEntity`, `LineOption`, `GroupRules`, `OptionData`, `ModifierGroupWithOptions`, `resolveLineOptions`, `lineKey`. `MAX_GROUP_SELECTIONS = 20`, names 1–100, money non-negative integers (`MAX_AMOUNT_SATANG`).
- `server/src/infrastructure/database/schema/modifiers.ts` — `modifier_options` has `price_satang`, `cost_satang`, `sort_order`, `is_active`, `unique(group_id, name)`, `check('modifier_options_non_negative', ...)`.
- `server/src/modules/modifiers/adapters/repository/modifier.drizzle.repository.ts` — maps rows to entities; `modifier.cached.repository.ts` wraps it: reads go through `IRepositoryReadCache.read('modifiers', …)`, each write calls `source.*` then `cache.changed('modifiers')`. A new column survives the cache because the snapshot is `option.toSnapshot()` and the deserializer builds `new ModifierOptionEntity(row)`.
- The three ports a `cafe-menu` use case needs are already registered against their cached adapters in one container, so it can inject them without a new binding: `categoryRepositoryToken` (`categories.module.ts`), `productRepositoryToken` (`products.module.ts`), `modifierRepositoryToken` (`modifiers.module.ts`), all imported into the container by `modules/di-registrations.ts`.
- `ICategoryRepository` = `findAll | findById | create | update`; `IProductRepository` = `findAll(query) | findById | findManyForUpdate | create(entity, branchId) | update | adjustStock | setImageKey`; `IModifierRepository` = `findAllGroups | findGroupView | findGroupById | findGroupsByIds | findOptionById | findGroupsForProduct | createGroup | updateGroup | createOption | updateOption | setProductGroups`.
- **No `findByName` / `findBySku` anywhere.** Duplicate matching must read once (`findAll()`, `findAll({ branchId, includeInactive: true, limit: 1000 })`, `findAllGroups()`) and match in memory.
- `setProductGroups(productId, groupIds)` **replaces** the product's whole set. It must never be called for a product that already exists.
- `products` list HTTP query allows `limit` up to `1000` (`product.schema.ts`); `page()` in `libs/http-schemas.ts` is the list shape.
- `auth.plugin.ts` takes ONE permission (`true | { can }`), so the other two checks must live in the use case (`requirePermission`).
- `app.module.ts` resolves each controller from the container and chains `.use(...)`; `di-registrations.ts` needs the new module's side-effect import.
- Scripts: `bun run db:generate` (`bun --env-file=.env drizzle-kit generate`), `bun run test:unit` (domains, libs, modules only), `bun run test:api` (needs PostgreSQL), `bun run test:web`, `bun run typecheck`, `bun run lint`, `bun run openapi:check`, `bun run screenshots`, `bun run e2e`.

## Waves

Wave 1 (T1–T4) can be built in parallel — no shared file. Wave 2 (T5–T6) needs Wave 1. Wave 3 (T7–T10) needs the API answer shape settled by T5.

## T1 — `is_default` on a modifier option (domain + migration)

Files: `server/src/domains/modifier.domain.ts`, `server/src/domains/modifier.domain.test.ts`, `server/src/infrastructure/database/schema/modifiers.ts`, `drizzle/0020_*.sql` + `drizzle/meta/*` (generated).

1. Failing test first in `modifier.domain.test.ts`: a `ModifierOptionEntity` built without `isDefault` reports `false`; one built with `isDefault: true` keeps it; `toSnapshot()` round-trips it; `defaultOptionIds([...])` returns the flagged option of each active group in group order, skips inactive groups and inactive options, returns `[]` when nothing is flagged, and returns only one id when two options of the same group are flagged.
2. `ModifierOptionProps` gains `isDefault: boolean`; the constructor normalizes `props.isDefault ?? false` (a 30-second-old read cache may not carry the field yet); `OptionData` picks it up; add `defaultOptionIds`.
3. Add `isDefault: boolean().notNull().default(false)` to `modifierOptions` in the schema.
4. Generate the migration: `bun run db:generate`. The worktree has no `.env` (and the repo rule is one `.env` at the repo root), so run it with the other checkout's file: `bun --env-file=D:/POS/.env drizzle-kit generate` — or export `DATABASE_URL` for the one command. Expect `drizzle/0020_modifier_option_default.sql` containing a single `ALTER TABLE ... ADD COLUMN is_default boolean NOT NULL DEFAULT false`. Do not hand-edit a generated migration; if the number differs, use what the generator wrote.
5. `resolveLineOptions` must **not** change. If a diff appears there, the task is wrong.

Verify: `bun run test:unit`, `bun run typecheck`. `git diff --stat` shows exactly four code files plus the migration.

Race risk: none (pure domain + schema).

## T5 — the `cafe-menu` module and `POST /api/v1/cafe-menu`

Files (new): `server/src/modules/cafe-menu/cafe-menu.module.ts`, `applications/schemas/cafe-menu-schemas.ts`, `applications/usecases/apply-cafe-menu.usecase.ts`, `applications/usecases/apply-cafe-menu.usecase.test.ts`, `adapters/controllers/cafe-menu.controller.ts`, `adapters/controllers/schemas/cafe-menu.schema.ts`. Files (changed): `server/src/modules/di-registrations.ts`, `server/src/modules/app.module.ts`.

1. Failing test first, against the mock ports in `server/src/__tests__/mocks.ts` (add mock category / product / modifier repositories there if the file has none, following the shape of the existing mocks):
   - creates one category, the products and the group with its options for a two-item selection, and links each new product to its groups;
   - a product that exists is skipped, counted, and **not** linked (`setProductGroups` is not called for it);
   - an existing category or group is reused, so `create` is not called for it;
   - an unknown key is rejected with `INVALID_CAFE_MENU_ITEM` and nothing is written;
   - an actor without `categories.write` or without `modifiers.write` is rejected with 403 and nothing is written;
   - the audit log is called exactly once;
   - everything happens inside one `IUnitOfWork.run()`.
2. `apply-cafe-menu.usecase.ts`: `@injectable()`, `/** Command. */`, `execute(input, actor, branchId)`, zod parse first, permissions before any read or write, `IUnitOfWork.run(...)` around the reads and writes, audit last inside the unit of work, and the answer shape from the spec.
3. Read what exists once each: `categories.findAll()`, `modifiers.findAllGroups()`, `products.findAll({ branchId, includeInactive: true, limit: 1000 })`. Match in memory with `planCafeMenu`.
4. Controller: `getRoutes()` like the other controllers, body `{ itemKeys: t.Array(t.String({ minLength: 1, maxLength: 64 }), { minItems: 1, maxItems: 60 }) }`, `auth: { can: 'products.write' }`, `branchId` from `await branch()`, and the response schema.
5. `cafe-menu.module.ts` registers the use case and the controller as singletons; add the side-effect import to `di-registrations.ts` and `.use(container.resolve(CafeMenuElysiaController).getRoutes())` to `app.module.ts` at the top level (not inside the `/catalog` group, because the route is `/api/v1/cafe-menu`).

Verify: `bun run test:unit`, `bun run typecheck`.

Race risk: two applies at once — both read before either writes, so the loser hits a unique constraint (`categories.name`, `modifier_groups.name`, `modifier_options (group_id,name)`, `products.sku`) and its whole unit of work rolls back with a 409. That is the documented behaviour in the spec; do not add a lock.
