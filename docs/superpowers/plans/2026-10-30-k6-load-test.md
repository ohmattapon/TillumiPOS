# k6 Load Test Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A repeatable k6 load test of the API with a runner that owns its throwaway database, API and fake bank, checks data invariants after the run, and writes a comparable result file.

**Architecture:** `load/run.ts` (Bun) creates `pos_load*` on 127.0.0.1:5434, migrates, seeds, starts the API and the fake KBank, spawns `k6 run` per profile, samples API/DB resources, runs SQL invariants and writes `load/results/*.json`. k6 scripts in `load/k6/` are TypeScript modules: one scenario per file, shared helpers in `load/k6/lib/`. Pure logic (guards, data generation, result merge/compare) is plain TS with `bun test` files next to it.

**Tech Stack:** Bun, k6 (TypeScript, installed with `winget install Grafana.k6`; CI uses `grafana/setup-k6-action`), PostgreSQL via `bun`'s `SQL`, the existing `server/test/kbank-server.ts` fake bank.

**Spec:** `docs/superpowers/specs/2026-10-30-k6-load-test-design.md`

## Global Constraints

- The runner and every k6 script refuse any database whose name does not start with `pos_load` or whose host is not `127.0.0.1`/`localhost`; k6 scripts refuse a `BASE_URL` that is not `localhost`/`127.0.0.1`.
- No password, connection string or secret in a committed file: values come from environment variables at run time; the owner password is generated per run.
- No new dependency in `package.json`; no change to API behavior or to `server/test/openapi-baseline.json`.
- The real bank is never called; only `server/test/kbank-server.ts` plays the bank.
- Money is integer satang; checkout runs with `CHECKOUT_MODE=shifts` against `/api/v2`.
- Commit only with `gitcz` (types `feat`, `test`, `docs`, `ci`, `chore`; never `build`), one concern per commit, trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Before saying done: `bun run typecheck` and `bun run test` pass.
- Thresholds (starting values, spec): reads p95 < 300 ms; sale/pay p95 < 800 ms; reports p95 < 3 s (one month) and < 8 s (one year); error rate < 1% of requests expected to succeed; every invariant passes. The first run is a baseline and never fails on latency.

## Review Focus

1. A run interrupted with Ctrl+C or a crash must stop the API, fake bank and k6 and leave no process holding the port (test in Task 1: the cleanup function is idempotent and runs on `SIGINT`).
2. The login lock and PIN lock must not disturb other scenarios (Task 5 uses its own users; test that no other scenario file imports the login helper with the lock user).
3. Two runs back to back must give the same seed data (Task 2: same seed → same product SKUs and bill totals).
4. A scenario that hits an expected 409 (stock shortage in contention) must not count as an error (Task 7: expected statuses are declared per request and the error-rate metric excludes them).
5. An invariant that finds a violation must fail the run even when all latency thresholds pass (Task 9: exit code non-zero, result file marks `passed: false`).
