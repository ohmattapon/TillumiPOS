# Load test ด้วย k6

ชุดทดสอบนี้จำลองวันขายของร้าน (เครื่องคิดเงิน 10 เครื่อง เจ้าของเปิดรายงาน จอลูกค้า รับสินค้า) แล้วตอบสองข้อ ระบบรับโหลดได้แค่ไหน และข้อมูลยังถูกต้องหลังโดนโหลดหนักหรือไม่ ผลทุกรอบเก็บเป็นไฟล์ JSON เพื่อเทียบก่อนและหลังแก้โค้ด

สำหรับผู้พัฒนาและผู้ดูแลระบบ ไม่ใช่เอกสารสำหรับแคชเชียร์ ไม่ต้องติดตั้งอะไรบนเครื่องของร้านที่ใช้งานจริง

แต่ละรอบ ตัวรัน `load/run.ts` ทำสิ่งต่อไปนี้เองทั้งหมด

1. ลบและสร้างฐานข้อมูล `pos_load` ใหม่ แล้ว migrate และใส่ข้อมูลตั้งต้น (สินค้า 2,000 รายการ สมาชิก 5,000 คน บิลย้อนหลัง 100,000 ใบ เครื่องคิดเงิน 10 เครื่อง)
2. เปิด API ของตัวเองบนพอร์ตว่าง และเปิด fake bank (`server/test/kbank-server.ts`) แทนธนาคารจริง
3. สั่ง k6 รันสคริปต์ใน `load/k6/` ระหว่างนั้นวัด CPU/หน่วยความจำของ API และสถานะ connection/lock ของฐานข้อมูลทุก 2 วินาที
4. ตรวจความถูกต้องของข้อมูลด้วย SQL (ดู [ตรวจความถูกต้องหลังรัน](#ตรวจความถูกต้องหลังรัน-invariant))
5. เขียนไฟล์ผลที่ `load/results/<เวลา>-<โปรไฟล์>.json` พิมพ์ตารางสรุปบนเทอร์มินัล แล้วปิด process และลบฐานข้อมูลทิ้ง

## ติดตั้ง k6

k6 ต้องรุ่น **2.3.0 ขึ้นไป** ซึ่งเป็นรุ่นแรกที่รันสคริปต์ TypeScript ชุดนี้ได้โดยตรง

- **Windows:** `winget install GrafanaLabs.k6` (รหัส `Grafana.k6` ไม่มีอยู่จริง) แล้วเปิดเทอร์มินัลใหม่ ถ้า k6 ไม่อยู่ใน PATH ตัวรันจะหาที่ `%ProgramFiles%\k6\k6.exe` ให้เอง
- **Linux และ macOS:** ดูวิธีติดตั้งที่ https://grafana.com/docs/k6/latest/set-up/install-k6/
- **CI:** workflow `load-test.yml` ติดตั้งด้วย `grafana/setup-k6-action` ให้เอง

ตรวจด้วย `k6 version` ถ้าตัวรันหา k6 ไม่เจอ จะพิมพ์คำแนะนำนี้ให้

## สิ่งที่ต้องตั้งก่อนรัน

ต้องมี PostgreSQL ที่รันบนเครื่องนี้ และตั้ง `LOAD_DB_ADMIN_URL` เป็นการเชื่อมต่อแบบผู้ดูแลที่สร้างและลบฐานข้อมูลได้ รูปแบบคือ

```text
postgres://<user>:<password>@127.0.0.1:<port>/postgres
```

PowerShell:

```powershell
$env:LOAD_DB_ADMIN_URL = 'postgres://<user>:<password>@127.0.0.1:<port>/postgres'
bun run load:smoke
```

bash:

```bash
LOAD_DB_ADMIN_URL='postgres://<user>:<password>@127.0.0.1:<port>/postgres' bun run load:smoke
```

ข้อควรระวัง

- ใส่ค่านี้ทางตัวแปรสภาพแวดล้อมของคำสั่งเท่านั้น ห้ามเขียนลงไฟล์ `.env` เอกสาร หรือ commit
- ห้ามมี `?` หรือ `#` ใน URL (ตัวรันปฏิเสธ)
- ใช้ PostgreSQL ที่แยกจากฐานข้อมูลพัฒนา (ไม่ใช่ `pos` ที่ใช้เขียนโค้ดทุกวัน) แม้ตัวรันจะแตะเฉพาะ `pos_load*` ก็ตาม

ตัวแปรอื่น (ไม่บังคับ)

| ตัวแปร | ค่าตั้งต้น | ความหมาย |
|---|---|---|
| `LOAD_DB_NAME` | `pos_load` | ชื่อฐานข้อมูล ต้องขึ้นต้น `pos_load` และมีเฉพาะ `a-z`, `0-9`, `_` |
| `LOAD_SCALE` | `1` | คูณอัตราการมาของลูกค้าทุกสถานการณ์ (มากกว่า 0 ไม่เกิน 100) ใช้ `0.2` บนแล็ปท็อป |
| `LOAD_DURATION_SCALE` | `1` | ย่อเวลา แต่ละช่วงยาวขึ้น x ค่านี้ และอัตราหารด้วยค่านี้ (ดูหัวข้อถัดไป) |
| `LOAD_BASELINE` | `0` | `1` = เกณฑ์ latency ไม่ตัดสินว่าล้ม (ใช้รอบแรก) |
| `LOAD_SEED_<ชื่อ>` | ตามตารางในสเปก | ขนาดข้อมูลตั้งต้น เช่น `LOAD_SEED_PAST_SALES=5000` |

## คำสั่งและโปรไฟล์

| คำสั่ง | โปรไฟล์ | บอกอะไร |
|---|---|---|
| `bun run load:smoke` | smoke: 1 VU ราว 1 นาที (สถานการณ์ `catalog` ถ้าไม่ระบุ) | สคริปต์และสภาพแวดล้อมถูกต้องไหม รันก่อนทุกครั้ง |
| `bun run load:shop-day` | load: วันขายตามเป้า 10 เครื่องคิดเงิน ราว 10 นาที (เช้า 50% พีคเที่ยง 100% บ่าย 60%) | ระบบรับร้านขนาดเป้าหมายได้ไหม นี่คือตัวเลขหลักที่ใช้เทียบ |
| `bun run load:stress` | stress: เพิ่มโหลดเป็นขั้น 1, 2, 4, 6, 8, 10, 15, 20 เท่าของพีค ราว 16 นาที หยุดเองเมื่อ error ถึง 5% | เพดานและจุดแรกที่พัง |
| `bun run load:spike` | spike: เงียบ แล้วกระโดดเป็น 10 เท่าครู่หนึ่ง แล้วกลับ | การฟื้นตัวหลังลูกค้าทะลักเข้ามา |
| `bun run load:soak` | soak: โหลดปานกลาง 45 นาที | หน่วยความจำ/connection รั่ว และ latency ที่ค่อยๆ แย่ลง |

คำสั่งทั่วไปส่งอาร์กิวเมนต์ต่อให้ตัวรัน:

```bash
bun run load <profile> [--scenario <name>] [--keep-db]
```

- `--scenario` เลือกส่วนเดียวของวัน: `checkout`, `orders`, `qr`, `members`, `reports`, `stock`, `display` หรือ `contention` (โปรไฟล์ที่ไม่ใช่ smoke ใช้ `shop-day` เป็นค่าตั้งต้น) `catalog` และ `auth` รันได้ใน smoke เท่านั้น คู่ที่ไม่มีความหมายถูกปฏิเสธก่อนสร้างฐานข้อมูล
- `contention` เน้นความถูกต้อง: เครื่องคิดเงินหลายเครื่องขายสินค้าที่สต็อกน้อยพร้อมกัน ยกเลิกบิลพร้อมขาย ส่ง idempotency key เดิมซ้ำพร้อมกัน และปิดกะระหว่างมี QR ค้าง
- `--keep-db` ไม่ลบฐานข้อมูลเมื่อจบ ไว้ตรวจด้วยมือหลังรันที่ invariant ล้ม

### LOAD_BASELINE และรอบแรก

รอบแรกของเครื่องหนึ่งยังไม่มีตัวเลขเทียบ ให้รันด้วย `LOAD_BASELINE=1` เกณฑ์ latency จะไม่ตัดสินว่าล้ม แต่ตัวรันพิมพ์ p95 ที่วัดได้ทุกรายการ ส่วน check ที่ผิด อัตรา error และ invariant ยังเข้มเหมือนเดิม จากนั้นเก็บไฟล์ผลรอบนั้นไว้เป็น baseline และเทียบรอบถัดไปกับมัน

### LOAD_SCALE และ LOAD_DURATION_SCALE

`LOAD_SCALE=0.2` ลดจำนวนลูกค้าที่มาต่อชั่วโมงเหลือ 20% ตัวเลขจึงเบาลงจริง

`LOAD_DURATION_SCALE` **ไม่ใช่การรันสั้นแบบเบา** มันย่อเวลาแบบ time-lapse ความยาวทุกช่วงคูณค่านี้ และอัตราการมาหารด้วยค่านี้ รอบสั้นจึงมีลูกค้าครบทั้งวันแต่มาถี่ขึ้น เช่น `0.15` กับโปรไฟล์ load ได้ 90 วินาทีที่หนักประมาณ 6.7 เท่าของพีคเที่ยง ใช้เมื่ออยากให้ทุกส่วนของวันได้ทำงานอย่างน้อยหนึ่งครั้งในเวลาสั้น ตัวเลข latency และ throughput ของรอบแบบนี้ **เทียบกับรอบเต็มเวลาไม่ได้** และเทียบกันเองก็แกว่งมาก ตัวรันพิมพ์คำเตือนนี้ทุกครั้งที่ตั้งค่าไม่ใช่ 1

ตัวอย่างรอบเล็กที่ใช้ตรวจว่าทุกอย่างทำงาน:

```bash
LOAD_SCALE=0.2 LOAD_BASELINE=1 LOAD_DURATION_SCALE=0.15 bun run load:shop-day
```

## อ่านผล

### ตารางบนเทอร์มินัล

หลัง k6 จบ ตัวรันพิมพ์

- `Iterations:` จำนวนรอบของแต่ละสถานการณ์
- `Dropped iterations:` ลูกค้าที่ k6 เริ่มไม่ทันเพราะเครื่องคิดเงินทุกเครื่องของสถานการณ์นั้นไม่ว่าง (ใน stress ข้อความ SATURATED แปลว่าถึงเพดานของเครื่องคิดเงินแล้ว)
- ตาราง invariant ว่าแต่ละข้อผ่านหรือไม่
- ตารางสรุป: p95 ของแต่ละคำขอ (ตาม tag `name`, แสดง 10 รายการที่ช้าที่สุด) อัตรา error CPU/RSS/connection/lock ที่รอ และ `Result file:` ตามด้วยที่อยู่ไฟล์

รหัสออกของ `bun run load*`: `0` = ผ่านทั้ง k6 และ invariant, `1` = k6 ข้ามเกณฑ์ (รหัส 99) หรือสคริปต์หยุด หรือมี invariant ล้ม ข้อความบอกว่าข้อไหน

### ไฟล์ผล (`load/results/*.json`, schemaVersion 1)

โฟลเดอร์นี้ถูก git ละเว้น

| ฟิลด์ | ความหมาย |
|---|---|
| `schemaVersion` | `1` เลขจะเพิ่มเมื่อฟิลด์เปลี่ยนความหมายหรือหายไป `compare.ts` ปฏิเสธรุ่นอื่น |
| `startedAt`, `profile`, `scenario` | เวลาเริ่ม (UTC) โปรไฟล์ และสถานการณ์ |
| `passed` | `false` เมื่อ k6 ข้ามเกณฑ์ หรือ invariant ข้อใดล้ม หรือรัน invariant ไม่ได้ |
| `machine` | `cpus`, `memoryGb`, `os`, `k6Version` ไว้ดูว่าตัวเลขมาจากเครื่องแบบไหน |
| `knobs` | `scale`, `durationScale`, `baseline` ตามตัวแปรที่ตั้ง |
| `seed` | ขนาดข้อมูลตั้งต้นที่ใช้ (จำนวนเท่านั้น) |
| `k6` | `exitCode` และ `metrics`: ค่าตัวเลขของทุก metric (`count`, `rate`, `avg`, `med`, `max`, `p(90)`, `p(95)`, `p(99)`, `passes`, `fails`) |
| `invariants` | ผลตรวจข้อมูลแต่ละข้อ (`name`, `passed`, `violations`, ตัวอย่างที่ผิดไม่เกิน 5 ราย) |
| `resources` | `peak`, `mean` ของ CPU (เป็น % ของแกนเดียว เกิน 100 ได้) RSS (MB) connection และ lock ที่รอ พร้อม `series` อนุกรมเวลาไม่เกิน 600 จุด (`null` = อ่านไม่ได้) |

ไฟล์ผลไม่เก็บ URL รหัสผ่าน token หรือค่า environment ใดๆ เก็บแค่ชื่อ metric ตัวเลข และตัวอย่างข้อมูลที่เป็น id กับตัวเลข

## เทียบสองรอบ

```bash
bun load/compare.ts load/results/<ก่อน>.json load/results/<หลัง>.json [--tolerance 10] [--force]
```

พิมพ์ metric ที่เปลี่ยนพร้อมเปอร์เซ็นต์ และนับตัวที่แย่ลงเกิน `--tolerance` (ค่าตั้งต้น 10%) การเปลี่ยนที่เล็กมาก (เช่น 0 เป็น 0.2 ms) ไม่นับ ความล้มเหลวที่รอบก่อนไม่มีนับว่าแย่ลงเสมอ

| รหัสออก | ความหมาย |
|---|---|
| `0` | ไม่มีอะไรแย่ลงเกินเกณฑ์ |
| `1` | มีอย่างน้อยหนึ่งตัวแย่ลง |
| `2` | เทียบกันไม่ได้: โปรไฟล์ สถานการณ์ ขนาดข้อมูล `LOAD_SCALE` หรือ `LOAD_DURATION_SCALE` ต่างกัน อ่านไฟล์ไม่ได้ หรือ schemaVersion ต่างกัน |

`--force` เทียบต่อแม้เงื่อนไขไม่ตรง (ใช้อ่านเทรนด์คร่าวๆ อย่าใช้ตัดสิน) เทียบเฉพาะรอบที่ตั้งค่าเหมือนกัน บนเครื่องเดิมที่ว่างเท่ากัน

## เกณฑ์ (threshold) และการปรับ

เกณฑ์ตั้งต้นเป็นสมมติฐานของผู้ออกแบบ ให้ปรับหลังรอบแรกจริง

| เรื่อง | เกณฑ์ |
|---|---|
| อ่านทั่วไป (catalog, สมาชิก, quote, สร้าง session จอลูกค้า) | p95 < 300 ms |
| ขาย, จ่ายออเดอร์, เปิดออเดอร์, ขอ QR, ปรับแต้ม, login | p95 < 800 ms |
| รายงาน | ช่วงวัน < 1 วินาที, เดือน < 3 วินาที, ปี < 8 วินาที |
| คำขอที่ควรสำเร็จแต่ล้ม (`expected_failed`) | อัตรา < 1% (409/400 ที่เป็นผลที่คาดไว้ เช่นสต็อกไม่พอใน contention ไม่นับ) |
| `checks` ของ k6 | ผ่านมากกว่า 99% |
| ปิดกะไม่สำเร็จ, VU หาเครื่องคิดเงินไม่ได้ | ต้องเป็น 0 |
| invariant | ต้องผ่านทุกข้อ |
| stress | หยุดทันทีเมื่อ error หรือ check ล้มเกิน 5% (รอตัวเลขนิ่งก่อน 1 นาที ย่อตาม `LOAD_DURATION_SCALE`) |

แก้ตรงไหน

- เกณฑ์ latency ของแต่ละสถานการณ์ อยู่ที่ `export const options` ในไฟล์ `load/k6/scenarios/<ชื่อ>.ts` (เช่น `'http_req_duration{name:checkout.sale}': ['p(95)<800']`)
- เกณฑ์ที่ใช้ทุกสถานการณ์ (`expected_failed`, `checks`, stress abort) อยู่ใน `load/k6/lib/thresholds.ts`
- อัตราลูกค้าต่อเครื่อง จำนวนเครื่องคิดเงินของแต่ละส่วน และขั้นของ stress อยู่ใน `load/k6/lib/mix.ts`
- แก้แล้วรัน `bun run test:load` ให้ผ่านก่อน

โหมด baseline (`LOAD_BASELINE=1`) ปลดเฉพาะเกณฑ์ latency ตามที่อธิบายข้างบน

## ตรวจความถูกต้องหลังรัน (invariant)

`load/invariants.ts` รัน SQL หลัง k6 จบ ข้อใดล้มถือว่ารอบนั้นล้ม แม้ latency ดี แต่ละข้อคืนจำนวนที่ผิดและตัวอย่างไม่เกิน 5 รายการ ที่เป็น id และตัวเลขเท่านั้น

| ข้อ | ตรวจอะไร |
|---|---|
| `receipt_numbers_unique` | เลขใบเสร็จไม่ซ้ำ |
| `stock_not_negative` | สินค้าที่ติดตามสต็อกไม่มีสต็อกติดลบ |
| `stock_matches_ledger` | `branch_stock` เท่ากับผลรวม `stock_movements` ต่อสาขาและสินค้า และไม่มี ledger ที่ไม่มีระดับสต็อก |
| `payments_match_bill` | ผลรวมการชำระเท่ากับยอดที่รับ และยอดรับหักเงินทอนเท่ากับยอดรวมบิล |
| `one_bill_per_idempotency_key` | (ผู้ทำ, action, idempotency key) เดียวกันมีบิลได้ไม่เกินหนึ่ง และบิลหนึ่งใบไม่เกิดจากสองใบรับคำสั่ง |
| `points_balance_matches_ledger` | `members.points_balance` เท่ากับผลรวม `member_point_movements` |
| `points_once_per_sale` | แต่ละบิลได้และคืนแต้มไม่ซ้ำ แต้มที่ได้ตรงกับบิล และบิลที่ยกเลิกคืนแต้มที่ใช้ครบ |
| `paid_qr_has_bill` | ไม่มี QR ที่จ่ายแล้วแต่ไม่มีบิลและเจ้าของไม่ได้ dismiss |
| `closed_shift_has_matching_summary` | กะที่ปิดแล้วมี `shift_summaries` และจำนวนบิล ยอดขาย เงินทอน และยอดแต่ละวิธีชำระตรงกับบิล |
| `line_shares_add_up_to_bill` | ส่วนแบ่งของทุกบรรทัด (`allocated_total`, `allocated_vat`) รวมเท่ากับยอดและ VAT ของบิล |
| `void_returns_each_line` | บิลที่ยกเลิกคืนสต็อกครบทุกบรรทัดตามชิ้นและแพ็ก และบิลที่ไม่ได้ยกเลิกไม่มีรายการคืน |

ถ้าเขียนข้อใหม่ ให้เพิ่มใน `CHECKS` ของไฟล์นั้นพร้อมเทสต์ที่เห็นมันล้มก่อน

## ความปลอดภัยของข้อมูล

- ตัวรันทำงานกับฐานข้อมูลชื่อ `pos_load*` บนเครื่องนี้เท่านั้น ชื่ออื่นหรือโฮสต์ที่ไม่ใช่ `127.0.0.1`/`localhost` ถูกปฏิเสธก่อนทำอะไร และ `pos_load` ถูก **ลบแล้วสร้างใหม่ทุกรอบ** อย่าเก็บอะไรไว้ในนั้น
- ห้ามชี้ไปที่ฐานข้อมูลพัฒนา ฐานข้อมูลของร้าน หรือ `pos_test`/`pos_e2e*`
- ไม่เรียกธนาคารจริง ตัวรันเคลียร์ค่า SCB เป็นค่าว่างและชี้ API ไปที่ fake bank ที่เปิดในเครื่องเอง
- รหัสผ่านและ PIN ของผู้ใช้ทดสอบสุ่มใหม่ทุกรอบ และส่งให้ k6 ทาง environment ของ process เท่านั้น ไม่ขึ้นบรรทัดคำสั่ง ไม่เขียนลงไฟล์
- ไฟล์ผลและบันทึกที่พิมพ์ไม่มีข้อมูลลับ (URL ในข้อความจากเครื่องมือถูกปิดบัง) ถ้าส่งไฟล์ผลให้คนอื่น ให้ดูสักครั้งว่าไม่มีอะไรที่ไม่ควรมี
- ถ้ารันถูกขัดจังหวะ (Ctrl+C) ตัวรันปิด process ทั้งหมดและลบฐานข้อมูลเอง

## ข้อจำกัดที่ควรรู้

- เครื่องเดียวกันรันทั้ง k6 API และฐานข้อมูล แย่งซีพียูกัน ตัวเลขจึงเป็นขอบล่างของเครื่องจริง ไฟล์ผลบันทึกสเปกเครื่องไว้
- fake bank ไม่ช้าเหมือนธนาคารจริง สถานการณ์ QR จึงวัดเฉพาะฝั่งของเรา
- stress ถูกจำกัดด้วยเครื่องคิดเงิน 10 เครื่อง (เครื่องหนึ่งรับลูกค้าได้ทีละคน) เมื่อระบบช้ากว่าอัตราที่ลูกค้ามา ผลจะออกมาเป็น `dropped_iterations` ไม่ใช่ latency ที่พุ่งไปเรื่อยๆ
- session และตัวล็อก PIN/login อยู่ในหน่วยความจำของ API (instance เดียว) สถานการณ์ auth จึงใช้ผู้ใช้ของตัวเอง ไม่ปนกับผู้ใช้ที่ขายของ
- รอบ time-lapse (`LOAD_DURATION_SCALE` ไม่ใช่ 1) แกว่งมาก ส่วนที่มาไม่บ่อย (รับสินค้า รายงาน) มีตัวอย่างเพียง 1-2 ครั้ง p95 ของมันจึงเป็นค่าเดียว
- ใน shop-day คำขอสตรีมของจอลูกค้า (`display.stream`) ถูกค้างไว้หลายวินาทีโดยตั้งใจ ตัวเลข "(all requests)" ในรอบนั้นไม่มีความหมาย ให้ดูตามชื่อคำขอ และ `compare.ts` ข้ามตัวเลขรวมนั้นให้
- ตัวอ่านทรัพยากรบน Linux (`/proc`) ทดสอบกับข้อความตัวอย่างเท่านั้น ตัวบน Windows ใช้งานจริงแล้ว

## สิ่งที่พบจากการรันรอบแรก

ข้อสังเกตเท่านั้น ไม่ได้แก้ API (การตัดสินใจเป็นของเจ้าของโปรเจกต์) รายงานเต็มอยู่ใน `.superpowers/sdd/2026-10-30-k6-load-test/` (`task-8-report.md`, `task-9-report.md`)

- **deadlock ของ PostgreSQL ใน stress:** รอบ stress ย่อเวลา (`LOAD_DURATION_SCALE=0.0625`) พบ `deadlock detected` 7 ครั้งใน log ของ API (0 ครั้งใน load และ spike) ทำให้ขาย 3 ครั้งและจ่ายออเดอร์ที่มี quote 3 ครั้งตอบ 500 วงรอที่เห็นเกี่ยวกับ: การ insert ลง `sales` (foreign key ไปที่ `promotions` แบบ `FOR KEY SHARE`), การล็อกแถวโปรโมชันด้วย `lockForUse` และการ insert ลง `receipt_counters` ลำดับล็อกใน AGENTS.md (order, QR, quote, promotion, member, product) ไม่ได้พูดถึง `receipt_counters`
- **เงิน QR ค้างไม่มีบิลหลัง deadlock:** ในรอบ stress เดียวกัน invariant `paid_qr_has_bill` ล้ม 4 รายการ (QR สถานะ paid ไม่มี `sale_id` ไม่ได้ dismiss) ใน `task-9-report.md` อธิบายว่าธนาคารรับเงินแล้ว แต่ transaction ขายถูก rollback จาก deadlock และ API ปฏิเสธปิดกะที่เกี่ยวข้อง ข้อมูลอื่นผ่านทุก invariant สถานการณ์ `qr` ยังไม่ลองขายซ้ำด้วย QR ใบเดิมหลังได้ 500 และไม่ให้เจ้าของ dismiss
- **jsonb ถูกเข้ารหัสซ้ำ:** `command_receipts.result` และ `shift_summaries.summary` ที่ API เขียนเป็น jsonb ที่เก็บ *สตริง* ของ JSON ส่วน seed เขียนเป็นออบเจ็กต์ invariant อ่านได้ทั้งสองแบบ ถ้าเขียน SQL เองกับสองคอลัมน์นี้ต้องใช้ `#>> '{}'`

## รันใน CI

Workflow `.github/workflows/load-test.yml` รันด้วยมือเท่านั้น (Actions แล้วเลือก Run workflow) ไม่รันกับ PR มันรัน `load:smoke` แล้วรันโปรไฟล์ load ตาม `scale` ที่เลือก (ค่าตั้งต้น 0.2) และอัปโหลด `load/results/` เป็น artifact ค่าตั้งต้น `baseline` เป็นจริง latency จึงไม่ทำให้ job ล้ม เพราะ runner ผันผวน แต่ invariant และ check ที่ผิดทำให้ล้มเสมอ ตัวเลขใน CI ใช้ดูแนวโน้ม

## เทสต์ของชุดนี้

```bash
LOAD_DB_ADMIN_URL='postgres://<user>:<password>@127.0.0.1:<port>/postgres' bun run test:load
```

`bun run test:load` อยู่นอก `bun run test` เพราะเทสต์ส่วนหนึ่ง (seed และ invariant) ต้องใช้ฐานข้อมูล ถ้าไม่ตั้ง `LOAD_DB_ADMIN_URL` เทสต์ที่ต้องใช้ฐานข้อมูลจะถูกข้าม ส่วนที่เหลือรันได้ `bun run typecheck` ตรวจโฟลเดอร์ `load/` ด้วย (`tsc -p load`)
